# Architecture

This document records the product changes from `init-design/SPEC.md` and the technical design. When it disagrees with the SPEC, this document wins. Everything the SPEC says that is not changed here still applies.

## 1. Product changes from the SPEC

### 1.1 Statuses are data, per project

- Each project owns its statuses. New projects get five defaults (`DEFAULT_STATUSES` in `packages/shared/src/domain/status.ts`):

  | Name        | Category      | Color     | Glyph                                            |
  | ----------- | ------------- | --------- | ------------------------------------------------ |
  | To do       | `todo`        | `#8E8E99` | empty ring                                       |
  | In progress | `in_progress` | `#C26A06` | ring + half pie                                  |
  | Need review | `in_review`   | `#0B68CB` | ring + three-quarter pie                         |
  | Reviewed    | `reviewed`    | `#18794E` | ring + full pie                                  |
  | Done        | `done`        | `#5B5BD6` | filled circle + check (SPEC glyph and animation) |

- The **category** gives a status its meaning and glyph shape; the **color** is the glyph color. Users can create, rename, recolor, recategorize, reorder and delete statuses. Names are unique per project (case-insensitive). A project keeps at least one status. Deleting a status that has tickets requires a target status; those tickets move to the end of the target group.
- Glyph shapes stay distinguishable without color: 0, 1/2, 3/4, full pie, check.
- `resolveStatus(statuses, category)` (shared) finds the status to use for a workflow step, with fallbacks when a category is missing.
- **Done** means category `done`. Progress %, open counts and overdue all use the category.
- Groups on the Project screen follow status order (position). Keyboard and drag moves cross groups in that order.
- The Project screen's filter is **All** plus one tab per status, in status order (§1.7).

### 1.2 The agent workflow

```
To do ──claim──▶ In progress ──submit──▶ Need review ──review: approved──▶ Reviewed ──person──▶ Done
   ▲                                          │
   └────────────── review: changes requested ─┘
```

- **Worker agent:** finds work with `claim_next_ticket` (category `todo`, ordered High → Low priority, then manual order, then number), works, comments as it goes, then `submit_for_review` with a summary, files and next steps. Submitting stores a report card and moves the ticket to the `in_review` status.
- **Reviewer agent:** lists `in_review` tickets, checks the work against the title, description and comments, then `review_ticket` with a verdict (`approved` / `changes_requested`), a 1–5 rating and a summary. Approved moves the ticket to `reviewed`; changes requested moves it to the top of `todo` so a worker picks it up next.
- **Agents can never move a ticket to a `done` status** (API returns 403). Only a person does that.
- Activity has an **actor**: `{ kind: 'human' | 'agent', name }`. People show as "You"; agents show by name with the terminal tile. Requests set the actor with `x-actor-kind` / `x-actor-name` headers (name URI-encoded). No header means the person.
- New activity type **review** renders as a card with the verdict, star rating and summary.
- A report whose text is TICKET / STATUS / SUMMARY / FILES / OUTPUT / NEXT fields (a submission, or a pasted Claude Code report, Markdown marks allowed) renders as labeled sections instead of the raw mono block (`features/ticket/activity/reportSections.ts`): a status line ("Submitted for review" when the STATUS words mean done, otherwise "Status: …" as written), Summary in body text, Next on a highlighted panel, then Output (the files Claude attached with `attach_file`, §4, PT-191) and Files, each one per line in mono and read the same way. A file list written over several lines keeps each line whole; a list on one line is split on commas outside brackets, so "src/a.ts (parser, tests)" stays one file. More than 6 files show the first 5 and a "Show N more" text button (§7.3's rule, 44px target, `aria-expanded`, "Show less" when open; `ReportFiles.tsx`). Next, Output and Files are left out when they say "none", also with Markdown marks around it ("**none**"). Submissions write labels in capitals, so when a field has a capital label, a line in another case that starts with the same word ("Next: …" or "Status: …" in a summary) is text of the field above it. Text before the first field, a field given twice or no SUMMARY keeps the raw text.
- Comments can be edited (sets `editedAt`, shows "edited") and deleted. Reports and reviews can be deleted. Events cannot be edited or deleted.

### 1.3 The copy/paste loop still exists

"Send to Claude Code" and "Paste report" work as in the SPEC, for agents without the MCP tools:

- Prompts are built on the server (`GET /api/tickets/:key/prompt`, `GET /api/projects/:key/prompt`) with the shared builders. Status labels use the status names. The ticket block also shows the last review (`Last review: Changes requested · 2/5` + summary). A ticket in an `in_review` status gets the review prompt instead (PT-193, `buildReviewPrompt` in `logic/reviewPrompt.ts`): review this one ticket with the tracker MCP tools, as `/mcp__tracker__review` does for all of them (read the ticket and the worker's report, check the real result, rate 1–5, call `review_ticket`, never move to Done), with the worker's report and any earlier review under the ticket block and no paste-back block. The answer says which with `role: work | review` (`roleForCategory`); the project prompt is always `work`. The reply format adds an `OUTPUT:` line after `FILES:` for results that aren't code, attached with `attach_file` (§4, PT-191).
- "Open tickets" for the project prompt means categories `todo` and `in_progress`, ordered in-progress first, then priority, then number.
- The switch reads "Move MOB-3 to {in_progress status name}" and shows for tickets in a `todo` status.
- Report STATUS words map to categories (`normalizeReportStatus`): reviewed/approved/verified → `reviewed`; done/complete/fixed/finished/resolved and review words → `in_review`; not started → `todo`; progress/partial/blocked/wip/started/ongoing → `in_progress`; to do → `todo`. A report never sets Done, and never moves a ticket in a `reviewed` or `done` status to a status that is not in a later category in `STATUS_CATEGORIES` order (`reportMayMove`, PT-173): a reviewer's own "STATUS: done" report used to send an approved ticket back to Need review, and "STATUS: approved" moved a ticket in a custom reviewed status ("QA passed") back to Reviewed. The ticket stays in its status, the report is still added to the activity, and the Paste report preview shows "Add report" for it.

### 1.4 Attachments

- Tickets (under the description) and comments can have attachments of four kinds. The text fields stay plain text. The rules live in `packages/shared/src/domain/attachment.ts` (`ATTACHMENT_TYPES`, `ATTACHMENT_KINDS`):

  | Kind    | Types (extensions)                              | Up to  |
  | ------- | ----------------------------------------------- | ------ |
  | `image` | PNG, JPEG (jpg, jpeg), GIF, WebP, HEIC, HEIF    | 15 MB  |
  | `video` | MP4, QuickTime (mov, as iPhones record), WebM   | 100 MB |
  | `text`  | Plain text (txt, log), Markdown (md), CSV, JSON | 5 MB   |
  | `pdf`   | PDF                                             | 25 MB  |

- No SVG or HTML: opened from the tracker's address they could run script.
- The type the browser gives decides. When it is empty, `application/octet-stream` (common for .log and .md), `application/vnd.ms-excel` (Windows, for .csv) or `text/x-markdown`, the extension decides (`resolveAttachmentType`). Other names systems give an allowed type count as it and the file keeps the allowed type (`text/x-log` as `text/plain`; `text/x-csv`, `application/csv` and `text/comma-separated-values` as `text/csv`; `image/jpg` as `image/jpeg`). Any other declared type is refused whatever the name. `checkAttachment(file)` gives the stored type and kind, or the message to show: one per kind from `tooLargeMessage` ("Videos can be up to 100 MB.") or `UNSUPPORTED_ATTACHMENT_MESSAGE`, which lists what can be attached. File inputs use `ATTACHMENT_ACCEPT` (every type and extension, because some systems give .log and .md no type; but not HEIC or HEIF, and JPEG first: iOS Safari converts a picked photo to the first type listed unless the list takes HEIC, so iPhones send JPEG, which the server shrinks and strips of its GPS location, PT-128. A HEIC that arrives another way, dropped on a Mac or sent by an agent, is still taken and stored as it came, like a video with its location: refusing it would turn away a file the person chose, with nothing they could do in the tracker instead), and `attachmentKind(mimeType)` tells how to show a stored attachment.
- **Adding files** (`features/attachments`): New ticket and the ticket screen (under the description), quick capture and the comment box take every kind: from **Add files** (in the comment box the paperclip **Attach files**), which on phones offers the photo library, the camera and Files (`ATTACHMENT_ACCEPT`); by paste into their text fields; and by drag and drop on desktop. `admitFiles` checks each file with the shared rules, and New ticket, quick capture and the comment box take up to 20 files (`MAX_NEW_ATTACHMENTS`), the ticket screen any number. What didn't go is said in the picker area (`FileNote`, `role="alert"`), not in a toast, which is gone after 2.2 s and cut to one line on a phone: "notes.svg can't be attached." (or "notes.svg and 2 more…") over the reasons, here the list of what can be attached, or "A new ticket can have up to 20 files."; and "clip.mov didn't upload." over why (`uploadFailureReason`: the bare 408 and 413 that Node and proxies send become "It took too long to send. Try again on a faster connection." and "The server won't take a file this big."; a bare 5xx, which a proxy for a stopped API sends but so can the API itself or a proxy whose connection broke during one upload, "The tracker couldn't save it. Try again.", since only a check of the tracker tells them apart and the banner says when it can't be reached: it said "Can't reach the tracker. Check your connection." while the tracker answered everything else, PT-109). What a pick left out and the uploads that failed since are two notes (`useFileNotice`); they stay until the next pick, a dismiss or a sent comment, and uploads that fail while the second is up join it. In New ticket, quick capture and the ticket screen the pick's note tops the file area, where Add files was, so the tiles of a big pick can't push it below the fold (PT-72: 21 files at 320×568), and it is scrolled into view at once (`block: 'nearest'`) for a pick from the Add tile under many files. A failure comes later, while the person may be anywhere, and Safari keeps no scroll anchor, so its note goes below the files and the Add tile: a note above them pushed every tile on screen down 53–70px, or landed unseen under the sheet's header (PT-72 review). The failed file keeps its tile among the uploads that follow the saved files, the picture dimmed under an alert mark in a red frame ("late.png didn't upload", `UploadThumbnail`), until its x, the note's Dismiss or the next pick lets it go: a tile that just went let the Add tile slide into its place and nothing in view said why (PT-95, 320×568 scrolled to the middle of 16 files). It holds back neither Create nor Comment (`uploads.uploading` leaves it out, `uploads.tiles` has it). When the note is out of sight, below the fold from the Add tile or from the middle of the files at 320×568 (on the ticket screen the tile can be out of sight too), a toast says it too and moves nothing (`useToastIfUnseen`, a hit test at the note's middle, `inSight`). In the comment box both notes sit just above Attach files; it keeps no failed tile, so when its late note is out of sight (from its first files at 320×568) a toast says it too (`FileNotes`, PT-101). A tap on Dismiss takes the note and its place at once, and for 500 ms (`CLICK_SHIELD_MS`) the screen or sheet it was on takes no taps, nor a double-click's later clicks (`holdPresses`; a mouse's single click and a key press go through, as on an action sheet, and on a screen so do taps on its nav bar and bottom bar while they stay where they were: the fixed or sticky bars a hit test finds at its top and bottom edges, not one the note is in, PT-101; from 768px so do taps on the header and the sidebar, found at the top and left edges beside the scroller the note is in, so that only that scroller's box could move them, PT-109, where a tablet held them too; a sheet holds all of itself, since one that fits its content shrinks with the note, so its header moves too and the scrim it uncovers would close it): what lay below slides up under the finger, or on a screen scrolled to its end, and in a sheet that fits the screen, what lay above slides down, and the second tap of a double tap pressed it: a draft file's x, the ticket screen's x, Comment or a field (PT-72 review, WebKit at 320×568 and 375×812). A note that kept its place for those 500 ms instead closed in one jump later, under a tap aimed at what the gap showed (PT-95). A key press, or a click with no pointer before it such as VoiceOver's (PT-101), dismisses without the hold (a press that ended off Dismiss, such as a mouse dragged off, or that the browser cancelled is no pointer before it, as on action sheets, §1.5, PT-106) and leaves focus where files are added, not on the page body: on Add files (the Add tile, or the button when the files are folded or there are none) or, in the comment box, on the next control, Attach files (`focusFirst`). Focus moves once the note and its failed tiles have gone (`flushSync`): when the failed file was the only tile, the Add tile that had focus gave way to the Add files button and focus fell to the body (PT-95 review). A ticket's upload that fails after its screen has closed is told in a toast. Photos are checked after the web app shrinks those past the server's pixel budget and converts HEIC (`lib/uploads.ts`, §3 PT-134), which brings most large ones under the limit. Each file uploads at once and shows a progress ring on its tile (`TrackerClient.uploadAttachment` reports progress through XMLHttpRequest, which fetch can't; Node falls back to fetch) and an x that stops it. Tiles keep the order the files were picked: in New ticket, quick capture and the comment box a file that finishes before one picked ahead of it waits in its tile with a full ring until that one is up (`usePickedOrder`), and its x then deletes it; on the ticket screen, where each file joins the ticket as it arrives, finished files go after the ticket's others in the order they finish. New ticket, quick capture and the comment box send their files' ids, in picked order, when they create; Create and Comment wait while a file is still uploading. Closing New ticket or quick capture without creating stops their uploads and deletes the uploaded files.
- Upload first (`POST /api/attachments` with the file itself as the body and an optional `?ticketKey=`, §3); without `ticketKey` the attachment is pending until a ticket or comment is created with its id in `attachmentIds` (or a create repeating a client id names it, §3), at most 20 (`tooManyFilesMessage`: "A new ticket can have up to 20 files.", "A comment can have up to 20 files."). The files list in the order of `attachmentIds` (`attachments.position`); a file uploaded to a ticket later goes after the ticket's others. Pending attachments older than 24 hours are deleted on startup. How files are stored and served: §3.
- **Tiles** (`ThumbnailGrid`), under the description and inside comment cards: images as before; videos show their first frame (a film icon until one is drawn, or when the browser can't play them) with a play badge and their length; text files and PDFs are wide tiles with an icon, the name and the size. A name too long for the one line of a small tile loses its middle, not its end ("crash-r…t-1.log", `splitFileName`), and its title shows it whole. Images and videos are named by number within their kind ("Open image 2", "Play video 1", "Remove video 1"), other files by name ("Open notes.txt"). Every x keeps the 44×44 target that never reaches a tile's middle (`test/regression/thumbnail-middle-never-removes`). Once an x is pressed (it removes a draft file or stops an upload at once; on the ticket screen it asks first) the grid takes no taps or clicks for 500 ms (`useRemoveShield`, with the action sheets' `useClickShield`, §1.5): the next file slides into its place under the finger or the mouse, and a double tap or double-click removed two (PT-83), on phones, touch tablets as wide as a desktop and with a mouse alike. Keyboard presses go through at once. An image the browser can't show (HEIC outside Safari) shows an icon, never a broken image.
- **Opening** (`AttachmentViewerProvider`, `viewerTarget`): images open the full-screen viewer (pinch and double-tap zoom, pan, swipe between the images, swipe down to close). Videos play in a full-screen viewer with the native controls (`overlays/VideoViewer`), scaled to fit the screen however small they were recorded, `playsinline` so iOS doesn't jump to full screen, starting at once where the browser allows it; swipe down or Close ends them, and the swipe takes only clearly downward drags, so taps and scrubbing reach the controls. Text files open in a sheet that reads the file and shows it monospaced and wrapped, scrolling, up to 100,000 characters ending on a whole line, then "Open the whole file" (a new tab); it swipes down to close like any sheet. PDFs open in a new tab.
- Agents get images as image content, text files inline and download links for the rest (§4).

### 1.5 Phone gestures and motion (Apple-like)

On phones (`max-width: 767px`) the app behaves like a native iOS app:

- **Navigation stack:** Projects → Project → Ticket screens stack. Push slides the new screen in from the right edge while the old one moves 30% left and dims; pop reverses. Desktop keeps the SPEC's 28px fade.
- **Edge swipe back:** dragging from the left edge pops interactively with a parallax underlay, and completes or cancels by distance and velocity with a spring. Disabled in iOS Safari browser mode, where Safari owns that gesture (enabled when installed to the home screen).
- **Sheets:** drag the grabber or sheet down to dismiss (follows the finger, rubber-bands upward, velocity-aware). Content scrolls inside; dragging down from the top of the content dismisses.
- **Unsaved changes:** a sheet with input never vanishes by accident. While `Sheet` gets `dirty`, a swipe-down past the threshold springs back, and a scrim tap or Escape (desktop too) leaves it open; an action sheet asks "Discard changes?" with "Discard changes" (Danger) and "Keep editing", which returns focus to the field. The header's `SheetCancelButton` asks the same on phones (iOS convention) and closes at once on desktop, where Cancel is a deliberate click. Create, Save and Apply close without asking, and a sheet without changes closes at once. These sheets set it: New ticket (any field off its default, or a file, including one still uploading), New project (text in any field), Edit project (a name, description or repository that differs from the project it opened with; when the project loads after the sheet opens, the loaded values are the start, not a change), Paste report (text in the box) and Statuses (an open status editor with a changed name, type or color). Quick capture sets it too (a title, description or file, including one still uploading).
- **Row swipe actions:** swipe a ticket row right to move it to the next status; swipe left to reveal "Status" and "Delete". A full swipe triggers the first action. Haptic tick at the threshold where supported.
- **Action sheets ignore a double tap's second tap** (PT-80). A tap opens an action sheet, which slides up under the finger, or turns it into its next step, whose row takes the tapped row's place (the confirm of Delete comment, report, review or project). The second tap of a double tap, 0 to 200 ms later, pressed the row that had just arrived there: it deleted the comment, report, review or project without a real confirm, and on a row near the bottom bar a double tap on the swipe's Delete deleted the ticket and one on Status moved it to Done (WebKit, iPhone 13 at 375×812 and 320×568). So an action sheet's rows take no taps for 500 ms after they appear, when it opens and whenever what its card shows changes: a row's label, tone or weight, or the caption's text (`actionSheetContent`), so a next step that keeps the same rows under a new question is held too (`useTapShield` in `lib/clickShield.ts`, `CLICK_SHIELD_MS`, built on `useClickShield`, the shield of the desktop menu's `MenuConfirm`, §1.7). Cancel never moves and takes taps at once, and so do keyboard presses (a click with `detail` 0). A single mouse click also goes through at once (PT-82): on desktop, Discard changes is an action sheet, and a click a person aims at it after reading can't be a stray tap. `MenuConfirm` still holds a mouse's single click for 500 ms (PT-97 changed these words, not the code): its Delete takes the place of the item just clicked, right under the mouse, where a held click costs one more click and a stray one deletes. The shield tells by the `pointerdown` before the click, since not every browser's click names its pointer: it holds touch and pen taps, a double-click's later clicks (`detail` 2 or more: a double-click on the New ticket backdrop near the bottom of the screen would put its second click on Discard changes), and clicks with no pointer before them. VoiceOver's taps are such synthetic clicks (`detail` 1), so they are held for 500 ms too. A press that ends without a click (dragged off the row, or dragging the sheet down) is forgotten when it ends, so it can't pass for the pointer of a later click that has none (PT-97): one released off the card makes no click on it and one the browser cancels none at all, so they are forgotten at once, and one released on the card makes its click there, which forgets it (`followPresses` in `lib/pressPointer.ts`). Only a press of the primary button counts: a right-click makes no click, so it stayed until the next one and let VoiceOver's click through at once (PT-115). A press that opens a context menu is forgotten too: a Mac's ctrl+click is the primary button's, and Chromium sends no click for it (PT-130). A timer after the `pointerup` forgot them before, and a busy page could take a click with no pointer 5–8 ms after the release first (Chromium, PT-106). A finger's `pointerup` lands where it went down wherever it lifts, since that element keeps its pointer, and Chromium sends its click a task later. One mechanism in `overlays/ActionSheet` covers every sheet: Comment, Report, Review and Project options, Delete ticket and Status from a row swipe, Remove image or file, and Discard changes. Tests and E2E specs wait 500 ms before tapping a sheet's row, like a person reading it (`readActionSheet`); unit tests of a phone's double tap press the rows with a touch pointer (`tap` in `overlays/testing.ts`), since a mouse click would go through. Those unit tests, and those of a double-click on a menu or popover (`doubleClick` in `test/regression/`), stop the clock once the screen is up (`stillClock` in `test/regression/`): performance.now and the timers move only when the test advances them, so a busy machine can't stretch a double tap's gap past the shield (PT-167, PT-176). An iPad has the desktop layout with touch taps, so the Playwright project `tablet` (WebKit, iPad Mini at 768×1024) runs the tests tagged `@tablet`: a double tap on Undo (and a tap in the sidebar right after it, which acts), on Delete comment in a menu, on Delete status, on the New ticket backdrop where Discard changes comes (PT-106), and on a file note's Dismiss in a comment box with only text, where Comment rises under the finger (PT-115).
- **A sheet or action sheet that a click closes holds the screen's presses** (PT-148). A closing sheet takes no taps, so the second tap of a double tap on its Close or Cancel, on a primary action that closes it (Create, Save, Run), on the scrim, or on Discard changes landed on the screen it uncovered: the title or description, which opened the keyboard (WebKit, 375×812 and 320×568); on desktop a double-click's second click landed on the ticket screen. An action sheet's Cancel, or a row that closes it (a row swipe's Status, Comment, Report and Project options, Chat options), did the same: a double tap on Project options' Cancel pressed the bottom bar's button under it. So when a pointer's click on a sheet or action sheet (Discard changes counts as its sheet's) closes it within `CLICK_SHIELD_MS`, at once or after a short request like Run's, the whole page holds presses for `CLICK_SHIELD_MS` (`useCloseHold` in `overlays/`, `holdPresses(document.body)`), the screen's bars included, since the sheet covered them. As everywhere, a mouse's single click and key presses go through. Discard changes' Keep editing holds nothing (`holdOnClose={false}`): the sheet under it stays open as the person left it. A swipe-down and Escape hold nothing either: neither is a click a second tap could follow, so the next tap is aimed and acts at once. Each press or key forgets the click before it, so a tap in a field followed by a swipe-down doesn't count as a click that closed the sheet. Tested in `test/regression/sheet-close-double-tap`, `test/regression/action-sheet-close-double-tap`, `lib/holdPresses.test` (the bars) and `e2e/sheet-close-double-tap.spec.ts` (Close in WebKit at 375 and 320 and a Chromium double-click at 1280; an action sheet's Cancel at 375).
- **Delete status ignores a double tap's second tap** (PT-97). In the Statuses sheet, Delete status turns the status editor into its delete confirm, which is shorter, so Add status below moved up under the finger: a double tap's second tap opened an empty new-status editor in place of the confirm (WebKit, iPhone 13 at 375×812), and where the confirm's Delete lands there instead it would delete the status. So for 500 ms after Delete status is pressed with a pointer, the sheet holds presses the way it does after a file note's dismiss (`holdPresses` in `lib/`, §1.4, which forgets a press that ends without a click as an action sheet does): the second tap of a double tap and a double-click's second click are dropped, keyboard presses go through, and tests wait before pressing the confirm.
- **Pull to refresh** on Projects and Project lists.
- **Large title** on Projects collapses into the nav bar title while scrolling.
- **Nav bar layout:** the back button (at least 44×44) and the right buttons keep their size. The title takes the space left, ends in an ellipsis and stays centred while it fits. When the back label has no room for a few letters, only the chevron shows.
- **Tap the nav bar to scroll up:** a tap anywhere on the nav bar except its buttons (including the safe-area padding at its top) smooth-scrolls the screen's scroller to the top, and jumps there with reduced motion (`navigation/useTapToTop.ts`). It is the bigger target, and it works off iOS too.
- **Tap the status bar to scroll up** (iOS, PT-178): iOS's status-bar tap only scrolls the document, and each screen scrolls in a scroller of its own, so the tap did nothing. On iOS (`isIOS`, Safari and the home-screen app) the page now has 1px of scroll (`html[data-status-bar-tap]` in `design/base.css`: the body is 1px taller than the window and `#root` is sticky at the top, so nothing moves on screen; `overscroll-behavior-y: none` on the root keeps iOS from rubber-banding the whole app on a drag outside a screen's scroller, and the status-bar tap still scrolls the page with it) and the window rests at `scrollY` 1. The tap scrolls the window to 0; `navigation/statusBarTap.ts` takes that as the tap, the stack scrolls its top layer's scroller to the top like the nav-bar tap (`useStatusBarTap`, `scrollScreenToTop`) and the window goes back to 1. Only a scroll to 0 from rest counts: not while a finger is down (a drag can move the window), not after the window moved elsewhere first (the keyboard moving the page), and not while a sheet pins the body (`isBodyScrollLocked`, pinning takes the window to 0) and not within 300ms of a resize of the window or the visual viewport or of a finger lifting (`SETTLE_MS`: Safari moves the window to 0 itself as its toolbar resizes after a drag from the bottom bar, as the keyboard closes or on a rotation). A window that can't reach 1 isn't asked again from its own scroll event, only after the next resize or finger lift, so it can't loop. The layers keep their own scrollers, so their saved positions, Back and Forward, swipe back and the sticky bars are as before. Elsewhere the page keeps no scroll range, so a desktop shows no scrollbar.
- **Bottom bar and the keyboard:** on touch phones the bottom bar slides away and is inert while a text field has focus, because the keyboard covers it anyway (`navigation/useEditingText.ts`). It comes back when the field loses focus, but not during a press: a tap whose mousedown takes focus out of the field, such as Comment or Save, keeps it away until the release, so the click lands on what was tapped. When it comes back, the screen scrolls the field that was edited, with its form (the comment box and its Comment button), to 8px above the bar on the next frame, once, so a scroll right after closing the keyboard stays where the user left it (`navigation/keepFieldInSight.ts`). Only a field that fits between the nav bar and the bar moves: a longer one, such as a long description, stays where it is, because bringing its end up would push the part just edited off the top. A sent form, such as the comment box after Comment, is kept at least 8px above the bar while what it sent lands above it (the new comment), also when the keyboard closed before the tap and when the new comment pushed it below the screen: each time the content around it changes size (`ResizeObserver`), for a second after the send (the new comment shows at once, before the tracker answers) and until the user touches or scrolls the screen. These scrolls go to a position (`scrollTo` the current `scrollTop` plus the distance), not by a distance: WebKit runs a smooth scroll on its own thread, so while the page is busy rendering the new comment the scroll moves on from where the box was measured, and a second scroll by a distance landed the box 17–24px above the bar in about half the runs. What lands later, such as an agent's report, pushes the box down like any other content. The bar hides with `translate`, which its entrance animation on `transform` can't override, so a field focused while the bar slides in still sends it away.
- Press feedback (scale .97), spring selections, `prefers-reduced-motion` honored everywhere.

### 1.6 Other additions

- Live updates: the server pushes change events over SSE; open screens refresh when an agent changes something. The web app reopens the stream when the browser gives up on it or when it stays silent for 35 s (two missed pings: a proxy can keep a dead stream open after the API server crashes), waiting 1 s, then doubling up to 15 s. A stream waiting for its next try opens at once when the tracker answers again (any answer from it, its recheck of `/api/health` included, even while slow reads keep the offline banner up: `connectLiveUpdates` follows the app's `tracker` flag, PT-126), and its wait starts over at 1 s, so the screens' data refreshes with the banner going: it waited for that try, up to 15 s (PT-118; behind a proxy answering a bare 502 for a stopped API, back after 20 s or 32 s: data back 1.3–1.6 s after the API answered, was 10.4–13.4 s, in Chromium and WebKit). A stream that is open or on its way, one the browser retries itself and one paused while hidden are left alone, so no second stream opens. After any reopen, including the first open after a failed connect, all cached data except session and meta refreshes; keys with pending edits and deleted keys are skipped. The ping interval and the silence window are `HEARTBEAT_MS` and `LIVE_STALE_MS` in `packages/shared` (`domain/liveUpdates.ts`), used by the server and the web app. A page hidden for 30 s closes its stream, so a phone's radio doesn't wake for every ping, and reopens it as soon as it is visible again, with the same refresh (`api/live/pauseWhileHidden.ts`); a quicker switch to another app keeps the stream. The time hidden decides, not whether the timer ran, because a phone runs no timers while it suspends a hidden page: such a page also gets a new stream on return, since the one it kept may have died. While a stream is closed or reconnecting, TanStack Query's refetch on focus and on reconnect (the browser online again) are off (`api/live/refreshPending.ts`), so a return after 30 s, or with the network back (a phone that lost it while locked), reads each open query once, after the new stream opens, and no change falls between that read and the stream; with the stream open, focus and reconnect read stale queries as before. After three failed tries (`LIVE_WAIT_ATTEMPTS`: a proxy can refuse the stream while the API answers), they read again without waiting, and a stream that opens later still refreshes everything. The tries the browser makes itself on a dropped stream count too (PT-82): each `error` it reports while it reconnects is one, the drop's own included, so a stream it keeps failing to reopen no longer holds focus reads back until the 35 s silence check. So focus reads come back about 6–7 s after a drop the browser keeps failing to reopen (the drop and its next two tries, 3 s apart), and about 4–4.5 s after one whose first try gets a 502 (the drop, that try and the app's reopening 1 s later), in Chromium and WebKit. Those tries count only toward the three: the wait before the app's own reopening grows with its own reopenings, so after a silence check or a 502 it still tries again after 1 s (PT-97: counted in, an outage longer than the silence check left 15 s before the app's first try, and a 502 2 s). When the browser gives up on the stream, the app reads `GET /api/session` again, because EventSource hides the status and a 401 looks like a proxy's 502: when the session has ended, the sign-in screen shows (which ends the retries); an unreachable server changes nothing.

Only the ticket screen reads this way: the board and lists read as usual, so while reads are slower than the timeout a list can show a title from before a write until its next refresh.
- **The offline banner** follows the API's answers (`app/reachability`): a request that gets no answer makes the tracker unreachable, and any answer from it, an error too, reachable. A bare 5xx (no error body: `http_error` with 500, 502, 503 or 504) comes from a proxy in front of a stopped API, but also from the API itself or from a proxy whose connection to it broke during one request, so it first checks the tracker with a fresh read of `GET /api/health` (`checkHealth` in `@tracker/client`, which the service worker leaves to the network), and only a check that gets no answer or a bare 5xx too makes it unreachable; one upload's 500 put "Can't reach the tracker" over the whole app (PT-101). The draft retries' own watcher (`features/ticket/drafts`) checks the same way, and the two share each check (`trackerCheckOf` in `app/trackerCheck`): every bare 5xx sent two at once (PT-109). One check runs at a time, and a bare 5xx starts none while the tracker is already unreachable. A check with no answer after 3 s (`CHECK_TIMEOUT_MS`, what the service worker gives a read before it answers from its saved copy) is stopped and counts as unreachable: one left waiting, as on a proxy that holds the connection to a stuck API, kept the tracker reachable and every later bare 5xx unchecked (PT-109). Its request ends then too, because the service worker doesn't take `/api/health`: the worker's own fetch for a stopped check stayed open until the connection closed, about 80 s (PT-113). While the tracker is unreachable and the page isn't hidden, the banner's watcher checks it again (`app/recheck`, sharing the check): 1 s after it was lost, then 2 s and then 3 s after each check ends (`RECHECK_MS` backing off to `RECHECK_MAX_MS`), and at once when the page is seen again. An answer clears the banner and refreshes the project list, so the banner goes within 3 s of the API answering again; it waited for the live stream's next try, up to 15 s away, and the reads after it, up to about 26 s (PT-113). Saved answers end only with an answer to a read or a write, not a check's: behind a connection where reads take longer than the service worker's 3 s, `/api/health`, which it leaves to the network, still answers at once, and each recheck's answer took the banner down and read the project list again, whose saved answer brought it back, every 4 s, with the list read 6 times in 30 s (PT-126). So the app keeps two flags (`Reachability` in `app/reachability`, their rules in `app/trackerState`): the banner's, up while the tracker gives no answer or reads come from saved copies, and the tracker's, up only while it gives no answer, which a check's answer takes down. Capture sync and the live stream's reopening follow the tracker's: following the banner's, a capture saved during an outage stayed queued after the tracker was back for as long as reads stayed slow, and the stream waited for its own next try, up to 15 s (PT-126 review). The first saved read after a read or a write got an answer puts the tracker's flag up too, until a check answers; later ones change nothing. Each check that takes the tracker's flag down reads the project list, and that read's answer clears the banner when the tracker is back and reads are quick (about 1 s after the API answered again behind a proxy answering a bare 502, as before). While reads stay slow the banner stays up, and the list is read again only when the tracker's flag went up in between (a check or a request got no answer), not on every check, until a focus read, a live update or a screen opened reads again. A banner watcher started while the tracker is already unreachable rechecks too. The screens' other data refreshes when the live stream reopens, which it then does at once (PT-118, Live updates above). The draft retries' watcher has no schedule of its own: one per watcher would send twice the checks. The browser's `offline` (or `navigator.onLine` false when the watcher starts) is only a hint (`app/offlineHint`, PT-179): it makes the tracker unreachable, so the banner comes at once, until an answer says otherwise; the rechecks then ask, and `online` asks at once. Before, the banner followed `navigator.onLine` too, and with it stuck at false in WebKit it said "Offline — showing saved data" for 20 minutes while the tracker answered. Nothing else reads `navigator.onLine`: `isNetworkError` counts only a request with no answer (a `TypeError`) and a bare 5xx, and capture sync and the draft retries try anyway, a request with no answer keeping what waits. Once the banner says "Offline — showing saved data" it says so until it goes: the tracker's first answer when it is back is noted a moment before its request reports success, and for that moment, about 1 ms with the service worker, the banner said "Can't reach the tracker" (PT-109).
- **Attachment files** are read cache-first (`pwa/attachmentFileRoute.ts`): whole images, text files and PDFs stay for 30 days, 100 at most. A ranged read, which is how browsers play video, matches no route, so it goes to the network without the service worker in the way (iOS doesn't play video without real ranges), and videos never go in the cache (`attachmentCachePlugin`), where one could take 100 MB.
- App updates never lose typed text. While the app stays open it looks for a new build when the page becomes visible and every 30 minutes, also while the browser says it is offline: WebKit has kept `navigator.onLine` false for 20 minutes after a network change while every request was answered, and no new build came (PT-179); a failed check is harmless. A new service worker takes over at once, but the page reloads into the new build only when no text field is focused, no dialog is open, there are no drafts (`hasDrafts()`) and no write is in flight, whether the page is visible or hidden. It checks again every second and on `visibilitychange` (`apps/web/src/pwa`). Writes in flight come from the QueryClient's mutation cache. A lazy chunk that fails to load (`vite:preloadError`: a page still on the old build asks for a file the new build replaced) reloads the page by the same rule (`pwa/reloadOnPreloadError.ts`); until then the failed import fails as usual. While either reload is on its way, no push goes (`lib/pageReload.ts`, PT-108, PT-119): between asking for a reload and unloading the page still runs, and a push meanwhile added an entry that the reload filled with the screen on show, so the history held Projects twice and the browser's Back stayed on it. That was first the push that waited for the failed chunk, then a tap while the new page was still coming on a slow network, as the first push's row had let go. Now the waiting push's row stays pressed until the new page replaces it, and so does the row of a tap meanwhile. The reload counts as on its way for 5 s at most (`RELOAD_ON_ITS_WAY_MS`), or until a Back or Forward, because it may never come: Chromium cancels it for a Back or Forward that comes before the new page (WebKit finishes it), and the browser's Stop cancels it with no event to tell the page. A first version kept a mark that the page was reloading for good, and then no push or replace went for the life of the page; now the row lets go when that time is up, and the next tap opens its screen. A replace the app makes on its own goes at once, since it adds no entry: held, it was dropped if the reload never came, so a ticket that answered 404 meanwhile never fell back to its project and its screen stayed on "Loading MOB-8" (PT-153). The time is read from `performance.now()`, which a wall clock set back can't stretch. A reload that waits for a safe moment (a text field in focus) lets the push and its screen's error show first, and then reloads that screen. It reloads at most once a minute: the reload's time is kept in `sessionStorage` (`tracker.chunkReloadAt`), and a chunk that fails again within a minute of it only logs a warning and the page stays, because the file is then missing for another reason (a proxy, a broken deploy) and reloading again would loop. Without session storage it doesn't reload, and its warning says so instead of claiming a reload was tried.
- **Draft contract** (`apps/web/src/lib/drafts.ts`): a feature that holds unsent text a reload would lose marks it with `useDraftMark(id, active)` (`lib/useDraftMark.ts`), `active` while the text differs from what is saved; the mark goes when `active` turns false (sent, saved or emptied) and when the component unmounts. Underneath are `markDraft(id)` and `clearDraft(id)`. Use one id per draft, such as `comment:MOB-3`. Marks are counted per id, so each `markDraft` needs its own `clearDraft`, and two mounted components that share an id keep the draft until both let go. Text in the ticket drafts store (next point) counts as a draft without a mark, until it is saved or dropped. While `hasDrafts()`, reloading or closing the page asks first (`beforeunload`; iOS doesn't show it). A draft that is never cleared keeps the page on the old build until the next launch. An open sheet needs no mark to hold an update, because the reload already waits while a dialog is open; quick capture marks `capture` only while it holds files (uploaded or on their way), which a reload loses, so that closing the page asks. The kept fields of New ticket and quick capture (below) are not a draft: `hasDrafts()` leaves them out, because the sheets open with them again after a reload, unless storage refused them (next point).
- **Unsaved ticket text survives leaving the ticket and reloading.** Title, description, assignee, comment edits and the comment box keep typed text in a small store (`apps/web/src/lib/storedDrafts.ts`, in `localStorage`, records below) under their draft ids (`title:MOB-3`, `description:MOB-3`, `assignee:MOB-3`, `comment-edit:<comment id>`, `comment:MOB-3`), with the ticket key, the field, the server value the text was typed over and, for a comment edit, whether Save was pressed for it. An entry stays until the tracker has its text, also while a save is on its way, so leaving the ticket or reloading during a request loses nothing. The ticket opens again with that text. An entry goes once the server has its text, when the comment box is sent or emptied, when an edit is cancelled or emptied (a comment needs text, so an empty edit can't be saved), on **Use theirs**, and when its comment or ticket is deleted: by the user, or elsewhere, which the app-wide sync below finds out (it reads every ticket that isn't open and has kept text) and so does the ticket screen when it gets a 404 for its ticket. The comment box's text is never sent for the user, and neither is an edit nobody pressed Save for: it opens again in its editor as it was left, without a note and without taking focus, and only Save sends it, after the check below. A comment whose send fails comes back into the box with its files, before anything typed there meanwhile, in this tab or another (`activity/useComposer.ts`). When storage refuses a write (full, or turned off), the new record stays in the page's memory and the record it outdates goes from storage (`lib/tabRecords.ts`; the sheet drafts below do the same with `lib/draftStorage.ts`), so a reload never brings back older text than the page had. Records in memory go to storage as soon as it has room again (at the next write it takes, or when a record leaves it, in this tab or another), so a reload keeps them, and storage refusing again is told again (PT-111 review). A toast says "Unsaved text can't be kept on this device, so it's lost if this page closes." each time storage starts refusing (decided once the records the new one outdates have gone, as their room may take it; with less room than one record it showed on most keystrokes, PT-136), and closing the page asks first. iOS doesn't ask, so that toast is the warning there: it stays 4 s and no toast replaces it, such as the "Can't reach the tracker" of a save that fails offline 0.4 s after typing stops, which waits until it has gone (`important` in `components/Toast`; the latest toast shown meanwhile waits). Two tabs share the store: a title, description or assignee field, and the comment box, show the text another tab keeps for them as soon as that tab types it (a `storage` event, or when the tab is shown again), a field unsaved like text kept from an earlier visit, so both tabs edit one text and neither types over text it hasn't shown. Once one tab saves a field, the other follows the tracker (failed saves below); once one tab sends or empties the comment box, the other's empties too. Comment edits show each tab's own text; the store keeps the one typed last.
  - Records (PT-111, `lib/draftRecord.ts`, `lib/tabRecords.ts`): each tab writes its kept text as records under keys of its own (`tracker.drafts:<tab>:<n>`), one per draft, with the text, its base and when the text was typed (`at`).
    - A record is never changed. A tab that types, rebases or ends a draft puts a new record, or none, and removes the records of that draft it has read; a record another tab put meanwhile stays.
    - A draft's text and base are its latest record's: the one typed last.
    - So a tab working from a copy of storage that hadn't heard of newer text can neither write older text over it nor drop it. Before, every tab wrote all drafts back as one map (`tracker.drafts`), and such a copy did both, which needed a patch per race (PT-90, PT-105).
    - That map, from versions before this one, is read as one more tab's records: text kept before the update, and text typed in a tab still on the older version until it reloads. Its entries go once newer text outdates them.
  - A comment on its way is kept too, under `comment-send:<send id>`, until it lands, so closing the page asks first (`activity/sentComments.ts`, PT-105). A page that goes anyway leaves it kept, as it may have reached the tracker without its answer reaching the page: the app-wide sync, once no tab has it on its way, reads the ticket and puts it back in the box unless the ticket has more comments with its text than when it was sent. Its files are not kept.
    - An open tab runs that sync 1 s after the page's marks stop counting: at once for a page that went (`pagehide`, not one the browser keeps to show again) or was killed, a minute on for one the browser froze (PT-135, other tabs' saves below). Else the next start does. Before (PT-105), the page put it back as it went, so one that had landed showed twice (PT-111).
    - A comment that comes back (its send failed, or it never landed) is a record of its own (`comment-back:<send id>`), shown in the box before what was typed there. Typing in a box that shows it takes it into the box's text. Written straight into the box's text, it could replace typing another tab did a moment before, and that tab, typing on, could replace it (PT-111).
  - A comment past 20,000 characters (a failed one joined to text typed meanwhile) isn't sent: a toast says "A comment can be up to 20,000 characters. This one has 21,001: shorten it to send it."
- **Unsent New ticket text survives a reload.** While the New ticket sheet is open with changes, its fields (title, description, status, priority, assignee, due date) and the files already uploaded are kept in the sheet drafts store (`apps/web/src/lib/sheetDrafts.ts`, `localStorage` `tracker.sheetDrafts`, in memory when storage fails, through `lib/draftStorage.ts`) under `new-ticket:<project key>`. Opening New ticket for that project again, after a reload, a crash or iOS stopping the app, starts from them; a kept status that was deleted meanwhile gives way to the sheet's default and counts as no change (a sheet that looks untouched closes without asking, and its entry goes); kept files 23 hours old are left out, because the server deletes uploads nothing uses after a day (`keptAttachments`). Files still uploading can't come back, so while they go, closing or reloading the page asks first (the draft `new-ticket-files:<project key>`). The entry goes when the ticket is created, when the sheet closes any other way (Cancel, Discard changes) and when the fields are back to blank. It is `localStorage`, not `sessionStorage`, because a home-screen app that iOS stopped starts a new session.
- **Unsent quick capture text survives a reload** the same way, under `capture` (`features/capture/keptCapture.ts`): the title and description, with the priority and the project picked in the sheet (none while the default applies; a kept project that is gone gives way to the default), and once Create is pressed the capture's client id and the text that Create sent (§1.9).   - Saves on their way (`fields/fieldSaves.ts`): on a slow connection several saves of a field can be on their way, and the tracker ends with the latest one's text. They are recorded per draft id, not in the field on screen, because the tracker may already have one of them without having answered it, which a check would take for someone else's change: the field opened again after leaving the ticket and the app-wide sync see them too.

Other text is sent again, also text an older save still on its way carries (typing more, then deleting it). The kept text goes only when the latest save sent lands; an older one landing records what the tracker has for now, which a later check compares with.
  - Retries: after a failure, typing no longer autosaves; a checked retry saves the text: Retry, leaving the field, opening the ticket again, and app-wide (`features/ticket/drafts/useTicketDrafts`, called once in `TrackerApp`) on start, on `online`, when a request gets an answer again after the tracker couldn't be reached, and when a bare 5xx gets a check the tracker answers (PT-109: it may have been a kept draft's own save, through a proxy whose connection broke, which otherwise waited for the next start, `online` or change in its project), also for tickets that aren't open; and when the tracker reports a change in a project that has tickets with kept text that aren't open (a live update refreshing one of its queries), which may be one of them deleted, reading only that project's tickets: an unsent comment can sit for days.

A field opened while the latest save of its kept text is on its way shows that text without a note and checks nothing: once that save lands it follows the tracker, and if it fails the field says the text isn't saved yet and is retried as usual.
  - The app-wide sync leaves the drafts of an open ticket to its screen, also while it loads, and a draft with a save on its way, in this tab or another, to that save (its own saves count the same way), so text kept from an earlier visit is sent once at start, and leaving a ticket while its saves are on their way brings no toast.
  - Other tabs' saves: other tabs know of a tab's saves on their way from marks in `localStorage` (`tracker.draftSaves:<tab>:<draft id>`, `fields/saveMarks.ts`): one key per tab and draft, which only that tab writes. When every tab wrote all marks back as one value, a tab that hadn't yet heard of another tab removing its mark put it back, and the other tabs waited a minute for a save that had landed. A mark stops counting a minute after its tab last sent or settled a save of the draft, so a tab that closed while sending doesn't hold the draft up; a save still hanging in an open tab after a minute stops counting too. A page that goes for good (`pagehide`, not one kept to show again) removes its marks at once, and each tab has a timer for the next of another tab's marks to run out (PT-105), so a field on screen, or a refused field waiting on it, moves on then; the app-wide sync notices on its next run and sends the draft as its own.
    - A page's marks also stop counting as soon as it has gone, however it went (PT-135): each page holds a Web Lock named after it from its start (`fields/pageLocks.ts`), which the browser lets go with the page; a tab that reads another page's marks asks for that page's lock, and removes those marks once it gets it. WebKit can lose a closing page's last writes to storage, its removal of its marks among them, and the other tab then waited for them to run out (1 close in 20 under load: the comment came back after 54 s). A page the browser froze keeps its lock, and without Web Locks (plain http, older browsers) nothing says a page went: the minute still applies there.

Other changes to marks run it only for a comment left on its way: they are mostly saves settling, which their tab follows up. A save that hangs in a tab that stays open keeps that tab's sync off its draft until it ends (requests have no time limit); opening its ticket retries it.

Once that save lands, the field keeps showing its text, without a note, until this tab's copy of the ticket changes (its own read lands, which takes a while on a slow connection). Typing there goes on top of that text instead of saving the older one over it, and the field's saves compare with that text rather than the older copy, so an edit back to the older text is saved too (`landed` in `fields/fieldDraft.ts`).
  - Comment edits: a comment edit's Save sends it at once, unless the edit was kept from an earlier visit or a save of it failed: then Save first checks the comment like a retry (next), and says "Can't reach the tracker" when it can't, leaving the edit failed (`activity/commentEdit.ts`). Typing after Save starts a new edit, which waits for Save again.

One the tracker refuses because another tab's edit landed first says at once that the comment changed elsewhere (below), with no toast, and keeps its text without Save pressed for it, so it isn't sent for the user again, also after a reload; Save then replaces theirs (PT-105). A save refused because an older save of the edit landed meanwhile goes again, typed over that save's text. An editor gone since (the ticket left and opened again) leaves the store alone: its refused text kept the gone editor's text over text typed since in the editor opened again, which a reload lost (PT-105).
  - The check: the retry first reads the ticket fresh (saved answers above), so the answer comes from the tracker, or the check fails and nothing is saved. If the ticket still has the value the text was typed over, the text is saved; if it already has the text, the draft is done. If someone else (an agent) changed it meanwhile, nothing is saved either way: the field keeps the text and says "Title changed elsewhere while yours wasn't saved." with **Save mine** and **Use theirs**, and a comment edit says "The comment changed elsewhere while your edit wasn't saved." (Save replaces it, Cancel keeps theirs). When that happens to a ticket that isn't open, a toast says "Your edit to MOB-3 isn't saved: it changed elsewhere."
  - Older saves: every field save says what its text was typed over (`expected`, §3): the text of the field's latest save still on its way; else text another tab saved, or was still sending, when the field was typed over (`landed`); else the base of its kept text. A save after a check names what the check found.
    - The tracker refuses a save that lands after newer text with 409 `stale` (no toast), so a save of tab A that hangs while tab B types on top can't overwrite B's text when it lands: B's save, typed over A's text, waits for it.

Retry meanwhile says "Another tab is still saving the assignee. Yours is tried again once that's done, within a minute." (`fields/useFieldRetry.ts`).
    - Until that check, the kept text going doesn't clear the note.
    - When its kept text has gone (another tab saved it, or typed over it and saved or let go of the newer text), the refused field reads the ticket and follows the tracker, instead of putting its older text back over newer text (PT-105). No tab removes text it hasn't read (records above), so the text only goes that way.
    - Otherwise the check finds its text saved, or someone else's change (the note with **Save mine** and **Use theirs**). It also counts the text the field typed over, because the base other tabs keep in step can lag a moment behind a save that just landed. The app-wide sync sends the base it just checked and doesn't count a `stale` refusal as refused: its next run checks the draft again.

A draft the tracker refuses otherwise (another 4xx) stays kept and the others go on; later runs in that page don't send the refused text again, only new text, and on its ticket's screen the field says it isn't saved and retries it there.

### 1.9 Quick capture

- **Entry points:** on phones a bottom bar on Projects with a primary "New ticket" (instead of a floating +); on desktop "New ticket" in the Projects header, its primary button (§1.7), and the shortcut **C** anywhere no text field, sheet or menu has the keyboard; the PWA manifest shortcut "New ticket" opens `/?capture`, which opens the sheet and then drops the parameter. C does nothing while a modal (`aria-modal`), a dropdown (`listbox`), a `menu` or a popover menu's invisible "Close menu" layer is in the page: popover menus keep focus on their trigger, and their layer would take the next click. A closing dropdown, calendar or ••• menu, inert while it takes the second click of a double-click, doesn't count.
- **Sheet** (`{ type: 'capture' }`, `features/capture`): title focused on open (phones too), optional description and files, Project (the last one used, `tracker.capture.project`, else the most recently active) and Priority (Medium). No status is sent, so the server uses the project's first status. Create shows "MOB-7 created" and stays on the current screen. Typed text survives a reload (§1.6); files make it the draft `capture`. A title, description or file makes the sheet `dirty` (§1.5), so a swipe-down, scrim tap, Escape, click outside or a phone's Cancel asks "Discard changes?"; Create closes without asking.
- **Offline:** when the tracker can't be reached, or hasn't answered within 8 s, a text-only capture waits in `tracker.capture.queue` (localStorage) with a client id, and Projects shows "N waiting to sync". A capture with files stays in the sheet instead ("Files need a connection…"), because they only live on the server.
- **Sync:** on start, when `app/reachability` turns reachable, on `online` and when the page becomes visible; one run at a time (across tabs too where there are Web Locks), oldest first, one request at a time, then "N tickets added". Created ids are skipped. Network, 401 and 5xx failures stop the run and keep the rest; a capture the create refuses for good (another 4xx, such as its project being deleted) is dropped with the one-line toast "Couldn't add “…”", the title clipped to 24 characters so it fits at 375px. Sends go through the mutation cache (writes in flight, reachability) and refetch nothing on failure.
- **One ticket per capture:** every create for a capture, the sheet's and each sync's, carries the capture's client id (`clientId`, §3), and the tracker answers a repeat with the ticket the first one made. So a capture is sent again without looking anything up, and still makes one ticket: after a lost answer, when its tab closed mid-request, or when two tabs send it at once. The sheet makes the id at a capture's first Create and keeps it with the kept text (`capture` in `tracker.sheetDrafts`, written before the request goes out) until the capture is created, waits in the queue or the sheet closes. So Create again after a lost answer (files still attached, added or removed), a reload, or a crash or iOS stopping the app mid-create shows the first request's ticket ("MOB-7 created"). Files added in between end up on it too: the tracker attaches a repeat's files the ticket lacks, after its others (§3, `test/regression/client-id-repeat-adds-files`). One that was gone by then (its upload expired after 24 h, or someone removed it from the ticket) is left out, and the toast says so: "MOB-7 created, but 1 file couldn't be attached" (PT-97, `test/regression/capture-repeat-file-left-out`). Edits made in between keep the id, and what the person changed wins (`features/capture/sendCapture.ts`): the first Create keeps the text it sent (`sent`, trimmed as sent) with the id, and a queued capture carries it too (one without it counts as unchanged). The answer to a repeat is the ticket as it is now, so the sheet saves to it only the title, description or priority the person changed since that first Create and the ticket doesn't have yet, with an ordinary update (`PATCH /tickets/:key`, like an edit on the ticket screen) before "MOB-7 created"; a sync does the same for a queued capture. A field the person left alone is never sent, so an edit someone else made to the ticket in between stays, also when the capture is unchanged (title and description edits are not in the activity, so it would be gone for good; `test/regression/capture-keeps-other-edit`); a field both changed gets the person's text. If the tracker refuses that update, the sheet keeps the text and says "MOB-7 was created with your earlier text, and this text couldn't be saved to it. Try again."; a sync counts the capture added, since its ticket exists, and says "MOB-7 created with your earlier text" instead of "Couldn't add …". If the update can't be reached, the capture waits or stays as for any create. A capture emptied of its title, description and files lets its id go, so what is typed next is a new capture; so does one opened after the sheet closed. Changing the project between two Creates still makes a second ticket, in the new project, since client ids are per project.
- **Fewer requests across tabs:** while a request for a capture is out (the sheet's, which keeps going after the 8 s save, or a sync's), its tab holds the Web Lock `tracker-capture-send:<id>`. A sync skips a capture it can't lock, reads it again once it holds the lock, and lets go only after the result is recorded. Web Locks need a secure context, so a phone on a plain http address keeps a lease time in `localStorage` `tracker.capture.sending.<id>` instead, renewed every 20 s and void a minute after the last renewal. That lease is not atomic: Chromium shows a tab another tab's writes a moment late, so two tabs coming back online together can both send a capture. The locks only spare requests (and a second "1 ticket added"); the client id is what keeps it one ticket.

### 1.11 Run in Claude Code

The prompt sheet keeps **Copy prompt**. A ticket can also go to a helper on the person's own computer (`tracker watch`, PT-140), which starts Claude Code there. The server keeps the queue (PT-139: `services/runs.ts`, `runQueue.ts`, `runners.ts`, `http/routes/runs.ts`).

- **Helpers** (`runners`). A helper picks a UUID once and checks in with `PUT /runners/:id { name, projectKeys }` when it starts and about every 20 s. That creates or updates its row and keeps it online: `online` while its last check-in or take is under 60 s old (`RUNNER_ONLINE_MS`). The same id after a restart finds the runs queued for it. Projects are kept by id, so a renamed key keeps the helper, and a deleted project drops out of its list. `DELETE /runners/:id` is for a computer the person no longer uses: its queued and running runs fail ("That computer was removed."). A helper that stops is only offline.
- **Runs.** `POST /tickets/:key/runs { runnerId, prompt, role? }` queues one on a helper that serves the ticket's project (409 when it doesn't). The prompt is the sheet's text, edits included. The helper takes its oldest queued run with `POST /runners/:id/next` (now `running`; the answer holds the prompt) and ends it with `POST /runs/:id/finish { status: done | failed | cancelled, error? }`. The person cancels with `POST /runs/:id/cancel`. Ending a run again the same way answers the run, since a helper retries a report the server may already have and reports "cancelled" after the person cancelled; another way answers 409. One queued or running run per ticket, whoever started it, since two Claudes on one ticket would undo each other's work. A partial unique index holds it, so two taps that race can't both start one: the second gets 409 "Claude is already working on MOB-3.", which names only the ticket. A run fails once its helper has been silent for 30 minutes (`HELPER_SILENCE_MS`), counted from the later of when the run was queued and the helper's last check-in: a queued one with "Your computer didn't take the run.", a running one with "Your computer stopped answering." So a run waits while its helper is busy with another, a phone stops waiting on a computer that is off, and a computer that died mid-run doesn't hold its ticket. This happens at the next run request; the web app reads a run it shows as waiting or working again (PT-141). A helper's late report on a run that already ended gets 409. A helper runs one run of each kind at a time (§1.12) and asks for the next of a kind only when it has none of it, so asking ends any run of that kind it still has as failed ("The helper restarted before it finished."): one that crashed and came back under the same id would otherwise keep it running.
- **Review runs** (PT-193, migration `0013_run_role`). A run has a `role`, `work` or `review` (`RUN_ROLES`; ask runs are `work`), set when it is queued (`queuedRunRow`): from the request, default `work`, so a server-side chain can queue a review itself. Runs queued before roles have a null column and read as `work` (`toRun`). The helper gets it with the job (`run.role`). The prompt sheet sends the role of the prompt it shows, so a ticket in Need review goes to a reviewer in two taps: **Send to Claude**, then **Run in Claude Code**. The sheet's title is then "Review with Claude" and its help speaks of a review (`sheetTitle`, `promptHelp`, `promptRole` in `features/claude/sendPrompt.ts`; the ticket's status decides until the prompt loads, so the title doesn't change under the person). A review run skips the report hand-back below, since a reviewer's words are a review, not a report of the work. When it ends done, the helper reads the ticket: still in an `in_review` status means Claude never called `review_ticket`, so the run ends failed with "Claude didn't record a review." (`REVIEW_NOT_RECORDED`, `watch/report/reviewCheck.ts`); a run that failed keeps its own error, and a ticket the helper can't read leaves it done, with a line in the window. A recorded review moves the ticket to Reviewed, or back to To do with the review card.
- **One user's runs are theirs alone.** Each run and helper keeps the user of the request that made it (`auth/scope.ts`: the session's or the token's user; null on a tracker without an owner, where everyone on this computer is the one person). Projects belong to users too (§3.1), so a run starts, and a helper serves a project, only where the person can reach the project (`requireProject` / `requireTicket` with the scope, 404 otherwise); a helper's project list leaves out projects its user can't reach. Every read and write of runs and helpers filters by it, except the expiry sweep, owner-set's takeover and the id check before a helper is created. Another user's run or helper answers 404, never 403, so nobody learns it exists; a helper id another user already took does too. Only a person starts a run: a request that acts as an agent (every API token does) gets 403 before its body is read, so agents can't start more agents. Only a helper (an API token, or anyone on a tracker without an owner) checks in, takes and ends runs; a browser session gets 403. The server sends a helper a run id, its ticket key and the prompt as text, never a command, folder or flag. When owner-set creates the owner, the runs and helpers made before it become the owner's, since everyone on this computer was that one person (`test/regression/ownerless-runs-after-owner-set`). Tests make a second user straight in the database, with a session and a token (`test/helpers/runs.ts` `addUser`; `test/integration/runIsolation`, `runEvents`, `userIsolation`).
- **Run events** go on `GET /events` as a named `event: run` (`{ type: 'run', runId, runnerId, projectId, ticketId, status }`), only to the streams of the run's own user (`events/runNotice.ts`). The web app's change handling reads unnamed events only. Starting, taking, ending and expiring a run send one, and so does removing its helper.
- **In the app** (PT-141: `api/hooks/runs.ts`, `api/workingRun.ts`, `features/claude/runs.ts`, `PromptFooter.tsx`, `useRunOffer.ts`, `features/ticket/main/LatestRun.tsx`, `features/connect/WatchSection.tsx`). The ticket's prompt sheet offers **Run in Claude Code** (primary, Play icon) beside **Copy prompt** (then secondary) when one of the person's helpers that serves the project is online: side by side with Run on the right on desktop, stacked full width with Run on top on phones, where it also comes first in the DOM for focus. The footer's state is worked out once (`runFooter`: Copy alone until the helpers are known, Run, the working line, or setup). With more than one helper, a **Run on** row above the buttons picks one, starting with the last one used on this device (`tracker.lastHelper`). The help text then speaks of both buttons. Run sends the box's text, edits included, closes the sheet and toasts "Sent to Claude on Dara's MacBook"; a refusal (409) shows in the sheet like its other errors. A closing sheet takes no taps, so the whole page holds a pointer's presses for `CLICK_SHIELD_MS` from then, as after any sheet that a click closes (§1.5, PT-148): the second tap of a double tap on Run had focused the comment box or the description, or reopened the sheet from the bottom bar (`test/regression/run-double-tap`). The Move to In progress switch shows as before and applies to Copy and Share only; Run ignores it, since Claude claims the ticket itself. During a queued or running run, "Claude is working on Dara's MacBook…" takes Run's place. With no helper online the footer stays Copy alone, and a Muted line under the box, "Run Claude Code from here" with a **set up your computer** text button, opens Connect Claude Code. The project's "Send open tickets" sheet keeps Copy only. The ticket screen shows the latest run under the title, above the latest review, in an activity card: "Claude is working on …" with **Cancel** while queued or running (presses are held a moment after it, since the card then leaves, and focus goes to the Status like after Move to Done, not to a text field that would open a phone's keyboard), "Claude stopped: <error>" with **Try again** (the prompt sheet) when it failed less than a day ago (`STOPPED_SHOWN_MS`, the simplest rule that lets an old failure go), and nothing when done or cancelled. A ticket's runs are read again every 30 s while the latest waits or works, since the tracker ends a silent run only when asked; helpers every 20 s while a list shows them, since check-ins send no event, and on every reconnect. A named `run` event (`parseRunEvent`) refreshes the runs of its ticket, found by id in the cache like a change, and the helpers (`api/live/refreshForRun.ts`). Connect Claude Code has a "Run Claude Code from your phone" step with the `watch` command for the project behind the sheet (the CLI's absolute path for a tracker on this computer; for one elsewhere a `/absolute/path/to/project-tracker` placeholder, since the helper runs in the project's folder rather than the checkout), a note on its limits (the Mac must be on, awake and logged in, and FileVault waits for the password after a restart; otherwise a run waits `HELPER_SILENCE_MS` and stops with `RUN_NOT_TAKEN`), and one line per helper of this user: name, projects, "Online" or "Last seen 2h ago".
- **Live steps** (PT-161; shared `logic/runSteps/`, server `services/runSteps.ts`, `http/routes/runSteps.ts`, helper `watch/stream/`, `watch/steps/`). The helper runs Claude with `--output-format stream-json --verbose`, one JSON event a line, and turns each into steps while Claude works (`createStepReader` in shared, one reader a run): a step is `{ kind: tool | text | agent | denied, label, subAgent, toolId }`. A tool call becomes one line saying what Claude asks to do, "Read apps/web/src/x.ts", "Run npm run verify", "Edit x.ts", "Search for 'foo' in apps/server", "Use tracker: claim_ticket PT-12", "Ask: Which file name should I use?" (AskUserQuestion); Claude's words a `text` step; the Agent tool (Task in older versions) "Start sub agent: <description>". Asked, not done (PT-161 review): a call can be refused, and "Ran echo hello > out.txt" read as done for a refused command. An Ask or Plan question refuses a command that changes anything (plan mode still runs one that only reads, such as `ls -la`), and a background sub agent's Bash and Read are refused; in a ticket run or an Edit question a call that needs the person's OK waits for their answer on the phone (Claude asks and waits, below, PT-163), and their Deny refuses it. A refused call gets a `denied` step after it, "Not allowed: Run echo hello > out.txt", with the same `toolId` (Claude Code's `tool_use_id`), so the phone can tie the two; the reader knows a refusal from the tool result's `tool_result_meta` (`permission_decision.decision: "reject"`) or an earlier `system/permission_denied` event, says it once, and remembers only the calls still open. A call that ran and failed ("File does not exist") is no refusal. A path in the project's folder shows from it. Only the tool's name and a short detail go: never a tool's result, a file's contents, a Write's or Edit's text, a sub agent's prompt, a command's later lines (a heredoc's body is a file), a fetched address's query, or an MCP tool's free text (only a ticket or project key). Secrets are masked in every label, Claude's words in `text` steps too, since Claude may repeat a command it ran (`maskSecrets`, its rules in `secretRules.ts`); the chat answer from the `result` event stays as Claude wrote it. Masking is best effort, a few rules for the usual shapes: a quoted header whose name is a secret's (`-H "X-Api-Key: …"`, Authorization, Cookie), `Authorization: Basic|Bearer …` unquoted, httpie's `X-API-Key:abc123`, a quoted JSON key's value (`{"password":"…"}`, escaped inside double quotes too, and Python's `{'password': '…'}`), the password after `-u`/`--user user:`, quoted or not (not a numeric `-u 1000:1000`), an address's `user:password@` or `token@`, a secret flag's value (`--token=…` always, `--token …` only when the value looks like a secret: quoted, or with a digit, or 12 characters or more, so "Pass --token to the CLI" stays), `NAME=value`, well-known token prefixes (this tracker's own `trk_`, `ghp_`, `github_pat_`, `sk-ant-`, a long `sk-`, `sk_live_`, `xoxb-`, `glpat-`, `AKIA…`) and Slack webhook addresses. A name is a secret's by its words (`secretNames.ts`): a word that is or ends in token, secret or password, or is passwd, passphrase, pwd, cookie or authorization, anywhere; key, pass, apikey, secretkey, accesskey, privatekey or authkey last; so `GPG_PASSPHRASE`, `CLIENTSECRET` and `GITHUB_TOKEN`, `PGPASSWORD` and `_authToken` are, `MONKEY`, `KEYBOARD_LAYOUT`, `BYPASS_CACHE` and `--key-path` aren't. A value that names a secret without holding it (`$TOKEN`, `$(gh auth token)`, a backtick, `{expr}`) stays. A bare value never starts with `-` and stops at whitespace, a quote, a backtick and `< > | ; & )`, so it never takes the next flag or shell word (`--with-token < token.txt` stays). Still shown: a short `-p`/`-a` password (`mysql -p hunter2`; those flags can't be told from `mkdir -p` or `ssh -p 22`), a secret passed as a plain argument (`aws configure set aws_secret_access_key …`), a short bare `--token abc`, and a JSON value that starts with a space or a quote (`{"password": " x"}`), since such a quote is read as closing a search (`rg '"token":' src` stays); still masked though harmless: `--sort-key=name`, `PASSWORD_MIN_LENGTH=8`, `CACHE_KEY=…`, `-u root:root`, and a closed `NAME=` string with another quoted string later on the line, which hides the text between them (`grep -rn "API_KEY=" apps --include="*.ts"` shows `grep -rn "API_KEY=****.ts"`, likewise `rg "token=" -g "*.ts"`). A JSON value ends only at its own quote, so `"it's"` is masked whole. Masking runs in the helper's stdout listener, so names in the rules are bounded and each rule starts at a quote, a space or a word's start: open-ended `[\w-]*` on both sides of a keyword took 2 s on a 2,000-character line and minutes on 13 KB (PT-161 review). Values run to their end, since a value ends its pattern and can't backtrack, and a cut value showed the rest of a long token (a 900-character session token); a quote left open masks to the line's end, unless a space follows it and no other quote follows on the line, since then it closes a string (`grep "API_KEY=" src` stays). ### 1.12 Ask Claude

A comment on a ticket was the only way to talk to Claude Code from the phone, and nothing could be asked without a ticket. Each project now has chats with Claude Code on the person's own helper (PT-156; server `services/chats.ts`, `askRuns.ts`, `chatAnswers.ts`, `chatTickets.ts`, `runEnding.ts`, `http/routes/chats.ts`; helper `src/watch/ask/`).

- **A question is a run.** Sending one queues an `ask` run on the chosen helper, beside the `ticket` runs of §1.11, so the queue, the helper's check-ins, cancel, silence and restarts work the same. A helper has a lane per kind: it asks for work with `POST /runners/:id/next?kind=ask|ticket` and runs one run of each kind at a time (`watch/lanes.ts`), so an Ask or Plan question is answered while a ticket run works, and taking an ask ends only a lost ask, never the running ticket run (`test/regression/ticket-run-blocks-ask`, the helper's `ask-while-ticket-runs`). A helper that names no kind was built before asks and throws on a run with no ticket, so the server gives it ticket runs only, never a question (`takenBy` in `repositories/runs.ts`, `test/regression/old-helper-edit-question`). A question queued on it waits for a helper that names its lane (update and restart `tracker watch`), until the person stops it, or until that helper is silent for `HELPER_SILENCE_MS`. One question at a time per chat (a partial unique index on `chat_id`, like the one per ticket: the second send gets 409 "Claude is still answering."). A lane refuses a run of another lane, and a ticket run with no ticket, so only a ticket run or an Edit question ever gets the helper's own permission mode (`refusal.ts`).
- **Options** (PT-160). A row above the chat box picks a **Model** (Default, Opus, Sonnet, Haiku) and a **Mode** (Ask, Plan, Edit). Both POSTs send names only, `{ model, mode }`, checked by zod in `askInput` (a bad name gets 400). A name left out keeps the chat's saved one, and a new chat starts with `default` and `ask` (`chosenAskOptions`, `test/regression/ask-keeps-chat-options`). The run keeps them (`runs.ask_model`, `ask_mode`; `Run.askOptions`), and the chat keeps the last choice (`chats.ask_model`, `ask_mode`; `Chat.options`), so the next question starts with it. The row shows the chat's saved choice and follows it when it changes, as when another device asks; a field the person changed stays until they send (`useAskOptions`, `test/regression/ask-options-follow-chat`). Only a person asks, so only a person picks Edit.
- **Effort** (PT-172). An **Effort** chip beside the model picks Default, Low, Medium, High, X-high or Max, sent as `effort` (zod `ASK_EFFORTS`; left out, it keeps the chat's saved one like the model and mode). Like the model, the run keeps it (`runs.ask_effort`, null on ticket runs and older questions, read as `default`) and the chat keeps the last one (`chats.ask_effort`, default `default`; migration `0010_ask_effort`). Haiku has no effort setting (`modelTakesEffort` in shared): the chip hides while Haiku is picked but keeps its choice for the next model, and the helper sends no `--effort` for Haiku.
- **Flags come from names.** The server sends text and names only. The helper turns each name into its own fixed flags (`watch/ask/askArgs`): always `claude -p --output-format stream-json --verbose` (PT-161, so its steps show while Claude works; only the output format changed); Model adds `--model opus|sonnet|haiku`, nothing for Default; Effort adds `--effort low|medium|high|xhigh|max` (`askEffortArgs`), nothing for Default, an unknown name or Haiku. **Ask** is read-only: `--permission-mode plan --strict-mcp-config --disallowedTools Edit Write NotebookEdit`, whatever `--permission-mode` the helper was started with, so Claude can read and search the folder but not change it, and has no tracker tools. **Plan** gets the same flags; only the prompt differs (make a plan, change nothing). **Edit** gets what a ticket run gets: the helper's own `--permission-mode` (`default` when it was given none, so the person on the phone is asked before each step, §1.11), the folder's MCP servers, the tracker's too, and the prompt tool (§1.11, PT-163), so Claude can change files, claim, work and submit tickets, and ask the person and wait. A name the helper doesn't know, or none from an older server, runs as Ask; nothing from the phone ever becomes a flag of its own. The question goes on stdin like a prompt. `test/regression/ask-is-read-only` runs a fake `claude` through the runners `tracker watch` builds (`claudeRunners.ts`) for a helper started with `bypassPermissions`, and checks the flags each kind and mode got.
- **Edit waits in the ticket lane.** `?kind=` on `POST /runners/:id/next` names the helper's lane: the ticket lane takes ticket runs and Edit questions, the ask lane Ask and Plan questions (`laneOf`; the same filter decides which lost runs a take ends). So an Edit question waits while a ticket run works, and a ticket run waits for it: with the one-helper-per-folder lock (§1.11), two Claudes never change one folder at once. A helper's lane refuses a run of another lane (`refusal.ts`). The helper picks how to run a job by the run's kind, so an Edit answer still goes back to the chat.
- **The answer** is the stream's `result` event (`watch/stream/claudeResult.ts`: its `result`, or a failed run's `errors`, `session_id` and `is_error`; `askOutcome`). Background work Claude starts, such as a background sub agent, gets a turn of its own when it ends, so a run can print several results (`result_index` 0, 1, …): the first says "I started the sub agent", the last has the answer. The last one is the answer and decides done or failed, as `--output-format json` prints only it: a run that failed and went on ends done, one whose last turn failed ends failed; the helper ends the run `done` with `{ answer, sessionId }`, cut to `CHAT_ANSWER_MAX` with a note rather than refused. The server adds Claude's message and keeps the session in the same transaction as the run's end. A `done` with no answer is stored as failed with `CHAT_NO_ANSWER`, so the chat says why. A failed or cancelled ask adds nothing; the person can ask again.

Portability rules (SQLite locally, Postgres on Railway): app-generated text ids (`crypto.randomUUID()`), epoch-ms timestamps as `bigint` (parsed to numbers), no booleans, no JSON columns, schema built only with Kysely's schema builder. Text is matched, searched and sorted in JS (`matchesSearch`, `findStatusByName`, `localeCompare`), never with SQL `LIKE` (case-insensitive in SQLite, not in Postgres) or an `ORDER BY` on text (Railway's `en_US` collation sorts differently from SQLite and PGlite); SQL orders numbers only, with ids as the tie-break, which sort the same under any collation. A NUL in text is dropped before it reaches either database (`db/stripNul.ts`), since Postgres refuses it and every write holding one answered 500 (`test/regression/nul-in-text`). The API drops it as the text arrives too (`jsonBody` and `queryParams` in `http/validation.ts`, and the actor name), so the answer to a write and its checks against stored text see the text as stored: the answer echoed the NUL, an edit that only added one counted as a change (an activity entry and a live update), and an edit typed over text holding one was refused as stale (PT-137, `test/regression/nul-in-answers`). `withoutNulInJson` walks the body with a loop, not recursion: a field nested 200,000 levels deep, under the 1 MB limit, overflowed the stack and answered 500 (PT-147, `test/regression/deep-json-body`). The sign-in body alone goes as sent (`jsonBodyAsSent`), since a password is compared with what owner:set was given. Postgres integers stop at 2^31 − 1 where SQLite's go on, so a value from outside that could pass it is checked first: ticket numbers in keys (`parseTicketKey`) and image dimensions (`test/regression/image-size-past-integer`). Postgres runs transactions side by side at READ COMMITTED: a write that depends on what was read is conditional (`updateTicketMatching`, `takeTicketNumber`'s `UPDATE … RETURNING`) or caught by a unique index (client ids, §3), and a retry runs outside the transaction, since a statement that fails in one ends it on Postgres. Integration tests run on SQLite and on PGlite (real Postgres in WASM); `test/integration/portability` covers where the two differ. `DATABASE_URL` picks the dialect: a file path or `:memory:` for SQLite, `postgres://…` for Postgres. Any other value holding `://`, `postgres:` or `postgresql:`, or two letters before `:/`, wherever it starts (`looksLikeUrl`: a one-slash `postgresql:/user:pw@host/db`, also with quotes, a space or `DATABASE_URL=` in front; `mysql://…`), is refused and never printed, not opened as a file, which made folders named after the password (PT-137, `test/regression/one-slash-database-url`; PT-147, `wrapped-one-slash-database-url`). So is any value with an `@` after a colon, a `user:password@` whatever the scheme or with none, also percent-encoded (`%3A`, `%40`) as copied from a query string or a log (`postgre:admin:pw@h/db`, `admin:pw%40h/db`, PT-151, `mistyped-scheme-database-url`); a file path holding both is refused too, and the error says a path can't hold one. A Windows drive has one letter before its colon, and a file name may hold one (`tracker-10:30.db`), so both stay paths (`test/regression/database-file-name-colon`).

### 2.1 Postgres and migrations

- **Pointing at Postgres:** `DATABASE_URL=postgres://user:password@host:5432/database`. On Railway the service takes the database's private address (`${{Postgres.DATABASE_URL}}`), which needs no SSL. SSL follows `sslmode` in the URL, else `PGSSLMODE`, with libpq's meanings (`db/postgresPool.ts`; node-postgres reads `require` as `verify-full`): `require` and `prefer` encrypt without checking the certificate, which Railway's public address needs (its certificate is self-signed), `verify-full` checks it, `disable` or none is plain. The pool has `DATABASE_POOL_MAX` connections (10), a `DATABASE_STATEMENT_TIMEOUT_MS` statement timeout (30000, `0` for none), 10 s to connect and 60 s idle in a transaction. A connection the database drops is logged and replaced on the next query, instead of ending the process. On SIGTERM or Ctrl-C the server takes no new connections, ends live-update streams at once (browsers reconnect), gives requests under way 10 s (`shutdown.ts`), then closes the pool once their queries are done.
- **Commands** (`db/cli.ts`), on `DATABASE_URL` or `data/tracker.db`: `npm run db:migrate` runs every pending migration; `npm run db:rollback -- --yes` undoes the last one (without `--yes` it only says which one it would undo); `npm run db:status` lists each as applied (with its time), pending, or applied by a build this one lacks. They run the source with tsx. The build has them as `node apps/server/dist/db.js migrate|rollback|status`, which needs no dev dependencies: a deploy's pre-deploy command is `node apps/server/dist/db.js migrate`. Migrations run without the statement timeout.
- **One transaction, one at a time:** a run is one transaction, so when any of its migrations fails none of the run is kept. That holds on SQLite too: Kysely assumes SQLite can't roll back DDL, and `db/sqliteDialect.ts` tells it otherwise. On Postgres Kysely (0.29, in `apps/server/node_modules`; the 0.27 at the root is only `kysely-pglite`'s peer and takes `pg_advisory_xact_lock`) holds a session advisory lock (`pg_advisory_lock`) around the run's transaction and reads what has run only once it has it, so a second deploy migrating at the same moment waits, then finds nothing to do (`test/integration/migrationCommands` sees the lock held during each migration). Kysely gives that wait its own one-hour `lock_timeout`, so `db.js` and `MIGRATE_ON_START=1`, though they run without the statement timeout, give up after an hour behind a stuck migration. Being a session lock, it needs a direct connection, not a PgBouncer in transaction mode. On SQLite transactions begin `IMMEDIATE`, taking the file's write lock up front, so a second process waits (the 5 s busy timeout) instead of failing halfway.
- **On start:** the server migrates a SQLite file itself. It leaves Postgres to the pre-deploy command, so a migration that fails stops the deploy while the old server keeps serving, where one at start would crash-loop the new server; it then checks the database has exactly its build's migrations, and refuses to start otherwise, naming the ones missing or the ones it doesn't know (`db/startup.ts`). `MIGRATE_ON_START=1` migrates Postgres on start too (for a host with no pre-deploy step; the lock keeps several servers safe), without the statement timeout like the commands: on one of the pool's connections, which gets its own timeout back after (PT-137, `test/regression/migrate-on-start-timeout`); and `MIGRATE_ON_START=0` leaves a SQLite file alone.
- **Undoing a release:** first undo its migrations with that release's build (`npm run db:rollback -- --yes` once per migration, from its checkout with `DATABASE_URL` set, or `node apps/server/dist/db.js rollback --yes` in its deployment), then deploy the older build. An older build refuses a database that has migrations it doesn't know, and so does its `db:migrate`. A down() drops what its up() added with the data in it, so take a backup first.
- **Writing a migration:**
  - Add `apps/server/src/db/migrations/NNNN_snake_case.ts` with the next number, exporting `up` and `down`, and list it in `migrations/index.ts` (the bundled server can't read a folder). `test/unit/migrationFiles` checks names, numbers and the list.
  - Never edit a migration once it has run anywhere but your own machine; write a new one.
  - Portable SQL only: Kysely's schema builder with `text`, `integer` and `bigint` (no booleans, JSON, enums, serial, or `alterColumn`, which SQLite lacks), explicit snake_case names (migrations run without the camel-case plugin), and a name for every index and constraint so down() can drop it. Raw `sql` only to move data, in SQL both databases take.
  - A real down(): it removes exactly what up() added, in reverse order. `test/integration/migrationRoundTrip` runs every up, down and up again on SQLite and PGlite and fails when a down() leaves the schema different, or when the two databases end up with different schemas.
  - The previous release keeps serving on the new schema until the new server is up, so add columns nullable or with a default, and drop or rename a column only in a later release, once no code reads it.
  - Nothing Postgres can't run in a transaction (`CREATE INDEX CONCURRENTLY`), and no SQLite table rebuild of a table others reference: foreign keys stay on inside a transaction, so dropping it deletes their rows.
  - A data migration uses its own SQL, not repositories or services, which change after it is written.

### 2.2 Running on Railway

Steps for the user: `docs/deploy-railway.md`.

- **Build and deploy** (`railway.json`, Railpack, Node 22 from `engines`): `npm ci`; `npm run build && NPM_CONFIG_PRODUCTION= npm prune --omit=dev` (Railpack sets `NPM_CONFIG_PRODUCTION=false`, under which npm keeps dev dependencies); pre-deploy `node apps/server/dist/db.js migrate`; start `node apps/server/dist/main.js` (node itself, so it gets SIGTERM); health check `/api/health`; `drainingSeconds` 15, more than the 10 s shutdown grace. `test/unit/railwayConfig` checks these against the server build's entries and the code. The bundle keeps npm dependencies external, so the deployment runs on the pruned `node_modules`; `sharp`'s Linux binaries come from the lockfile's optional packages.
- **On Railway** (`RAILWAY_ENVIRONMENT_ID` set, `railway.ts`, applied in `loadConfig`): `HOST` defaults to `0.0.0.0`, `TRUST_PROXY` to 1 (Railway's edge sets `X-Forwarded-For` and `X-Forwarded-Proto`), `PUBLIC_URL` to `https://` + `RAILWAY_PUBLIC_DOMAIN`. The server refuses to start, and `db.js` to migrate, unless `DATABASE_URL` is `postgres://` or a file under `RAILWAY_VOLUME_MOUNT_PATH`, and unless files go to S3 or to an `UPLOADS_DIR` under it, since a deployment's own disk goes with the next deploy (`test/regression/railway-data-off-volume`: a value pasted with quotes passed as a SQLite path). The messages never show the value. Logs name the database with `describeDatabase`, which never prints a URL it can't read (`test/regression/describe-database-password`).
- **Disk uploads** arrive as `.<uuid>-<key>.partial` beside the stored files and take their key once whole; opening disk storage removes partial files, since a stop that cuts an upload at the grace exits before the handler can (`test/regression/upload-cut-at-shutdown`).
- **One replica:** sign-in limits (§3.1) and live-update events live in the process's memory.
- **Tracker first, then helpers:** a helper newer than its tracker may call routes the tracker doesn't have yet (asking the person, §1.11), so a deploy goes out before `tracker watch` is updated on the computers; such a helper denies those steps with "Update the tracker."
- **Response headers** (`http/responseHeaders.ts`): Hono's `secureHeaders` on every answer: HSTS (180 days, subdomains; browsers ignore it over plain http, so local runs are unaffected), `nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy: no-referrer`, same-origin opener and resource policies. No Content-Security-Policy there: it would replace the `sandbox` one text attachments get (§3). `/api/events` answers `Cache-Control: no-cache, no-transform` and `X-Accel-Buffering: no`, so a proxy neither buffers nor compresses it and the pings arrive; the server compresses nothing on the fly (the web build ships `.br`/`.gz` copies).
- **Railway's limits:** a request ends after 15 minutes (live-update streams reconnect) and an upload must arrive within 5 minutes, sooner than the server's hour.
- **Moving a local tracker in** (PT-124, `src/dataMove/`, `node --env-file=.env apps/server/dist/data-move.js --from <db> --uploads <dir> [--dry-run] [--allow-existing]` or `npm run data:move`, run once from a laptop on Railway's public Postgres URL with `PGSSLMODE=require`, `docs/deploy-railway.md` step 7): the target is only `postgres://` and S3 (`moveTarget.ts`), since a SQLite file or a local folder could only be a slip (an empty `$DB` once made `?sslmode=require` a SQLite file that took every row, and a path naming the source another way migrated it); values are never printed. It backs the SQLite file up with SQLite's online backup to a temporary copy (removed on exit, Ctrl-C, SIGTERM and SIGHUP, which closing its terminal tab sends) and migrates the copy, never the original; checks every file before it touches the target: a missing one, or an image `compressImage` can't store, whose metadata it can't remove (a TIFF, one cut off before its picture), stops the move before any file or row is written, listed by id, ticket key or the comment holding it (only comments hold files), file name, size and reason, never ticket text (`refusedImages.ts`: in the local tracker the user removes one on a ticket from the ticket's files, and deletes a comment holding one, since the app can't remove a single file from a comment; a dry run lists them with the target's problems); migrates the target only when it has no tables at all, and refuses one behind this build (deploy the commit first, else the older server would refuse its next start), one with unknown migrations or with tables but no migrations; refuses a target holding projects or tickets unless `--allow-existing`, and one already holding the same ids or a project key; opens storage only to write (a dry run never does); uploads every file, images through `compressImage` with the row's type, name, size, dimensions and key updated and its id kept; then inserts projects, statuses, tickets, activities and attachments in that order, with their ids, in one transaction; then counts each table's rows by id and checks every attachment's object and size. Files first, so a failed run leaves files but no rows, and running again starts over under the same keys; an error or a signal ends with whether rows were written (`stopped.ts`). Pending uploads (on no ticket or comment) stay behind, and the plan says how many (`pendingUploads.ts`): only the page or agent that uploaded one can attach it, through the tracker it went to, and a server stopped during an upload leaves one naming a missing or partial file, which refused the whole move (PT-133 review). Sign-in tables stay behind, invites too: the online owner is set with owner-set. Moved projects and files go to the target's owner, or to nobody until owner-set makes one, which then gets them (`dataMove/owner.ts`, PT-142).

### 2.3 Versions and releases

Steps: `docs/releasing.md`.

- One semver version for the whole app: the root `package.json` (`APP_VERSION` in `packages/shared/src/logic/appVersion.ts`, baked into each build; the server and agent builds keep only its `version` field, `scripts/build/rootVersionOnly.ts`). Workspace packages stay private at `0.0.0`. It started at 1.0.0 (PT-182), since the tracker was already in daily use on Railway.

| `DELETE /chats/:id`                                                         | A person deletes the chat with its messages and runs, cancelling an answer in progress (§1.12)                                                                    |
| `POST /chats/:id/messages/:messageId/ticket`                                | A person creates the ticket on Claude's card `{ title, description, priority }`; a repeat gets the same ticket                                                    |

Status changes made by the dropdown, a report, sending, claiming, submitting or reviewing put the ticket at the **top** of its new group (`topRank`). Drags and keyboard moves renumber the destination group (`planMove`).

**Client ids.** `POST /projects/:key/tickets` takes an optional `clientId` (1–64 characters) from a client that may send the same create again (quick capture, §1.9). The ticket keeps it, unique per project. A create that repeats it answers 201 with the ticket the first one made, as it is now, whatever the body's text says (quick capture saves the text the person changed with an update, §1.9), and logs nothing. Only its files count: those in `attachmentIds` the ticket lacks, pending uploads chosen after the first create, are attached after the ticket's other files in the order given, as a file uploaded to it later would be, with a new `updatedAt` and a change event; a file that is gone, such as one the first create attached and someone removed from the ticket since, or one chosen after it whose upload expired (24 h, §1.4), is left out (PT-82; it answered "Some files could not be attached. Upload them again." for a ticket that exists, `test/regression/client-id-repeat-removed-file`), and the answer names it: the ticket with `leftOutAttachmentIds`, a field only there when a file was left out (`CreatedTicket`, PT-97, `test/regression/client-id-repeat-expired-file`), while one that can't be attached otherwise (on another ticket or a comment) refuses the repeat with 400, as it would a create, and none is attached. A first create naming a file that is gone is still refused. Without new files a repeat changes nothing. It is looked up in the create's transaction, so two identical creates at once give one ticket, one number and the same answer. On Postgres with several connections both can miss it; the unique index then refuses the second once the first has committed (`23505`; SQLite's `SQLITE_CONSTRAINT_UNIQUE` is caught too), and the second, rolled back with its number, runs again like a later repeat. SQLite and PGlite run one transaction at a time, so `test/regression/client-id-race` makes the lookup miss to show it.

**Saves typed over a value.** `PATCH /tickets/:key` takes an optional `expected` with the text the title, description or assignee was typed over (the assignee trimmed, as kept). A field the update names in both that has other text now refuses the whole update with 409 `stale` and changes nothing, so an older save that lands late can't overwrite a newer one. That holds also when the update would change nothing: a tab that cleared a name another tab was still sending must not let that save land after it. The write matches the values too (`updateTicketMatching`), so on Postgres a save committed after the read is caught as well. Agents send no `expected` and save as before. The web app sends it with every field save (§1.6). `PATCH /activity/:id` takes `expected: { text }` the same way for a comment edit (trimmed, as kept; `updateActivityMatching`, PT-105).

**Attachment files.** `POST /attachments` takes the file itself as the body: its type as `Content-Type` (`application/octet-stream` when the browser gives none), its name percent-encoded in `X-File-Name` (`FILE_NAME_HEADER`) and `?ticketKey=`. A form, as pages from before this sent, gets "Reload the page and add the file again." The type and a declared `Content-Length` are checked with `checkAttachment` (§1.4) before the body is read, so each kind has its own limit. The body then streams to storage as it arrives (`measureUpload`, `FileStorage.write`), so the server holds a chunk of an upload, never the file (with S3, up to two 5 MB parts; images, at most 15 MB, are read whole to be compressed, below): reading it whole first took a 95 MB video from 76 MB to 660 MB; streamed, the server keeps nothing (`npx tsx scripts/check-upload-memory.ts` shows its memory under a few 95 MB uploads). While it streams, a body sent without a length is cut off at its kind's limit (the same message), and one that breaks off or ends short of its length gets "The file did not arrive whole. Try again."; either way no file and no row are kept. Uploads get an hour (`requestTimeout` in `main.ts`; Node's default of five minutes answered 408 to a 100 MB video sent slower than 2.8 Mbit/s), so the largest file arrives over a 240 kbit/s uplink. Every other request keeps Node's five minutes to send its body (`endSlowRequests`, which answers 408 and closes the connection the way Node does), even one answered before its body has arrived, as a GET or HEAD is, and headers keep Node's one minute. `npm run dev`'s Vite server gives requests the same hour (`vite.config.ts`), since uploads pass through its `/api` proxy. Files are stored as `<id>.<extension of the type>` (`FileStorage`: disk; S3 when `S3_BUCKET` is set, as `attachments/<key>` in a private bucket, `docs/s3-storage.md`, PT-122; memory in tests; one contract test runs against all three), images keep the dimensions of the stored file, and names lose their control characters (Postgres refuses a NUL; a tab or line break becomes a space) and are cut to 200 characters without splitting one, before their extension so it stays (PT-127 review; `attachment.<ext>` when there is none). `GET /attachments/:id/file`:

- Always `Accept-Ranges: bytes`. One range (`bytes=a-b`, `bytes=a-` or `bytes=-n`) answers 206 with `Content-Range` and reads only those bytes from storage (`FileStorage.read(key, range)`; disk storage streams them, S3 storage asks S3 for just those bytes). iOS Safari doesn't play video without this. A range that starts past the end (or `bytes=-0`) answers 416 with `Content-Range: bytes */size`; several ranges or a malformed one get the whole file (200). HEAD answers the headers of the whole file and ignores `Range`; it asks storage whether the file is there (`FileStorage.stat`) without opening it.
- `Content-Disposition: inline; filename="…"; filename*=UTF-8''…` (RFC 5987, with an ASCII fallback), so downloads keep their names. `X-Content-Type-Options: nosniff` and `Cache-Control: private, max-age=31536000, immutable` on every answer with the file.
- Text kinds are served with `; charset=utf-8` and `Content-Security-Policy: sandbox` (defense in depth). Not PDFs: Chrome won't show a sandboxed PDF.
- An upload's row goes in first, pending (no ticket, no comment), and is finished with its size and ticket once the file is whole, so no file is stored without a row naming it: an upload cut off or a server stopped half way leaves a pending row, which the start-up clean-up of pending uploads removes with its file after a day (the data move leaves it out, §2.2). An upload whose pending row is gone by then answers 500 and removes its file. Deleting an attachment, ticket, comment or project removes its rows first, then its files (`removeFiles`): a file storage won't remove is logged with its key as one to remove by hand (`File <key> stays in storage and must be removed by hand`), since nothing removes it later, and the delete still answers as done, since the tracker no longer has it. No server removes a file its own database didn't delete or record as pending: a start-up sweep that removed the bucket's files no row named deleted another database's files on a shared bucket (PT-133 review).

**Images are compressed before they are stored** (PT-127, `apps/server/src/images/`), and only the result is kept: the attachment's type, name and size are the stored file's (`IMG_0042.JPG` becomes `IMG_0042.webp`). An image upload is read whole (at most its 15 MB; the limits apply to the original as before), then sharp turns it upright from its EXIF orientation, drops its metadata (EXIF with the GPS location and camera, XMP, IPTC, text chunks) and converts it to sRGB, shrinks it to a pixel budget without ever enlarging it, and encodes WebP, which every browser the app supports and Claude read:

- Photos (JPEG, WebP): lossy, quality 80, within 2560×1920 pixels (4.9 MP; a 12 MP iPhone photo becomes 2560×1920). A budget of pixels rather than a longest side keeps a panorama tall enough to see.
- PNGs (screenshots, drawings): lossless, so text stays sharp, within a 4K screen's 3840×2160 (8.3 MP; phone, iPad and MacBook screenshots keep every pixel).
- The bytes decide what an image is (`sniffImageType`), whatever its name or type says: browsers take the type from the name, so a JPEG saved as .png arrives as image/png (PT-127 re-review). It is read, stripped, stored and named as what it is (`photo.png` holding a JPEG is stored as `photo.webp`, or kept as `photo.jpg`). A JPEG is known by its start marker `FF D8` alone, as libjpeg and libvips know it, since they skip stray bytes after it (a GPS JPEG with one there was kept with its GPS, PT-127 review). sharp may run only its JPEG, PNG, WebP and HEIF readers (`sharp.block`), and the format it reads must be the one sniffed, so a body is never drawn as SVG, TIFF or PDF. A TIFF body is refused with the unsupported-type message, since its EXIF can't be stripped; bytes that are no image we know are kept as declared. libjpeg's warnings don't stop a decode (`failOn: 'none'`): files every viewer shows, with extra bytes before a marker or a cut-off end, were kept with their GPS.
- The WebP is stored when the image had to turn, shrink or lose metadata, even if it came out larger; otherwise only when it is at least 10% and 16 KB smaller, so a small or already lean image keeps its type, name and pixels.
- Kept as they came: GIFs (they may move; an animation decoded whole could take hundreds of MB), animated WebPs, images too big to decode (past 50 MP; past 25 MP held whole: a progressive JPEG, an interlaced PNG, a WebP, or a picture turned a quarter, which a JPEG first shrinks while reading, so a 48 MP portrait iPhone photo still fits; or estimated past 450 MB of work), a JPEG of more than 100 scans (`MAX_JPEG_SCANS`, `countJpegScans`; encoders write about 10: libjpeg reads every scan before its first row comes out and sharp checks its timeout only between rows, so 950,000 empty scans in 14 MB ran 160 s, holding a photo lane and one of Node's 4 thread-pool threads; it is now counted and kept, stripped, in 0.13 s), an encode that fails or passes 30 s, and HEIC/HEIF, because sharp's prebuilt libvips has no HEVC decoder (`DECODES_HEIC`; a build with one converts them). File pickers don't offer HEIC, so iPhones send JPEG (§1.4, PT-128). Compression failing never refuses an upload.
- A kept JPEG, PNG or WebP loses its metadata without being decoded (`stripMetadata`, chosen by the bytes): JPEG segments but those the picture is drawn from (frame headers, tables, restart interval, scans) and the ICC profile when its chunks make one well-formed profile (numbered 1 to their count once each, the size its header says, `acsp`, at most 1024 tags, every tag inside it, and nothing outside the tags but up to 3 zero bytes of padding; otherwise every ICC chunk goes, as libjpeg ignores a misnumbered one anyway; real profiles stay byte for byte; the rule removes only bytes outside the tags: any tag's data, of any kind and size, a made-up private tag too, still passes, and closing that would mean rewriting or replacing profiles, PT-175), with the first JFIF and the first Adobe header, cut to the fields libjpeg reads (no JFIF thumbnail or extension, nothing after Adobe's color transform, PT-152; files from Preview, ImageMagick, Pillow and libjpeg keep theirs byte for byte), so other APP segments, comments and markers libjpeg doesn't know go, between scans too, and so does anything after the end marker; the walk skips stray bytes before a segment, right after the start marker too, and reads a length field below 2 as an empty segment, as libjpeg does (such a segment was stored without its length bytes, and nothing could show the file, PT-146); PNG ancillary chunks but those that change how it looks (transparency, color, size, APNG frames), so text, `eXIf`, `tIME` and unknown chunks, wherever they are, and anything after `IEND`; WebP chunks but the picture's, its animation's and its color profile's (only a well-formed one, as for JPEG; the header's ICC flag goes with it). A PNG's `iCCP` stays as it is: a well-formed profile can carry any bytes in a tag anyway, so checking the compressed one would add little. Each strip reads the upload in place and copies only what it keeps. Which way is up stays as a one-entry EXIF (JPEG) or `eXIf` (PNG), and width and height are as shown. A strip that finds no image data (cut off before its picture) refuses the upload (`NOT_WHOLE_MESSAGE`) rather than store a file nothing shows, or one with its metadata. A HEIC keeps its metadata (taking boxes out of HEIF needs a rewrite of its offsets), and a GIF has nowhere to put a location.
- Memory: each encode is estimated from its pixels and what is held whole (`workBytes`: 64 MB, 2 bytes a channel for each pixel held whole, then 4 bytes per pixel out, 44 lossless; upper bounds of measured peaks) and let in while the estimates fit in its lane: photos (estimated up to 100 MB) within 200 MB, so one never waits behind a big image, and the rest within 450 MB (`createWorkLimiter`). No image estimated past 450 MB is decoded. So image work stays within about 650 MB on top of the server's own memory, plus the uploads waiting their turn (each at most 15 MB). One libvips thread an image (`sharp.concurrency(1)`), libvips' cache off. Measured peak RSS on an M-series Mac: alone, a 12 MP photo +38 MB, a 48 MP portrait JPEG +51 MB, a 25 MP progressive 4:4:4 JPEG +190 MB, a 25 MP WebP +174 MB, a 4K screenshot made lossless +292 MB (a 25 MP interlaced 16-bit PNG took +525 MB and is now kept instead); six crafted big images and two photos at once +534 MB (658 MB in all), the photos done in 0.4 s; three 4K screenshots, two 25 MP WebPs, a progressive JPEG and two photos +594 MB (736 MB). A 4.8 MB iPhone JPEG became 838 KB (−82%), a phone screenshot 168 KB → 65 KB.

**The web app prepares images before it uploads them** (PT-134, `apps/web/src/lib/imagePlan.ts` decides, `images.ts` encodes on a canvas), to the server's own budgets (`MAX_PHOTO_PIXELS`, `MAX_LOSSLESS_PIXELS` and `sizeWithin` in `@tracker/shared`, `domain/imageBudget.ts`), so nothing is shrunk twice. The step stays because it drops GPS on the phone, makes a JPEG of a HEIC the browser can decode (Safari) and keeps uploads small: Railway ends an upload after 5 minutes.

- A JPEG or WebP within 4.9 MP and up to 2 MB goes as it is; the server makes its WebP and drops its metadata. A bigger one becomes a JPEG within 4.9 MP at quality 0.92, close to lossless as the server encodes it once more, sent only when that is smaller than the original. Otherwise the original goes, even past the budget, and the server shrinks it and drops its GPS in its one lossy pass (PT-145): a light 2592×1944 JPEG of 240 KB went up as 486 KB (Chromium) or 738 KB (WebKit) and was compressed twice; it now goes as it is and is stored as 40 KB of WebP at 2560×1920, without its GPS. Past 25 MP (`MAX_WHOLE_DECODE_PIXELS`), where the server may keep a photo as it came, the JPEG always goes. A photo counts as a JPEG or WebP by its first bytes (`imageBytes.ts`), not its type: browsers take the type from the name but decode by content, so a HEIC named .JPG (Safari) or an AVIF named .jpg (Chrome, Safari), which the server can neither read nor strip, went as it was and was stored with its GPS. A photo whose bytes are neither is always converted (PT-145 review). Both sides are rounded down, so the result is within the budget and the server keeps its size.
- A PNG within 8.3 MP and 15 MB goes as it is, so the server stores it lossless. Past 8.3 MP it becomes a PNG within it; a PNG still over 15 MB then, or over 15 MB within 8.3 MP, holds a photo's detail and becomes a JPEG within 4.9 MP.
- A HEIC the browser decodes always becomes a JPEG within 4.9 MP; one it can't (Chrome) goes as it is and is kept as it came (above). GIFs go as they are.
- A canvas holds only pixels, so what the app encodes has no metadata. Before, every image past 2048px or 2 MB became a 2048px JPEG at quality 0.85: photos were compressed twice and never reached 2560×1920, and screenshots arrived as JPEG with blurred text.
- Measured with a 12 MP iPhone photo (4032×3024, a 4.9 MB JPEG with GPS): the upload went from 1.6 MB (WebKit) and 0.85 MB (Chromium) at 2048×1536 to 2.4 MB and 1.7 MB at 2560×1920, 19 s and 14 s at 1 Mbit/s (the original takes 39 s). The server stores 819 KB and 799 KB of WebP at 2560×1920 (858 KB from the original), where it stored 620 KB and 560 KB at 2048×1536. No stored file kept the GPS: a JPEG or a screenshot with GPS in its `eXIf` chunk sent as it is, a HEIC converted in WebKit (`compressImage.test.ts`, "what the web app sends as it is").

### 3.1 Sign-in and API tokens

- **Who gets in.** Every `/api` route needs an account's session cookie or an API token, except `GET /api/health`, `GET`, `POST` and `DELETE /api/session`, `POST /api/invites/check` and `/accept`, and `POST /api/password-resets/check` and `/use`; that includes `GET /api/events` and attachment files (`http/auth.ts`). A request gets `401 unauthorized` ("Sign in to use this tracker."). Once an owner exists, sign-in is required everywhere. Before that, the rule (`authConfig.ts`, `http/localRequest.ts`, PT-120 review): a server bound to loopback (`HOST` 127.0.0.1, localhost or ::1), not behind a proxy (no `TRUST_PROXY`) and without `TRACKER_TOKEN` (which used to protect it, so it stays closed) answers requests made on its own machine without sign-in: the Host is a loopback name (not a page that reached it by DNS rebinding, not another device), and so is every `X-Forwarded-Host` and `X-Forwarded-For` entry. The dev server (Vite, `host: true`) passes requests from the whole LAN on to the API, so its proxy sends `xfwd` (`vite.config.ts`), and a phone using it must sign in. A proxy or tunnel on the same machine (`ssh -R`, `socat`, a bare nginx) that sends `Host: localhost` and no `X-Forwarded-For` can't be told apart from a local request, so everything it passes on gets in; the start line says to set an owner before using one (`auth/startupNotice.ts`, PT-138). Requiring an owner on every server was the other choice, but it would end the documented local setup without one. Only `localhost`, `127.x.x.x` and `::1` count as loopback (`isLoopbackHost` in `@tracker/shared`, also used by the CLI and the Connect sheet); `*.localhost` doesn't, since some Linux resolvers ask DNS for it (PT-138). Everyone else, and every request to any other server, Railway included, gets `401`, and `GET /api/session` says `setupRequired`, which the sign-in screen turns into the setup command. Without an owner, the actor header is taken as sent, as before.
- **Accounts.** `users` holds the owner (`role` `owner`, made by owner-set) and the people the owner invited (`role` `user`). Migration 0011 makes only the earliest account the owner, and its down() refuses while invited accounts exist ("Can't undo 0011_user_projects while invited accounts exist…"): without roles and owners they would see and change the owner's projects, and running it again would give their projects to the owner (`test/regression/rollback-makes-users-owners`). Undoing that release then means restoring the backup taken before it. There is no open sign-up: the tracker is on the public internet. Users share nothing: each sees only the projects they made, the owner included; the owner's one extra is inviting.
- **The owner** is set with `npm run owner:set -- --email …` (`apps/server/src/cli/setOwner.ts`; `node apps/server/dist/owner-set.js` in a build). It reads the password from the terminal (twice, hidden) or the first line of a pipe, never from env vars or arguments, needs at least 12 characters and keeps only an scrypt hash (N=2^15, r=8, p=1, 16-byte salt, 64-byte key; the parameters are stored with the hash). It works on the server's database (SQLite file or `DATABASE_URL`) through `prepareDatabase`, so it migrates a local SQLite file but never applies a checkout's migrations to Postgres. Run again, it replaces the owner's email and password and ends the owner's sessions; API tokens stay. An email another account uses is refused. Creating the owner gives it everything made before it, when everyone on this computer was that one person: projects, pending uploads, runs, helpers and chats. A hash in an env var was the other choice: the command keeps the account in the database the server already has, and changing the password needs no redeploy.
- **Signing in:** `POST /api/session { email, password }` for any account (`auth/login.ts`). Wrong email and wrong password get the same answer ("Email or password is incorrect.") after the same work: the password is always checked against the account's hash, or a throwaway hash for an email no account has. Each try counts before it is checked, so tries sent side by side can't slip past the limits: 10 per address and 30 per account (the typed email, lower-cased) in 15 minutes, then `429 rate_limited` with `Retry-After` and "Try again in N minutes" until the window ends; a success clears both. The limits are kept in memory (`auth/loginLimits.ts`, at most 10,000 keys), fine for one server process. The address is the connection's, or with `TRUST_PROXY=N` the Nth entry from the end of `X-Forwarded-For` (the one the trusted proxy added; earlier entries come from the client).
- **Sessions** are rows (`sessions`), so they can be ended. The cookie `tracker_session` holds 256 random bits (base64url); the table keeps its SHA-256. It is `HttpOnly`, `SameSite=Lax`, `Path=/`, and `Secure` on https, behind a trusted proxy that says `X-Forwarded-Proto: https`, or with `NODE_ENV=production`. A session ends after 30 days without use and 90 days after sign-in in any case; use renews it at most once a day, with a new cookie `Max-Age`. Signing in again from the same browser ends its previous session, a sign-in clears ended sessions, and a cookie the server doesn't know is cleared. `DELETE /api/session` ends this session and `DELETE /api/sessions` every session of this account; both clear the cookie and send `Clear-Site-Data: "cache"`, so the browser also drops its HTTP cache, where attachment files are kept for a year.
- **Writes from other sites:** besides `SameSite=Lax`, a POST, PATCH, PUT or DELETE whose `Sec-Fetch-Site` is `cross-site` or `same-site` gets `403`, which also covers sites under the same registrable domain.
- **API tokens** for Claude Code agents: `trk_` and 256 random bits, sent as `Authorization: Bearer …`. Created with a name ("Claude laptop", 1–60 characters), the secret is in the answer once; the table keeps its SHA-256 and a hint (`trk_` and 4 characters) to tell tokens apart. `GET /api/tokens` lists name, hint, created and last used (updated at most once a minute); `DELETE /api/tokens/:id` revokes at once. Each account manages its own tokens, signed in with its password (session cookie), and so signs out everywhere, so a token that leaks can't make more of itself (`403`). A token acts for its account: it reaches that account's projects only. An unknown token counts as none, so a local tracker without an owner stays open to agents still set up with an old `TRACKER_TOKEN`. A request with a token always acts as an agent, whatever `X-Actor-Kind` says (it keeps the name it sends, else "Agent"), so it can never move a ticket to Done; only an account's session acts as the person. An agent, with a token or without, can't be called "You" or "User" (any case, compared after NFKC and without invisible format characters, so full-width letters and zero-width spaces don't get past; lookalikes from other scripts do): those are the person's names in the web activity and in the CLI text agents read, so the request gets `400 invalid_input` asking for another name (`refusePersonName` in `http/actor.ts`, PT-138). Refused rather than relabelled: activity shows no account's name (`users.name` is kept but shown nowhere yet), so there is none to compare with, and the web already marks agents with their avatar. The CLI, MCP server and Connect sheet use them since PT-125 (§4).
- **Invites** (PT-142, `auth/invites.ts`, `auth/acceptInvite.ts`, `http/routes/invites.ts`). Only the owner, signed in with the password, makes, lists and cancels them (another account, a token or a tracker without an owner gets 403). An invite is 256 random bits; the table keeps its SHA-256, and the link holds it after `#` (`/invite#<secret>`, `invitePageUrl`), which browsers never send to a server, so it stays out of logs and `Referer`. It works once and for 7 days (`INVITE_TTL_MS`). `POST /api/invites/check { secret }` answers `expiresAt`, and `POST /api/invites/accept { secret, name, email, password }` makes a `user` account (email lower-cased, password at least 12 characters, scrypt like the owner's) and signs it in (201 with the session, as a sign-in). The link is checked before the password is hashed. A used, expired or unknown link gets 404 with what to do ("This invite was already used. Sign in instead.", "This invite has expired. Ask for a new one.", "This invite link does not work. Ask for a new one."); telling them apart gives nothing to someone guessing 256 bits. An email that has an account gets 409 and the invite stays usable; the account is inserted and the invite used (a conditional update) in one transaction, so two accepts at once make one account. Both public routes read at most 16 KB, like sign-in, and pass the password as sent (`jsonBodyAsSent`); the name loses its control characters (a tab or line break becomes a space, a NUL goes), and one left empty is refused. They have a limit per address with sign-in's numbers, counted apart from sign-in's (`limitTries` in `http/tryLimits.ts`, 10 tries in 15 minutes, then `429` with `Retry-After`). It runs after the body is validated, which looks nothing up, so a short password, an empty name or a mistyped email costs no try; every try that reaches the invite lookup counts, before it is checked, since a valid link with a taken email would otherwise make the server hash a password as often as it is sent, and the web app checks a link once per page. Tests send three accepts of one invite at once (one account) and two invites with one email (201 and 409), on SQLite and PGlite.
- **Changing a password** (PT-177, `auth/changePassword.ts`, `http/routes/password.ts`). Any account, owner or invited, signed in with its password (a token or a tracker without an owner gets 403), changes its own with `POST /api/password { currentPassword, newPassword }` (Account, Change password). The new one follows the invite's rule (12 to 1,024 characters, scrypt); a wrong current password gets `400` "Your current password is not right." and changes nothing. On success every other session of the account ends and this one stays, in one transaction with the new hash: whoever knew the old password may hold a session. API tokens stay: they are separate credentials the person makes and revokes in Connect, and ending them would stop every agent each time a password changes; one that leaked is revoked there. Tries are limited per account with sign-in's numbers, counted apart (10 in 15 minutes, then `429`): per account rather than per address, since whoever guesses already holds the session and an address is cheap to change. A mistyped form (an empty current password, a short new one) costs no try, as for invites. The body is read up to 16 KB, like sign-in's.
- **Reset links** (PT-177, `auth/passwordResets.ts`, `auth/resetPassword.ts`, `http/routes/passwordResets.ts`). A forgotten password, or one that leaked, is answered by the owner with a reset link for that account (Account, People, Reset link). It is an invite for an account that exists, so it lives in the `invites` table with `kind` `reset` and the account in `user_id` (migration 0012), and shares the invite's code (`auth/links.ts`: 256 random bits, the SHA-256 kept, the link holding it after `#` as `/reset-password#<secret>`, `resetPageUrl`; used once by a conditional update). A lookup asks for its kind, so an invite link never resets a password and a reset link never makes an account; 0012's down() deletes reset links, which would otherwise work as invites. Only the owner, signed in with the password, lists invited accounts (`GET /api/users`, with when an open reset link stops working) and makes or cancels a link (`POST` and `DELETE /api/users/:id/reset-link`); another account, a token or a tracker without an owner gets 403, and the owner's own account or an unknown one gets 404 (the owner changes theirs in the app or with owner-set). An account has at most one open link: a new one replaces the last, so only the link sent last works, and a partial unique index on `user_id` for unused reset links keeps it so when two are made at once on Postgres (the second gets `409`). A link works for 24 hours (`RESET_TTL_MS`): the owner sends it while the person waits to get back in, and one that leaks is good for a day at most. `POST /api/password-resets/check { secret }` answers the account's email and `expiresAt`, and `POST /api/password-resets/use { secret, password }` sets the password (same rule as above) and ends every session of that account, in one transaction with using the link; three uses at once set it once. A used, expired or unknown link gets 404 with what to do ("This reset link was already used. Sign in, or ask the owner for a new one.", "This reset link has expired. Ask the owner for a new one.", "This reset link does not work. Ask the owner for a new one."). Using it does not sign in: the browser may be someone else's, like the owner's trying the link, and signing in with the new password lets a password manager save it. API tokens stay, as for a change; since a reset is often for a leaked password, the Password set page and the People note say to check Connect for tokens the person doesn't recognize. Both public routes read at most 16 KB and have their own limit per address with sign-in's numbers (`limitTries`, counted apart from sign-in's and the invites'), after validation, so a short password costs no try. The web page (`app/ResetScreen.tsx`) works signed in or not, checks the link once, and ends on "Password set" with Go to sign in. Removing an account is left out on purpose (PT-177): what happens to its projects, runs and tokens needs its own decision, so for now it stays a database task.
- **Whose projects.** `projects.owner_id` is the user a project belongs to; migration 0011 gave every existing project to the owner. A request's user is its scope (`auth/scope.ts`: the session's or token's user, null on a tracker without an owner, whose projects have none). Services for project data take a `UserContext` (the service context with the scope, `services/context.ts`, built in each route with `userContext`); run and chat services already took the scope. One place decides what a request reaches: `services/lookups.ts` finds a project by key or id, a ticket by key or id, a status, an activity item and an attachment only through a project the scope owns, else 404 with the not-found message, never 403, so nobody learns anything about another user's project. A file on no ticket yet (a pending upload) is its uploader's (`attachments.user_id`), to read and to attach (`linkAttachments`). Lists filter in the query (`ownedBy` in `repositories/projects.ts`): projects, statuses and tickets across projects (search, Ready), people, project counts and a helper's projects. Keys stay unique across users (SQLite can't drop the column's unique constraint without rebuilding a table others reference): a new project takes the next free key (MOB2 when MOB is taken), which shows only that the key is taken: not the project's name, owner, tickets or count. A repeated create that names another user's file leaves it out as gone, so its answer doesn't confirm the id (`reachableAttachmentIds`, `test/regression/repeat-create-other-users-file`). Live updates go only to their own user: a change notice carries the user whose project changed (`events/changeNotice.ts`, like run notices), and a stream sends only its own user's (`http/routes/events.ts`). `test/integration/userIsolation` checks every route by session and token on SQLite and PGlite, `invites` the invites.
- **Live-update streams** check their access again before each event and each ping (`http/routes/events.ts`, `auth/accessCheck.ts`): a stream whose session ended (signed out, everywhere, expired) or whose token was revoked gets nothing more and closes, and so does an open one once an owner is set up.
- **Body size:** checked after access, so only sign-in reads a body from someone not signed in: at most 16 KB there, 1 MB for every other JSON body (a body whose length says more is refused unread; one without a length is read only up to the limit), `413 too_large`. Uploads keep their limits per kind (§1.4).
- `TRACKER_TOKEN` on the server is no longer a password; the server says so at start when it is still set, and keeps a server without an owner closed.

- **Reaching an online tracker** (PT-125). Flags (`--url`, `--token`) win, then env (`TRACKER_URL`, `TRACKER_API_TOKEN`, `TRACKER_TOKEN`), then a saved config file, then `http://localhost:4100` (`config.ts`). `tracker login [--url URL]` reads the token hidden from the terminal (or the first line of a pipe), checks it with `GET /api/session` and saves it in `~/.config/project-tracker/config.json` (`XDG_CONFIG_HOME`, or `TRACKER_CONFIG` for another path) with mode 0600 in a 0700 folder, written to a temp file and renamed (`configFile.ts`); each save tightens a `project-tracker` folder made earlier with wider permissions (not a folder `TRACKER_CONFIG` shares with other files, like the home folder; PT-132); `tracker logout` forgets it. The file keeps a token per tracker URL (normalized: lower-case host, no trailing slash) and the last tracker logged in to as the default, so a token is only ever sent to the tracker it was saved for (`savedConfig.ts`). A token only travels over https, or plain http to this computer (`localhost`, `127.x.x.x`, `[::1]`; not `*.localhost`, which some Linux resolvers send to DNS, PT-138): `login` refuses an `http://` address of another computer before it asks for the token, and the CLI and MCP server refuse to run with a token for one (`plainHttp.ts`, PT-132). Refused rather than warned about: the MCP server's warnings go to a log nobody reads, and the http address of an https tracker (Railway) redirects, which drops the token, so it could not work anyway. A tracker on another computer without https is reached through an SSH tunnel to `localhost`. A file rather than env alone: the CLI (Claude Code's Bash calls, the desktop app) and the MCP server read one place without exports, and the token stays out of shell history, dotfiles and `~/.claude.json`. `login` refuses `--token`, which would land in shell history. A new name, `TRACKER_API_TOKEN`, because the server warns at start when `TRACKER_TOKEN` is set. Errors (`errors.ts`): a `401` replaces the server's sign-in text with the tracker's URL and either "needs an API token" or which token it refused (`--token`, `TRACKER_API_TOKEN`, `TRACKER_TOKEN`, the saved one) and where its replacement goes; the tracker's own JSON errors (a `403` like "Only a person can move tickets to Done.") pass through; a bare `403`/`404` (another server at that URL), `5xx` (restarting), `429`, a non-JSON answer and a network failure name the URL. Nothing prints the token; the MCP server's start line says only where its token came from.
- **Connect sheet** (`features/connect`, PT-125): the tracker's address (`/api/meta`'s `serverUrl`, or the page's origin when it names the same host, since behind Railway's TLS proxy the server sees http; a plain-http address of another computer, like `http://192.168.1.20:4100` with `HOST=0.0.0.0`, becomes `http://localhost` on the same port, which the CLI accepts and which works on the tracker's own computer, and the row says agents elsewhere need its https address, `agentAddress.ts`, PT-138), then on a tracker that signs its owner in the **API tokens** list (name, hint, created, last used) with **Revoke** (an inline confirm; for 500 ms after Revoke is pressed the sheet holds a pointer's presses, `holdPresses`, so a double tap's second tap can't revoke) and a name field with **Create token**, whose secret shows once in a card with **Copy token** and "You won't see this token again" until **Done** or the sheet closes; an open tracker says it needs no token. The card scrolls into view (`block: 'nearest'`, instant with reduced motion), since on a phone it opens below the fold. The secret lives only in the create mutation, which has `gcTime: 0`, so Done (`reset()`) or the sheet closing drops it from memory (PT-132). The setup steps follow: build, `login --url` (only with sign-in) and `claude mcp add`, with absolute paths from `/api/meta` for a tracker on this computer (loopback address) and `"$(pwd)/apps/agent/dist/mcp.js"` run in the person's own checkout for one elsewhere, whose paths are the server's. Hooks in `api/hooks/apiTokens.ts` (not in the `api` barrel, like the meta hook); `API_TOKEN_NAME_MAX` moved to `@tracker/shared`'s `domain/apiToken.ts` so the web reads it without zod. On a desktop the sheet is the `wide` size (PT-183): up to 980px wide, 5vh from the top and at most 90vh tall, so the header with Close stays put and only the body scrolls (`overlays/Sheet.module.css`); where its body is 840px or wider the overview, address and tokens sit in a 340px column beside the commands (`Columns.tsx`, a container query), each command stays on one line in a grey box that scrolls sideways with a fade at its edge (its focus ring is on the box, which the fade can't clip), the tracker's address wraps instead (a Railway address doesn't fit the narrow column), and the setup commands carry their step numbers. A wide desktop sheet's body is focusable (`tabIndex={-1}`) and takes first focus instead of the panel, so Page Down and the arrow keys scroll it at once (`SheetPanel.tsx`). Phones keep the single column and wrapped commands.
- `move_ticket` uses `PATCH /tickets/:key { statusId }` (top of the new group). In agent-facing text the person is called "User".
- The tools take as much text as the API, from the limits in `@tracker/shared` (`TICKET_TITLE_MAX`, `TICKET_DESCRIPTION_MAX`, `TICKET_ASSIGNEE_MAX`, `COMMENT_TEXT_MAX`, `REPORT_TEXT_MAX` for a report's summary, files and next steps and a review's summary, and `TICKET_SEARCH_MAX` for `list_tickets`' query, the API's `q`), so too long a text fails before it is sent; `test/tools/limits.test.ts` checks each tool field against the API's schema.
- **Attaching files** (PT-191, `tools/attachFile.ts`, `files/`): `attach_file { ticket, paths, comment? }` and `tracker attach KEY FILE… [--comment TEXT]` upload local files with `TrackerClient.uploadAttachment`, one at a time in the order given: to the ticket (under the description), or with a comment as pending files named in a new comment. The type comes from the name and the shared rules decide (`checkAttachment`), before anything is read. Only files in the current folder or a temp folder (`tmpdir()`, and `/tmp`, which on a Mac is another folder and where Claude Code keeps its scratch files) can go, compared by real path on both sides (`allowedRealPath`), so a symlink or `..` leading out is refused: text in a ticket could otherwise make Claude send `~/.ssh` away. Every file is checked before any is sent, so a refused one leaves the ticket as it was. The reply format of the prompt (§1.3), which ticket runs use too, has an `OUTPUT:` line for them.
- **Attachments:** `get_ticket`, `claim_ticket`, `claim_next_ticket` and `tracker show` list a ticket's attachments under the description and each comment's in its card. Images keep their line (name, size, dimensions), and the MCP tools return up to 4 as image content (PNG, JPEG, GIF, WebP up to 1.5 MB). Text files are shown inline in a code fence (`TrackerClient.fetchAttachmentText`), up to 20,000 characters each, ending on a whole line when one is near, and 40,000 in all (Claude Code caps a tool result at about 25,000 tokens); a cut file gets a note with its download URL. Videos, PDFs and text files left out are one line with name, type, size and the download URL (`attachmentFileUrl`, based on `TRACKER_URL`). When the agent sends an API token and a link is shown, the text ends with a note that downloads need it as `Authorization: Bearer`.
- **`tracker watch [PROJECT]`** (PT-140, `src/watch/`, `cli/watchCommand.ts`): the helper of §1.11, one job per file. `watch.ts` locks the folder (`folderLock.ts`: a file named after the folder beside the config, holding the process id; a second helper there is refused, a dead one's lock is taken over), since two helpers in one folder would run two Claudes in one tree. `setup.ts` loads the config, checks `claude --version`, works out the project (the argument, else the one project whose `repo` is this folder, both paths resolved with `realpath`), and checks in. A tracker that can't be reached at start is waited for, as after a login before the network is up. Its id is a UUID made once per tracker and folder and kept in the config (`identity.ts`), so a new network, address or token keeps it and runs queued meanwhile find it; its name is the Mac's Sharing name (`scutil --get ComputerName`; `os.hostname()` can be the network address), else the host name, or `--name`. It checks in every 20 s and asks for runs then; it also follows `GET /events` for `run` events (`liveStream.ts`: its own SSE reader at the client's `eventsUrl()`, reopened after `LIVE_STALE_MS` of silence, 1 s doubling to 15 s) and asks for runs each time the stream opens, so a run queued while it was down still starts. `runLoop.ts` takes one run at a time in each of two lanes, `ticket` and `ask` (`lanes.ts`; an `ask` run of §1.12 goes through `ask/`: read-only flags, its answer read from the stream's result and sent back, no report hand-back; the window names it `chat <first 8 of its id>`): the prompt goes to `claude -p --output-format stream-json --verbose` on stdin in the folder (`claude.ts`), never as an argument, so text can't become a flag; `--permission-mode` is the only other flag from the person's command line, and the prompt tool's `--mcp-config` and `--permission-prompt-tool` the only ones the helper adds, for a ticket run and an Edit question, which also gets `--permission-mode default` when the person gave none (§1.11, Claude asks and waits; an Ask or Plan question gets the read-only flags of §1.12 instead). stdout is read a whole line at a time (`stream/jsonLines.ts`; a chunk can end mid-line, and a line that is no JSON is shown as text), each event goes to the steps (§1.11 live steps), and the window shows what `claude -p` showed before: stderr and the result's text, never raw JSON. A ticket outside its project is refused without starting Claude (`refusal.ts`), and so is a run taken while stopping (reported cancelled). Exit 0 is done, a cancel is cancelled, anything else failed with why it ended and Claude's words (`outcome.ts`). A ticket run, like a question, ends as its last turn's `result` event says (`finalResult` in `stream/claudeResult.ts`, the one place to read that event): a failed last turn fails the run even after exit 0, and the failure text is that result's own, such as "Reached maximum number of turns (2)", not the tail of the window, which held the report printed before it (`failureOf`, shared with `askOutcome`, PT-196); with no failed result the window's tail stays, since stderr is all a Claude Code that could not start prints. The end is reported until the tracker answers (`retry.ts`), since asking for the next run ends one it still has. A `cancelled` event for its run, or a cancelled run found at a check-in, stops Claude. Ctrl-C, SIGTERM and closing the terminal stop Claude and report the run cancelled (output to a closed terminal is dropped, `cli/terminal.ts`); a second signal of any kind quits at once, and while a run's end is still unreported it says so. A lost tracker is logged once, in `describeError`'s words, and again when it is back. Check-ins and each lane report their problems apart (`problems.ts`): a problem is logged once whichever reports it, and the tracker is back only when none has one, so one lane's empty take no longer said it was back while the other lane still failed (PT-158, `test/regression/lane-problems-apart`). **Before it watches** (PT-155, `watch/mcp/`), `setUp` checks that Claude Code can start the `tracker` MCP server: `claude mcp list` in the folder, which starts every server to see whether it answers, read by `parseMcpList` (`<name>: <command or url> - <state>`, a name with spaces or colons and a command with dashes in it). A `tracker` server that doesn't answer, or none at all, refuses the runs with one line naming the command behind it and how to fix it; a list it can't read (an older Claude Code, a changed format) only says so and carries on, so a helper that works is never stopped by the check. Claude Code with no tracker tools can claim, comment and submit nothing: it did the work, printed its report and left the ticket empty and in To do, and the run still ended as finished (AWP-3, a user-scope MCP pointing at a file that no longer existed). **A work run that ends other than cancelled hands its report back** (a review run never does, §1.11): the helper takes the last `TICKET: <key>` block of the last result that has one (`reportBlockFor` in shared, which leaves the working notes before it out, on each result on its own: a block runs to the end of its text, so a later turn's words would join the report) and sends it to `POST /api/reports/apply` the way **Paste report** does (`watch/report/handBack.ts`), so the report and its status change land even when Claude had no tools. It first reads the ticket and sends nothing when a `report` entry has appeared since the run was taken (`submit_for_review` and Paste report both leave one), so a ticket never gets the report twice. A cancelled run was stopped part way, so what it printed is not a report. **While a run goes on**, every 30 s the window gets “Still working on MOB-1… (2m)” (`watch/stillWorking.ts`): the window shows Claude's words only when it finishes, so it looked dead for the whole run and a long run looked like a stuck one. Tests: `apps/agent/test/watch/` (the MCP list and its check, the sign of life, the hand-back, the stream's lines and result, the step batcher; real Claude Code 2.1.296 stream-json runs, trimmed and with a neutral folder, in `packages/shared/test/fixtures/stream-json/` for `createStepReader`: refusals by a hook and by the person, AskUserQuestion, a foreground sub agent and a background one with two results, a ticket run that reads, edits, runs `npm test` and prints its report, and one stopped by `--max-turns`; `test/watch/stream/recordedRuns` replays the last two through `runClaude` with their exit codes, for the steps, the outcome and the hand-back), `test/regression/` (two watchers in one folder, the id, reporting until answered, stopping during a take, output line breaks, the report of a run whose Claude had no tracker tools), and `apps/server/test/integration/trackerWatch` (the real server with the watcher and a fake `claude` through a connection it cuts: a printed report that moves the ticket to Need review; steps that reach `GET /runs/:id/steps` while Claude still works; and the whole command: project from the folder, `claude` from PATH, Ctrl-C cancelling, and a broken `tracker` MCP server refusing to watch; and a fake `claude` that starts the real prompt tool from `--mcp-config` and calls it: an Edit question that waits and goes on once the person allows, a question that gets the person's choice, a ticket run that goes on without a denied step, and a stopped run whose request ends).
- **Starting by itself** (PT-143, `src/watch/autostart/`, macOS): `tracker watch --install` refuses a token from an environment variable or `--token` (the job won't have it, and while it is set it wins over the saved one) and a folder where a helper other than the installed job already runs, then runs the normal setup (so a bad project, a refused token or a missing `claude` fails there), then writes a LaunchAgent named after the folder (`names.ts`) and loads it with `/bin/launchctl bootstrap gui/<uid>` (booted out first when `launchctl print` finds it loaded, since the code for "not loaded" differs between macOS versions; a failed bootstrap removes the plist). The job (`job.ts`) runs `/usr/bin/env node`, this CLI's loader flags and script, and `watch --url=<url>` with the same `--as`, `--name`, `--permission-mode` and `--no-keep-awake`, each as one `--option=value` argument so a value starting with `-` stays a value, then the project key, which is refused unless it is letters and digits since it can come from the tracker's list; `env` so a node upgrade that moves node's folder doesn't break it. It runs in the folder with the install's `PATH` (launchd's lacks `~/.local/bin`, where `claude` lives) and `TRACKER_CONFIG` set to the config file itself, so the job finds the token, its id and its lock as the terminal does. `RunAtLoad`, and `KeepAlive` only after an unsuccessful exit, since a helper that stops cleanly was stopped on purpose (logout sends SIGTERM); `ThrottleInterval` 120 s, so a problem that won't fix itself logs every two minutes; output to `~/Library/Logs/<label>.log`; the running helper puts the time on every line, errors included, when not in a terminal. Install warns when the folder or the CLI script is in Documents, Desktop or Downloads: started at login, node needs its own Files and Folders permission there, lost on a node upgrade. `--uninstall` boots it out (an error other than "not loaded" stops it) and deletes the plist; `--check` says whether it is installed, whether launchd runs it or its last exit code and log, and how the tracker named in the plist last saw this folder's helper (the plist is read only when installed); both take no project or options. While it runs, `caffeinate -i -w <pid>` keeps the Mac from idle sleep and ends with it (`keepAwake.ts`; `--no-keep-awake` turns it off).
