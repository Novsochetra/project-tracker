# Architecture

This document records the product changes from `init-design/SPEC.md` and the technical design. When it disagrees with the SPEC, this document wins. Everything the SPEC says that is not changed here still applies.

## 1. Product changes from the SPEC

### 1.1 Statuses are data, per project

- Each project owns its statuses. New projects get five defaults (`DEFAULT_STATUSES` in `packages/shared/src/domain/status.ts`):

  | Name        | Category      | Color     | Glyph                                            |
  | ----------- | ------------- | --------- | ------------------------------------------------ |
  | To do       | `todo`        | `#8E8E99` | empty ring                                       |
  | In progress | `in_progress` | `#C26A06` | ring + half pie                                  |
  | Need review | `in_review`   | `#0B68CB` | ring + three-quarter pie                         |
  | Reviewed    | `reviewed`    | `#18794E` | ring + full pie                                  |
  | Done        | `done`        | `#5B5BD6` | filled circle + check (SPEC glyph and animation) |

- The **category** gives a status its meaning and glyph shape; the **color** is the glyph color. Users can create, rename, recolor, recategorize, reorder and delete statuses. Names are unique per project (case-insensitive). A project keeps at least one status. Deleting a status that has tickets requires a target status; those tickets move to the end of the target group.
- Glyph shapes stay distinguishable without color: 0, 1/2, 3/4, full pie, check.
- `resolveStatus(statuses, category)` (shared) finds the status to use for a workflow step, with fallbacks when a category is missing.
- **Done** means category `done`. Progress %, open counts and overdue all use the category.
- Groups on the Project screen follow status order (position). Keyboard and drag moves cross groups in that order.
- The Project screen's filter is **All** plus one tab per status, in status order (§1.7).

### 1.2 The agent workflow

```
To do ──claim──▶ In progress ──submit──▶ Need review ──review: approved──▶ Reviewed ──person──▶ Done
   ▲                                          │
   └────────────── review: changes requested ─┘
```

- **Worker agent:** finds work with `claim_next_ticket` (category `todo`, ordered High → Low priority, then manual order, then number), works, comments as it goes, then `submit_for_review` with a summary, files and next steps. Submitting stores a report card and moves the ticket to the `in_review` status.
- **Reviewer agent:** lists `in_review` tickets, checks the work against the title, description and comments, then `review_ticket` with a verdict (`approved` / `changes_requested`), a 1–5 rating and a summary. Approved moves the ticket to `reviewed`; changes requested moves it to the top of `todo` so a worker picks it up next.
- **Agents can never move a ticket to a `done` status** (API returns 403). Only a person does that.
- Activity has an **actor**: `{ kind: 'human' | 'agent', name }`. People show as "You"; agents show by name with the terminal tile. Requests set the actor with `x-actor-kind` / `x-actor-name` headers (name URI-encoded). No header means the person.
- New activity type **review** renders as a card with the verdict, star rating and summary.
- A report whose text is TICKET / STATUS / SUMMARY / FILES / NEXT fields (a submission, or a pasted Claude Code report, Markdown marks allowed) renders as labeled sections instead of the raw mono block (`features/ticket/activity/reportSections.ts`): a status line ("Submitted for review" when the STATUS words mean done, otherwise "Status: …" as written), Summary in body text, Next on a highlighted panel, then Files one per line in mono. A file list written over several lines keeps each line whole; a list on one line is split on commas outside brackets, so "src/a.ts (parser, tests)" stays one file. More than 6 files show the first 5 and a "Show N more" text button (§7.3's rule, 44px target, `aria-expanded`, "Show less" when open; `ReportFiles.tsx`). Next and Files are left out when they say "none", also with Markdown marks around it ("**none**"). Submissions write labels in capitals, so when a field has a capital label, a line in another case that starts with the same word ("Next: …" or "Status: …" in a summary) is text of the field above it. Text before the first field, a field given twice or no SUMMARY keeps the raw text.
- Comments can be edited (sets `editedAt`, shows "edited") and deleted. Reports and reviews can be deleted. Events cannot be edited or deleted.

### 1.3 The copy/paste loop still exists

"Send to Claude Code" and "Paste report" work as in the SPEC, for agents without the MCP tools:

- Prompts are built on the server (`GET /api/tickets/:key/prompt`, `GET /api/projects/:key/prompt`) with the shared builders. Status labels use the status names. The ticket block also shows the last review (`Last review: Changes requested · 2/5` + summary).
- "Open tickets" for the project prompt means categories `todo` and `in_progress`, ordered in-progress first, then priority, then number.
- The switch reads "Move MOB-3 to {in_progress status name}" and shows for tickets in a `todo` status.
- Report STATUS words map to categories (`normalizeReportStatus`): reviewed/approved/verified → `reviewed`; done/complete/fixed/finished/resolved and review words → `in_review`; not started → `todo`; progress/partial/blocked/wip/started/ongoing → `in_progress`; to do → `todo`. A report never sets Done.

### 1.4 Attachments

- Tickets (under the description) and comments can have attachments of four kinds. The text fields stay plain text. The rules live in `packages/shared/src/domain/attachment.ts` (`ATTACHMENT_TYPES`, `ATTACHMENT_KINDS`):

  | Kind    | Types (extensions)                              | Up to  |
  | ------- | ----------------------------------------------- | ------ |
  | `image` | PNG, JPEG (jpg, jpeg), GIF, WebP, HEIC, HEIF    | 15 MB  |
  | `video` | MP4, QuickTime (mov, as iPhones record), WebM   | 100 MB |
  | `text`  | Plain text (txt, log), Markdown (md), CSV, JSON | 5 MB   |
  | `pdf`   | PDF                                             | 25 MB  |

- No SVG or HTML: opened from the tracker's address they could run script.
- The type the browser gives decides. When it is empty, `application/octet-stream` (common for .log and .md), `application/vnd.ms-excel` (Windows, for .csv) or `text/x-markdown`, the extension decides (`resolveAttachmentType`). Other names systems give an allowed type count as it and the file keeps the allowed type (`text/x-log` as `text/plain`; `text/x-csv`, `application/csv` and `text/comma-separated-values` as `text/csv`; `image/jpg` as `image/jpeg`). Any other declared type is refused whatever the name. `checkAttachment(file)` gives the stored type and kind, or the message to show: one per kind from `tooLargeMessage` ("Videos can be up to 100 MB.") or `UNSUPPORTED_ATTACHMENT_MESSAGE`, which lists what can be attached. File inputs use `ATTACHMENT_ACCEPT` (every type and extension, because some systems give .log and .md no type), and `attachmentKind(mimeType)` tells how to show a stored attachment.
- **Adding files** (`features/attachments`): New ticket and the ticket screen (under the description), quick capture and the comment box take every kind: from **Add files** (in the comment box the paperclip **Attach files**), which on phones offers the photo library, the camera and Files (`ATTACHMENT_ACCEPT`); by paste into their text fields; and by drag and drop on desktop. `admitFiles` checks each file with the shared rules, and New ticket, quick capture and the comment box take up to 20 files (`MAX_NEW_ATTACHMENTS`), the ticket screen any number. What didn't go is said in the picker area (`FileNote`, `role="alert"`), not in a toast, which is gone after 2.2 s and cut to one line on a phone: "notes.svg can't be attached." (or "notes.svg and 2 more…") over the reasons, here the list of what can be attached, or "A new ticket can have up to 20 files."; and "clip.mov didn't upload." over why (`uploadFailureReason`: the bare 408 and 413 that Node and proxies send become "It took too long to send. Try again on a faster connection." and "The server won't take a file this big."). It stays until the next pick, a dismiss or a sent comment; uploads that fail while it is up join it. A ticket's upload that fails after its screen has closed is told in a toast. Photos are checked after the web app scales down those larger than 2048px and converts HEIC (`lib/uploads.ts`), which brings most large ones under the limit. Each file uploads at once and shows a progress ring on its tile (`TrackerClient.uploadAttachment` reports progress through XMLHttpRequest, which fetch can't; Node falls back to fetch) and an x that stops it. New ticket, quick capture and the comment box send their files' ids when they create; Create and Comment wait while a file is still uploading. Closing New ticket or quick capture without creating stops their uploads and deletes the uploaded files.
- Upload first (`POST /api/attachments`, multipart `file` + optional `ticketKey`); without `ticketKey` the attachment is pending until a ticket or comment is created with its id in `attachmentIds`, at most 20 (`tooManyFilesMessage`: "A new ticket can have up to 20 files.", "A comment can have up to 20 files."). Pending attachments older than 24 hours are deleted on startup. How files are stored and served: §3.
- **Tiles** (`ThumbnailGrid`), under the description and inside comment cards: images as before; videos show their first frame (a film icon until one is drawn, or when the browser can't play them) with a play badge and their length; text files and PDFs are wide tiles with an icon, the name and the size. A name too long for the one line of a small tile loses its middle, not its end ("crash-r…t-1.log", `splitFileName`), and its title shows it whole. Images and videos are named by number within their kind ("Open image 2", "Play video 1", "Remove video 1"), other files by name ("Open notes.txt"). Every x keeps the 44×44 target that never reaches a tile's middle (`test/regression/thumbnail-middle-never-removes`). An image the browser can't show (HEIC outside Safari) shows an icon, never a broken image.
- **Opening** (`AttachmentViewerProvider`, `viewerTarget`): images open the full-screen viewer (pinch and double-tap zoom, pan, swipe between the images, swipe down to close). Videos play in a full-screen viewer with the native controls (`overlays/VideoViewer`), scaled to fit the screen however small they were recorded, `playsinline` so iOS doesn't jump to full screen, starting at once where the browser allows it; swipe down or Close ends them, and the swipe takes only clearly downward drags, so taps and scrubbing reach the controls. Text files open in a sheet that reads the file and shows it monospaced and wrapped, scrolling, up to 100,000 characters ending on a whole line, then "Open the whole file" (a new tab); it swipes down to close like any sheet. PDFs open in a new tab.
- Agents get images as image content, text files inline and download links for the rest (§4).

### 1.5 Phone gestures and motion (Apple-like)

On phones (`max-width: 767px`) the app behaves like a native iOS app:

- **Navigation stack:** Projects → Project → Ticket screens stack. Push slides the new screen in from the right edge while the old one moves 30% left and dims; pop reverses. Desktop keeps the SPEC's 28px fade.
- **Edge swipe back:** dragging from the left edge pops interactively with a parallax underlay, and completes or cancels by distance and velocity with a spring. Disabled in iOS Safari browser mode, where Safari owns that gesture (enabled when installed to the home screen).
- **Sheets:** drag the grabber or sheet down to dismiss (follows the finger, rubber-bands upward, velocity-aware). Content scrolls inside; dragging down from the top of the content dismisses.
- **Unsaved changes:** a sheet with input never vanishes by accident. While `Sheet` gets `dirty`, a swipe-down past the threshold springs back, and a scrim tap or Escape (desktop too) leaves it open; an action sheet asks "Discard changes?" with "Discard changes" (Danger) and "Keep editing", which returns focus to the field. The header's `SheetCancelButton` asks the same on phones (iOS convention) and closes at once on desktop, where Cancel is a deliberate click. Create, Save and Apply close without asking, and a sheet without changes closes at once. These sheets set it: New ticket (any field off its default, or a file, including one still uploading), New project (text in any field), Edit project (a name, description or repository that differs from the project it opened with; when the project loads after the sheet opens, the loaded values are the start, not a change), Paste report (text in the box) and Statuses (an open status editor with a changed name, type or color). Quick capture sets it too (a title, description or file, including one still uploading).
- **Row swipe actions:** swipe a ticket row right to move it to the next status; swipe left to reveal "Status" and "Delete". A full swipe triggers the first action. Haptic tick at the threshold where supported.
- **Pull to refresh** on Projects and Project lists.
- **Large title** on Projects collapses into the nav bar title while scrolling.
- **Nav bar layout:** the back button (at least 44×44) and the right buttons keep their size. The title takes the space left, ends in an ellipsis and stays centred while it fits. When the back label has no room for a few letters, only the chevron shows.
- **Tap the nav bar to scroll up:** a tap anywhere on the nav bar except its buttons (including the safe-area padding at its top) smooth-scrolls the screen's scroller to the top, and jumps there with reduced motion (`navigation/useTapToTop.ts`). Each screen scrolls in its own scroller, and iOS's status-bar tap only scrolls the document, so the nav bar takes over that job.
- **Bottom bar and the keyboard:** on touch phones the bottom bar slides away and is inert while a text field has focus, because the keyboard covers it anyway (`navigation/useEditingText.ts`). It comes back when the field loses focus, but not during a press: a tap whose mousedown takes focus out of the field, such as Comment or Save, keeps it away until the release, so the click lands on what was tapped. When it comes back, the screen scrolls the field that was edited, with its form (the comment box and its Comment button), to 8px above the bar on the next frame, once, so a scroll right after closing the keyboard stays where the user left it (`navigation/keepFieldInSight.ts`). Only a field that fits between the nav bar and the bar moves: a longer one, such as a long description, stays where it is, because bringing its end up would push the part just edited off the top. A sent form, such as the comment box after Comment, is kept at least 8px above the bar while what it sent lands above it (the new comment), also when the keyboard closed before the tap and when the new comment pushed it below the screen: each time the content around it changes size (`ResizeObserver`), for a second after the send (the new comment shows at once, before the tracker answers) and until the user touches or scrolls the screen. What lands later, such as an agent's report, pushes the box down like any other content. The bar hides with `translate`, which its entrance animation on `transform` can't override, so a field focused while the bar slides in still sends it away.
- Press feedback (scale .97), spring selections, `prefers-reduced-motion` honored everywhere.

### 1.6 Other additions

- Live updates: the server pushes change events over SSE; open screens refresh when an agent changes something. The web app reopens the stream when the browser gives up on it or when it stays silent for 35 s (two missed pings: a proxy can keep a dead stream open after the API server crashes), waiting 1 s, then doubling up to 15 s. After any reopen, including the first open after a failed connect, all cached data except session and meta refreshes; keys with pending edits and deleted keys are skipped. The ping interval and the silence window are `HEARTBEAT_MS` and `LIVE_STALE_MS` in `packages/shared` (`domain/liveUpdates.ts`), used by the server and the web app. A page hidden for 30 s closes its stream, so a phone's radio doesn't wake for every ping, and reopens it as soon as it is visible again, with the same refresh (`api/live/pauseWhileHidden.ts`); a quicker switch to another app keeps the stream. When the browser gives up on the stream, the app reads `GET /api/session` again, because EventSource hides the status and a 401 looks like a proxy's 502: when the server now needs a token, the token screen shows (which ends the retries); an unreachable server changes nothing.
- Project options menu adds **Manage statuses** and **Connect Claude Code** (MCP setup instructions with copy buttons).
- **Links:** http(s) URLs in comments, reports (raw text and every section) and review summaries are links that open in a new tab (`rel="noopener noreferrer"`), in the link color and wrapping anywhere. Punctuation after a URL stays out of it ("see https://x.dev/a." links `https://x.dev/a`), and a closing bracket only stays when the URL opened it. An apostrophe inside a URL stays (`…/The_Hitchhiker's_Guide…`). CJK punctuation ends a URL like a space, because CJK text has no spaces ("请看https://x.dev/a。谢谢" links `https://x.dev/a`), while CJK letters stay in it. The trimming is one pass from the end, so text of any allowed length (reports take 100,000 characters) splits in linear time; `test/regression/link-trim-long-text` keeps 100,000 trailing brackets or dots under 100 ms. The text is split into text and links (`apps/web/src/lib/linkify.ts`) and rendered as React nodes, so nothing else becomes markup. The description is always the editable field (§4.3), so its URLs stay plain text.
- **A render error stays small** (`lib/ErrorBoundary.tsx`, which logs what failed and the error to the console): an activity item that fails to render shows as a card with "Couldn't show this item", its text as plain text and its menu, so a comment can still be edited or deleted, and a report or review deleted (`features/ticket/activity/UnshownItem.tsx`). The latest review under the title has its own boundary, and its stand-in keeps **Delete review** and **Move to Done**. A stand-in tries the real card again once its activity changes, as when an Edit from it saves, but not while an edit is open in it: a comment's edit lives outside its boundary, shared by the card and its stand-in, so it carries over and focus goes back to the options button (`ActivityRow.tsx`, `CommentMenu.tsx`). Items are built so that one activity in a shape the app doesn't expect can't fail the others (`activityItems.ts`): an actor it can't read shows as "Someone" with an empty avatar, and a type it doesn't know (from a newer tracker) as "Couldn't show this item" with its text and no menu. Reports are read inside their card (`ReportBody`), so a report the reader trips on only takes down its own card.
- **A screen, the shell or a sheet that fails** shows a small fallback instead of a white page. A screen shows "Something went wrong" with **Back** (when it has a parent) and **Reload** in its place (`app/ScreenError.tsx`). Each screen's boundary sits inside its stack layer (`app/renderScreen.tsx`), so the stack, the sidebar and breadcrumb, and the edge swipe back keep working. On desktop the sidebar and the header have their own boundaries (`app/ShellError.tsx`), since they read the same projects answer as the screens: a sidebar that fails keeps its frame, **All projects** and "Couldn't show the projects", a header an empty bar, and both are tried again when the projects answer changes. A sheet that fails shows a small sheet with "Something went wrong", **Close** and **Reload** (`app/sheets/SheetError.tsx`); opening it again tries it afresh.
- Optional access token: when `TRACKER_TOKEN` is set, the API needs `Authorization: Bearer <token>` or the session cookie from `POST /api/session`. The web app shows a token screen once. After a sign-in it reads `GET /api/session` once more and ignores the answer, so the service worker replaces its saved signed-out copy and an offline start opens the app.
- Installable PWA (manifest, icons, offline app shell).
- **Saved answers:** the service worker reads `GET /api` network-first (3 s timeout; not `/api/events` or attachment files) and answers from its cache when the network fails, is too slow, or a proxy answers for a stopped API with a bare 5xx. It marks those answers with `x-tracker-saved` (`pwa/savedAnswerPlugin`), and a fetch wrapper (`pwa/savedAnswers`, installed by the shell) notes whether the latest answer was one. A read answered that way counts as the tracker being unreachable (`app/reachability`), so the banner says "Offline — showing saved data", and capture sync and draft retries don't start; writes are never cached. A fresh read (`x-tracker-fresh`, `{ fresh: true }` in `@tracker/client`) still goes through the service worker but is never answered from its cache: it waits for the tracker or fails, and its answer refreshes the cached copy. After a write to a ticket (any mutation that settles for it, `api/refresh.ts`) and after a change a live update reports for it (`api/live/refreshForChange.ts`; a saved copy can't hold the change that caused the update), `useTicket` reads that ticket fresh until one such read lands (`api/freshReads.ts`), so a copy saved before the change can't put the old text back on screen when reads are slower than the timeout, and saved answers after that read already have the change. When the fresh read gets no answer, a copy on screen stays; with no copy in memory (such as after a reload), the ticket is read as usual instead, and a saved copy beats nothing while the tracker can't be reached. The tickets still waiting for their fresh read are kept for the tab across a reload (`sessionStorage` `tracker.freshReads`, written on `pagehide`, taken over by the next page's first read), so a reload in the seconds after a save, which is also when an app update reloads, reads fresh too. Only the ticket screen reads this way: the board and lists read as usual, so while reads are slower than the timeout a list can show a title from before a write until its next refresh.
- **Attachment files** are read cache-first (`pwa/attachmentFileRoute.ts`): whole images, text files and PDFs stay for 30 days, 100 at most. A ranged read, which is how browsers play video, matches no route, so it goes to the network without the service worker in the way (iOS doesn't play video without real ranges), and videos never go in the cache (`attachmentCachePlugin`), where one could take 100 MB.
- App updates never lose typed text. While the app stays open it looks for a new build when the page becomes visible and every 30 minutes (skipped while offline). A new service worker takes over at once, but the page reloads into the new build only when no text field is focused, no dialog is open, there are no drafts (`hasDrafts()`) and no write is in flight, whether the page is visible or hidden. It checks again every second and on `visibilitychange` (`apps/web/src/pwa`). Writes in flight come from the QueryClient's mutation cache. A lazy chunk that fails to load (`vite:preloadError`: a page still on the old build asks for a file the new build replaced) reloads the page by the same rule (`pwa/reloadOnPreloadError.ts`); until then the failed import fails as usual. It reloads at most once a minute: the reload's time is kept in `sessionStorage` (`tracker.chunkReloadAt`), and a chunk that fails again within a minute of it only logs a warning and the page stays, because the file is then missing for another reason (a proxy, a broken deploy) and reloading again would loop. Without session storage it doesn't reload.
- **Draft contract** (`apps/web/src/lib/drafts.ts`): a feature that holds unsent text a reload would lose marks it with `useDraftMark(id, active)` (`lib/useDraftMark.ts`), `active` while the text differs from what is saved; the mark goes when `active` turns false (sent, saved or emptied) and when the component unmounts. Underneath are `markDraft(id)` and `clearDraft(id)`. Use one id per draft, such as `comment:MOB-3`. Marks are counted per id, so each `markDraft` needs its own `clearDraft`, and two mounted components that share an id keep the draft until both let go. Text in the ticket drafts store (next point) counts as a draft without a mark, until it is saved or dropped. While `hasDrafts()`, reloading or closing the page asks first (`beforeunload`; iOS doesn't show it). A draft that is never cleared keeps the page on the old build until the next launch. An open sheet needs no mark to hold an update, because the reload already waits while a dialog is open; quick capture marks `capture` only while it holds files (uploaded or on their way), which a reload loses, so that closing the page asks. The kept fields of New ticket and quick capture (below) are not a draft: `hasDrafts()` leaves them out, because the sheets open with them again after a reload.
- **Unsaved ticket text survives leaving the ticket and reloading.** Title, description, assignee, comment edits and the comment box keep typed text in a small store (`apps/web/src/lib/storedDrafts.ts`, `localStorage` `tracker.drafts`, in memory when storage fails) under their draft ids (`title:MOB-3`, `description:MOB-3`, `assignee:MOB-3`, `comment-edit:<comment id>`, `comment:MOB-3`), with the ticket key, the field, the server value the text was typed over and, for a comment edit, whether Save was pressed for it. An entry stays until the tracker has its text, also while a save is on its way, so leaving the ticket or reloading during a request loses nothing. The ticket opens again with that text. An entry goes once the server has its text, when the comment box is sent or emptied, when an edit is cancelled or emptied (a comment needs text, so an empty edit can't be saved), on **Use theirs**, and when its comment or ticket is deleted: by the user, or elsewhere, which the app-wide sync below finds out (it reads every ticket that isn't open and has kept text) and so does the ticket screen when it gets a 404 for its ticket. The comment box's text is never sent for the user, and neither is an edit nobody pressed Save for: it opens again in its editor as it was left, without a note and without taking focus, and only Save sends it, after the check below.
- **Unsent New ticket text survives a reload.** While the New ticket sheet is open with changes, its fields (title, description, status, priority, assignee, due date) and the files already uploaded are kept in the sheet drafts store (`apps/web/src/lib/sheetDrafts.ts`, `localStorage` `tracker.sheetDrafts`, in memory when storage fails; both stores use `lib/draftStorage.ts`) under `new-ticket:<project key>`. Opening New ticket for that project again, after a reload, a crash or iOS stopping the app, starts from them; a kept status that was deleted meanwhile gives way to the sheet's default and counts as no change (a sheet that looks untouched closes without asking, and its entry goes); kept files 23 hours old are left out, because the server deletes uploads nothing uses after a day (`keptAttachments`). Files still uploading can't come back, so while they go, closing or reloading the page asks first (the draft `new-ticket-files:<project key>`). The entry goes when the ticket is created, when the sheet closes any other way (Cancel, Discard changes) and when the fields are back to blank. It is `localStorage`, not `sessionStorage`, because a home-screen app that iOS stopped starts a new session.
- **Unsent quick capture text survives a reload** the same way, under `capture` (`features/capture/keptCapture.ts`): the title and description, with the priority and the project picked in the sheet (none while the default applies; a kept project that is gone gives way to the default). They are kept while the sheet is open with a title or description, and go when the capture is created or waits offline, when the sheet closes any other way and when the text is emptied. Its files are not kept: after a reload the capture opens with its text only, and its uploads wait on the server until they expire (§1.4).
- Failed saves keep the typed text. Title, description and assignee show "Title isn't saved yet." with **Retry** under the field; a comment edit whose Save failed keeps its editor open and shows "Your edit isn't saved yet." next to Save. Text kept from an earlier visit opens the same way. On a slow connection several saves of a field can be on their way, and the tracker ends with the latest one's text (`fields/fieldSaves.ts`). They are recorded per draft id, not in the field on screen, because the tracker may already have one of them without having answered it, which a check would take for someone else's change: the field opened again after leaving the ticket and the app-wide sync see them too. So leaving a field sends nothing more only when the latest save sent carries the text the field shows and is still on its way: that save settles the field. Other text is sent again, also text an older save still on its way carries (typing more, then deleting it). The kept text goes only when the latest save sent lands; an older one landing records what the tracker has for now, which a later check compares with. After a failure, typing no longer autosaves; a checked retry saves the text: Retry, leaving the field, opening the ticket again, and app-wide (`features/ticket/drafts/useTicketDrafts`, called once in `TrackerApp`) on start, on `online` and when a request gets an answer again after the tracker couldn't be reached, also for tickets that aren't open; while tickets that aren't open have kept text, also when the tracker reports a change (a live update refreshing the cache), which may be one of them deleted. Retries started by an answer or a change are at least 10 s apart, because a failed retry itself makes the tracker look unreachable and the refetch after it reachable again. Retry and leaving the field say "Can't reach the tracker" when it can't be reached. Retries the app starts on its own show no toast, also when their save fails, because the note already says the text isn't saved. A field runs one retry at a time and none while a save of it is on its way, also one sent before it opened; a comment edit runs one at a time and none while its own Save is on its way. A field opened while the latest save of its kept text is on its way shows that text without a note and checks nothing: once that save lands it follows the tracker, and if it fails the field says the text isn't saved yet and is retried as usual. The app-wide sync leaves the drafts of an open ticket to its screen, also while it loads, and a draft with a save on its way to that save (its own saves count the same way), so text kept from an earlier visit is sent once at start, and leaving a ticket while its saves are on their way brings no toast. A comment edit's Save sends it at once, unless the edit was kept from an earlier visit or a save of it failed: then Save first checks the comment like a retry (next), and says "Can't reach the tracker" when it can't, leaving the edit failed (`activity/commentEdit.ts`). Typing after Save starts a new edit, which waits for Save again. The retry first reads the ticket fresh (saved answers above), so the answer comes from the tracker, or the check fails and nothing is saved. If the ticket still has the value the text was typed over, the text is saved; if it already has the text, the draft is done. If someone else (an agent) changed it meanwhile, nothing is saved either way: the field keeps the text and says "Title changed elsewhere while yours wasn't saved." with **Save mine** and **Use theirs**, and a comment edit says "The comment changed elsewhere while your edit wasn't saved." (Save replaces it, Cancel keeps theirs). When that happens to a ticket that isn't open, a toast says "Your edit to MOB-3 isn't saved: it changed elsewhere." The app-wide sync goes ticket by ticket: no answer, a 401 or a 5xx ends the run and the rest wait for the next one, while a draft the tracker refuses otherwise (another 4xx) stays kept and the others go on.
- **Error toasts** (`components/Toast`): a toast is a success (the SPEC's circle-check) or an error, `show(text, { kind: 'error' })`: a circle-alert in `--danger-inverse` (#F97066, 6.2:1 on Ink, where Danger is 2.6:1), in the same status region with the same timing, so it is announced the same way. Every failure toast uses it; `test/regression/error-toast-icon` fails when a `show()` of `errorMessage(…)`, the network message, a dropped capture or an edit that changed elsewhere leaves the kind out.
- **Undo after a status move.** A status change from a row swipe (list and Ready for you), the Status action sheet, Ready for you's Done button, a drag or arrow-key move into another status (list and board), the ticket's Status dropdown (which had no toast before) and Move to Done shows "MOB-3 moved to Done" with **Undo** for 4 s (`DURATION.toastUndo`), instead of 2.2 s. Undo says "MOB-3 moved to Reviewed", flashes the row and puts the ticket back with the move API (`features/project/undo`): above the ticket that was below it, else below the one that was above it, else where its old rank sorts, read from the project's tickets as they are when Undo is pressed (cached, or fetched), so live updates meanwhile count. It waits for the move to be saved: a refused move is already back and needs nothing, and a move-back sent sooner could reach the tracker first. A move-back that fails (offline) shows the error toast and the ticket stays moved. In Ready for you the ticket comes back at the top, since that list is ordered by last update. Reorders within a status have no toast and no Undo, as before.
  - The button: "Undo" in `--accent-inverse` (#A3A3F2, 7.4:1 on Ink), a 44×44 target beside the toast's last line that reaches past a one-line toast's 41px instead of making it taller, with hover and focus drawn as a pill inside the toast. The toast comes last in the tab order, so ⌘Z or Ctrl+Z (`aria-keyshortcuts`) runs Undo from anywhere except a text field, which keeps it for its own typing. While the toast is hovered or has focus it stays, and gets its 4 s again after; Undo pressed from the keyboard sends focus back where it came from. When focus is then on the moved ticket's row or handle (or ⌘Z was pressed there), it goes along to the ticket's handle in its old group, in the list and on the board: the row there is a new element, and focus on the old one fell to the page (`rowHasFocus` and `requestHandleFocus` in `dnd/handleFocus.ts`). Undo runs once, and for 500 ms the toast's band catches taps (`TOAST_SHIELD_MS`), so the second tap of a double tap doesn't open the row below. Toasts without Undo let taps through as before. Reduced motion uses the global rule.

### 1.9 Quick capture

- **Entry points:** on phones a bottom bar on Projects with a primary "New ticket" (instead of a floating +); on desktop "New ticket" in the Projects title row and the shortcut **C** anywhere no text field, sheet or menu has the keyboard; the PWA manifest shortcut "New ticket" opens `/?capture`, which opens the sheet and then drops the parameter. C does nothing while a modal (`aria-modal`), a dropdown (`listbox`), a `menu` or a popover menu's invisible "Close menu" layer is in the page: popover menus keep focus on their trigger, and their layer would take the next click.
- **Sheet** (`{ type: 'capture' }`, `features/capture`): title focused on open (phones too), optional description and files, Project (the last one used, `tracker.capture.project`, else the most recently active) and Priority (Medium). No status is sent, so the server uses the project's first status. Create shows "MOB-7 created" and stays on the current screen. Typed text survives a reload (§1.6); files make it the draft `capture`. A title, description or file makes the sheet `dirty` (§1.5), so a swipe-down, scrim tap, Escape, click outside or a phone's Cancel asks "Discard changes?"; Create closes without asking.
- **Offline:** when the tracker can't be reached, or hasn't answered within 8 s, a text-only capture waits in `tracker.capture.queue` (localStorage) with a client id, and Projects shows "N waiting to sync". A capture with files stays in the sheet instead ("Files need a connection…"), because they only live on the server.
- **Sync:** on start, when `app/reachability` turns reachable, on `online` and when the page becomes visible; one run at a time (across tabs too where there are Web Locks), oldest first, one request at a time, then "N tickets added". Created ids are skipped. Network, 401 and 5xx failures stop the run and keep the rest; a capture the create refuses for good (another 4xx, such as its project being deleted) is dropped with the one-line toast "Couldn't add “…”", the title clipped to 24 characters so it fits at 375px. Sends go through the mutation cache (writes in flight, reachability) and refetch nothing on failure.
- **One ticket per capture:** every create for a capture, the sheet's and each sync's, carries the capture's client id (`clientId`, §3), and the tracker answers a repeat with the ticket the first one made. So a capture is sent again without looking anything up, and still makes one ticket: after a lost answer, when its tab closed mid-request, or when two tabs send it at once.
- **Fewer requests across tabs:** while a request for a capture is out (the sheet's, which keeps going after the 8 s save, or a sync's), its tab holds the Web Lock `tracker-capture-send:<id>`. A sync skips a capture it can't lock, reads it again once it holds the lock, and lets go only after the result is recorded. Web Locks need a secure context, so a phone on a plain http address keeps a lease time in `localStorage` `tracker.capture.sending.<id>` instead, renewed every 20 s and void a minute after the last renewal. That lease is not atomic: Chromium shows a tab another tab's writes a moment late, so two tabs coming back online together can both send a capture. The locks only spare requests (and a second "1 ticket added"); the client id is what keeps it one ticket.

## 3. HTTP API

All routes are under `/api`, JSON in and out. Errors: `{ "error": { "code", "message" } }` with codes `invalid_input` (400), `unauthorized` (401), `forbidden` (403), `not_found` (404), `conflict` (409), `no_match` (422). `packages/client/src/client.ts` is the reference for every route and its types.

| Method & path                                                               | Does                                                                                                                     |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `GET /projects`                                                             | Project summaries in creation order (counts, `lastActivityAt`)                                                           |
| `POST /projects`                                                            | Create (prefix: `resolvePrefix` + `uniquePrefix`; color `PROJECT_COLORS[count % 6]`; default statuses) → `ProjectDetail` |
| `GET/PATCH/DELETE /projects/:key`                                           | Read / edit name, description, repo / delete with everything in it                                                       |
| `GET /projects/:key/board`                                                  | Project, statuses, ticket list items                                                                                     |
| `GET /projects/:key/prompt`                                                 | Project prompt and open ticket count                                                                                     |
| `GET /projects/:key/tickets?status=&category=&q=`                           | Filtered tickets (status by name, case-insensitive)                                                                      |
| `GET /tickets?status=&category=&q=`                                         | The same filters across every project, most recently updated first, with the statuses of their projects                  |
| `POST /projects/:key/tickets`                                               | Create ticket (top of its group, "created the ticket"); a repeated `clientId` gets the first one (below)                 |
| `POST /projects/:key/statuses`, `PUT /projects/:key/statuses/order`         | Create status / reorder                                                                                                  |
| `PATCH /statuses/:id`, `DELETE /statuses/:id?moveTo=`                       | Edit / delete status                                                                                                     |
| `GET/PATCH/DELETE /tickets/:key`                                            | Ticket detail / edit fields (events per SPEC §6.2) / delete                                                              |
| `POST /tickets/:key/move`                                                   | Drag or keyboard move (`planMove`)                                                                                       |
| `GET /tickets/:key/prompt`, `POST /tickets/:key/sent`                       | Ticket prompt / mark as sent                                                                                             |

| `POST /attachments`, `GET /attachments/:id/file`, `DELETE /attachments/:id` | Upload / serve / delete files (below)                                                                                    |

Status changes made by the dropdown, a report, sending, claiming, submitting or reviewing put the ticket at the **top** of its new group (`topRank`). Drags and keyboard moves renumber the destination group (`planMove`).

**Client ids.** `POST /projects/:key/tickets` takes an optional `clientId` (1–64 characters) from a client that may send the same create again (quick capture, §1.9). The ticket keeps it, unique per project. A create that repeats it answers 201 with the ticket the first one made, as it is now, whatever the rest of the body says, and changes or logs nothing. It is looked up in the create's transaction, so two identical creates at once give one ticket, one number and the same answer. On Postgres with several connections both can miss it; the unique index then refuses the second once the first has committed (`23505`; SQLite's `SQLITE_CONSTRAINT_UNIQUE` is caught too), and the second, rolled back with its number, runs again like a later repeat. SQLite and PGlite run one transaction at a time, so `test/regression/client-id-race` makes the lookup miss to show it.

**Attachment files.** `POST /attachments` checks the file with `checkAttachment` (§1.4), so each kind has its own limit; the route itself refuses a body over the largest limit plus 64 KB of form overhead ("Files can be up to 100 MB.") before reading it. The server gives a request an hour (`requestTimeout` in `main.ts`; Node's default of five minutes answered 408 to a 100 MB video sent slower than 2.8 Mbit/s), so the largest file arrives over a 240 kbit/s uplink; headers keep Node's one minute. Files are stored as `<id>.<extension of the type>` (`FileStorage`: disk, or memory in tests), images keep their dimensions, and names are cut to 200 characters without splitting one (`attachment.<ext>` when there is none). `GET /attachments/:id/file`:

- Always `Accept-Ranges: bytes`. One range (`bytes=a-b`, `bytes=a-` or `bytes=-n`) answers 206 with `Content-Range` and reads only those bytes from storage (`FileStorage.read(key, range)`; disk storage streams them). iOS Safari doesn't play video without this. A range that starts past the end (or `bytes=-0`) answers 416 with `Content-Range: bytes */size`; several ranges or a malformed one get the whole file (200). HEAD answers the headers of the whole file and ignores `Range`.
- `Content-Disposition: inline; filename="…"; filename*=UTF-8''…` (RFC 5987, with an ASCII fallback), so downloads keep their names. `X-Content-Type-Options: nosniff` and `Cache-Control: private, max-age=31536000, immutable` on every answer with the file.
- Text kinds are served with `; charset=utf-8` and `Content-Security-Policy: sandbox` (defense in depth). Not PDFs: Chrome won't show a sandboxed PDF.

## 4. Agent integration (`apps/agent`)

- **MCP server** (`tracker-mcp`, stdio): tools `list_projects`, `list_statuses`, `list_tickets`, `get_ticket`, `create_ticket`, `update_ticket`, `move_ticket`, `add_comment`, `claim_next_ticket`, `claim_ticket`, `submit_for_review`, `review_ticket`; prompts `work` and `review` that appear as slash commands in Claude Code. Config by env: `TRACKER_URL`, `TRACKER_TOKEN`, `TRACKER_AGENT_NAME`.
- **CLI** (`tracker`): the same operations for shells and agents without MCP.
- Register with Claude Code for every project: `claude mcp add tracker -s user --env TRACKER_URL=http://localhost:4100 --env TRACKER_AGENT_NAME=Claude -- node <repo>/apps/agent/dist/mcp.js`.
- `move_ticket` uses `PATCH /tickets/:key { statusId }` (top of the new group). In agent-facing text the person is called "User".
- **Attachments:** `get_ticket`, `claim_ticket`, `claim_next_ticket` and `tracker show` list a ticket's attachments under the description and each comment's in its card. Images keep their line (name, size, dimensions), and the MCP tools return up to 4 as image content (PNG, JPEG, GIF, WebP up to 1.5 MB). Text files are shown inline in a code fence (`TrackerClient.fetchAttachmentText`), up to 20,000 characters each, ending on a whole line when one is near, and 40,000 in all (Claude Code caps a tool result at about 25,000 tokens); a cut file gets a note with its download URL. Videos, PDFs and text files left out are one line with name, type, size and the download URL (`attachmentFileUrl`, based on `TRACKER_URL`). When `TRACKER_TOKEN` is set and a link is shown, the text ends with a note that downloads need it as `Authorization: Bearer`.
