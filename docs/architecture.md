# Architecture

This document records the product changes from `init-design/SPEC.md` and the technical design. When it disagrees with the SPEC, this document wins. Everything the SPEC says that is not changed here still applies.

## 1. Product changes from the SPEC

### 1.1 Statuses are data, per project

- Each project owns its statuses. New projects get five defaults (`DEFAULT_STATUSES` in `packages/shared/src/domain/status.ts`):

  | Name        | Category      | Color     | Glyph                                            |
  | ----------- | ------------- | --------- | ------------------------------------------------ |
  | To do       | `todo`        | `#8E8E99` | empty ring                                       |
  | In progress | `in_progress` | `#C26A06` | ring + half pie                                  |
  | Need review | `in_review`   | `#0B68CB` | ring + three-quarter pie                         |
  | Reviewed    | `reviewed`    | `#18794E` | ring + full pie                                  |
  | Done        | `done`        | `#5B5BD6` | filled circle + check (SPEC glyph and animation) |

- The **category** gives a status its meaning and glyph shape; the **color** is the glyph color. Users can create, rename, recolor, recategorize, reorder and delete statuses. Names are unique per project (case-insensitive). A project keeps at least one status. Deleting a status that has tickets requires a target status; those tickets move to the end of the target group.
- Glyph shapes stay distinguishable without color: 0, 1/2, 3/4, full pie, check.
- `resolveStatus(statuses, category)` (shared) finds the status to use for a workflow step, with fallbacks when a category is missing.
- **Done** means category `done`. Progress %, open counts and overdue all use the category.
- Groups on the Project screen follow status order (position). Keyboard and drag moves cross groups in that order.
- The Project screen's filter is **All** plus one tab per status, in status order (§1.7).

### 1.2 The agent workflow

```
To do ──claim──▶ In progress ──submit──▶ Need review ──review: approved──▶ Reviewed ──person──▶ Done
   ▲                                          │
   └────────────── review: changes requested ─┘
```

- **Worker agent:** finds work with `claim_next_ticket` (category `todo`, ordered High → Low priority, then manual order, then number), works, comments as it goes, then `submit_for_review` with a summary, files and next steps. Submitting stores a report card and moves the ticket to the `in_review` status.
- **Reviewer agent:** lists `in_review` tickets, checks the work against the title, description and comments, then `review_ticket` with a verdict (`approved` / `changes_requested`), a 1–5 rating and a summary. Approved moves the ticket to `reviewed`; changes requested moves it to the top of `todo` so a worker picks it up next.
- **Agents can never move a ticket to a `done` status** (API returns 403). Only a person does that.
- Activity has an **actor**: `{ kind: 'human' | 'agent', name }`. People show as "You"; agents show by name with the terminal tile. Requests set the actor with `x-actor-kind` / `x-actor-name` headers (name URI-encoded). No header means the person.
- New activity type **review** renders as a card with the verdict, star rating and summary.
- A report whose text is TICKET / STATUS / SUMMARY / FILES / NEXT fields (a submission, or a pasted Claude Code report, Markdown marks allowed) renders as labeled sections instead of the raw mono block (`features/ticket/activity/reportSections.ts`): a status line ("Submitted for review" when the STATUS words mean done, otherwise "Status: …" as written), Summary in body text, Next on a highlighted panel, then Files one per line in mono. A file list written over several lines keeps each line whole; a list on one line is split on commas outside brackets, so "src/a.ts (parser, tests)" stays one file. More than 6 files show the first 5 and a "Show N more" text button (§7.3's rule, 44px target, `aria-expanded`, "Show less" when open; `ReportFiles.tsx`). Next and Files are left out when they say "none", also with Markdown marks around it ("**none**"). Submissions write labels in capitals, so when a field has a capital label, a line in another case that starts with the same word ("Next: …" or "Status: …" in a summary) is text of the field above it. Text before the first field, a field given twice or no SUMMARY keeps the raw text.
- Comments can be edited (sets `editedAt`, shows "edited") and deleted. Reports and reviews can be deleted. Events cannot be edited or deleted.

### 1.3 The copy/paste loop still exists

"Send to Claude Code" and "Paste report" work as in the SPEC, for agents without the MCP tools:

- Prompts are built on the server (`GET /api/tickets/:key/prompt`, `GET /api/projects/:key/prompt`) with the shared builders. Status labels use the status names. The ticket block also shows the last review (`Last review: Changes requested · 2/5` + summary).
- "Open tickets" for the project prompt means categories `todo` and `in_progress`, ordered in-progress first, then priority, then number.
- The switch reads "Move MOB-3 to {in_progress status name}" and shows for tickets in a `todo` status.
- Report STATUS words map to categories (`normalizeReportStatus`): reviewed/approved/verified → `reviewed`; done/complete/fixed/finished/resolved and review words → `in_review`; not started → `todo`; progress/partial/blocked/wip/started/ongoing → `in_progress`; to do → `todo`. A report never sets Done.

### 1.4 Attachments

- Tickets (under the description) and comments can have attachments of four kinds. The text fields stay plain text. The rules live in `packages/shared/src/domain/attachment.ts` (`ATTACHMENT_TYPES`, `ATTACHMENT_KINDS`):

  | Kind    | Types (extensions)                              | Up to  |
  | ------- | ----------------------------------------------- | ------ |
  | `image` | PNG, JPEG (jpg, jpeg), GIF, WebP, HEIC, HEIF    | 15 MB  |
  | `video` | MP4, QuickTime (mov, as iPhones record), WebM   | 100 MB |
  | `text`  | Plain text (txt, log), Markdown (md), CSV, JSON | 5 MB   |
  | `pdf`   | PDF                                             | 25 MB  |

- No SVG or HTML: opened from the tracker's address they could run script.
- The type the browser gives decides. When it is empty, `application/octet-stream` (common for .log and .md), `application/vnd.ms-excel` (Windows, for .csv) or `text/x-markdown`, the extension decides (`resolveAttachmentType`). Other names systems give an allowed type count as it and the file keeps the allowed type (`text/x-log` as `text/plain`; `text/x-csv`, `application/csv` and `text/comma-separated-values` as `text/csv`; `image/jpg` as `image/jpeg`). Any other declared type is refused whatever the name. `checkAttachment(file)` gives the stored type and kind, or the message to show: one per kind from `tooLargeMessage` ("Videos can be up to 100 MB.") or `UNSUPPORTED_ATTACHMENT_MESSAGE`, which lists what can be attached. File inputs use `ATTACHMENT_ACCEPT` (every type and extension, because some systems give .log and .md no type), and `attachmentKind(mimeType)` tells how to show a stored attachment.
- **Adding files** (`features/attachments`): New ticket and the ticket screen (under the description), quick capture and the comment box take every kind: from **Add files** (in the comment box the paperclip **Attach files**), which on phones offers the photo library, the camera and Files (`ATTACHMENT_ACCEPT`); by paste into their text fields; and by drag and drop on desktop. `admitFiles` checks each file with the shared rules, and New ticket, quick capture and the comment box take up to 20 files (`MAX_NEW_ATTACHMENTS`), the ticket screen any number. What didn't go is said in the picker area (`FileNote`, `role="alert"`), not in a toast, which is gone after 2.2 s and cut to one line on a phone: "notes.svg can't be attached." (or "notes.svg and 2 more…") over the reasons, here the list of what can be attached, or "A new ticket can have up to 20 files."; and "clip.mov didn't upload." over why (`uploadFailureReason`: the bare 408 and 413 that Node and proxies send become "It took too long to send. Try again on a faster connection." and "The server won't take a file this big."; a bare 5xx, which a proxy for a stopped API sends but so can the API itself or a proxy whose connection broke during one upload, "The tracker couldn't save it. Try again.", since only a check of the tracker tells them apart and the banner says when it can't be reached: it said "Can't reach the tracker. Check your connection." while the tracker answered everything else, PT-109). What a pick left out and the uploads that failed since are two notes (`useFileNotice`); they stay until the next pick, a dismiss or a sent comment, and uploads that fail while the second is up join it. In New ticket, quick capture and the ticket screen the pick's note tops the file area, where Add files was, so the tiles of a big pick can't push it below the fold (PT-72: 21 files at 320×568), and it is scrolled into view at once (`block: 'nearest'`) for a pick from the Add tile under many files. A failure comes later, while the person may be anywhere, and Safari keeps no scroll anchor, so its note goes below the files and the Add tile: a note above them pushed every tile on screen down 53–70px, or landed unseen under the sheet's header (PT-72 review). The failed file keeps its tile among the uploads that follow the saved files, the picture dimmed under an alert mark in a red frame ("late.png didn't upload", `UploadThumbnail`), until its x, the note's Dismiss or the next pick lets it go: a tile that just went let the Add tile slide into its place and nothing in view said why (PT-95, 320×568 scrolled to the middle of 16 files). It holds back neither Create nor Comment (`uploads.uploading` leaves it out, `uploads.tiles` has it). When the note is out of sight, below the fold from the Add tile or from the middle of the files at 320×568 (on the ticket screen the tile can be out of sight too), a toast says it too and moves nothing (`useToastIfUnseen`, a hit test at the note's middle, `inSight`). In the comment box both notes sit just above Attach files; it keeps no failed tile, so when its late note is out of sight (from its first files at 320×568) a toast says it too (`FileNotes`, PT-101). A tap on Dismiss takes the note and its place at once, and for 500 ms (`CLICK_SHIELD_MS`) the screen or sheet it was on takes no taps, nor a double-click's later clicks (`holdPresses`; a mouse's single click and a key press go through, as on an action sheet, and on a screen so do taps on its nav bar and bottom bar while they stay where they were: the fixed or sticky bars a hit test finds at its top and bottom edges, not one the note is in, PT-101; from 768px so do taps on the header and the sidebar, found at the top and left edges beside the scroller the note is in, so that only that scroller's box could move them, PT-109, where a tablet held them too; a sheet holds all of itself, since one that fits its content shrinks with the note, so its header moves too and the scrim it uncovers would close it): what lay below slides up under the finger, or on a screen scrolled to its end, and in a sheet that fits the screen, what lay above slides down, and the second tap of a double tap pressed it: a draft file's x, the ticket screen's x, Comment or a field (PT-72 review, WebKit at 320×568 and 375×812). A note that kept its place for those 500 ms instead closed in one jump later, under a tap aimed at what the gap showed (PT-95). A key press, or a click with no pointer before it such as VoiceOver's (PT-101), dismisses without the hold (a press that ended off Dismiss, such as a mouse dragged off, or that the browser cancelled is no pointer before it, as on action sheets, §1.5, PT-106) and leaves focus where files are added, not on the page body: on Add files (the Add tile, or the button when the files are folded or there are none) or, in the comment box, on the next control, Attach files (`focusFirst`). Focus moves once the note and its failed tiles have gone (`flushSync`): when the failed file was the only tile, the Add tile that had focus gave way to the Add files button and focus fell to the body (PT-95 review). A ticket's upload that fails after its screen has closed is told in a toast. Photos are checked after the web app scales down those larger than 2048px and converts HEIC (`lib/uploads.ts`), which brings most large ones under the limit. Each file uploads at once and shows a progress ring on its tile (`TrackerClient.uploadAttachment` reports progress through XMLHttpRequest, which fetch can't; Node falls back to fetch) and an x that stops it. Tiles keep the order the files were picked: in New ticket, quick capture and the comment box a file that finishes before one picked ahead of it waits in its tile with a full ring until that one is up (`usePickedOrder`), and its x then deletes it; on the ticket screen, where each file joins the ticket as it arrives, finished files go after the ticket's others in the order they finish. New ticket, quick capture and the comment box send their files' ids, in picked order, when they create; Create and Comment wait while a file is still uploading. Closing New ticket or quick capture without creating stops their uploads and deletes the uploaded files.
- Upload first (`POST /api/attachments` with the file itself as the body and an optional `?ticketKey=`, §3); without `ticketKey` the attachment is pending until a ticket or comment is created with its id in `attachmentIds` (or a create repeating a client id names it, §3), at most 20 (`tooManyFilesMessage`: "A new ticket can have up to 20 files.", "A comment can have up to 20 files."). The files list in the order of `attachmentIds` (`attachments.position`); a file uploaded to a ticket later goes after the ticket's others. Pending attachments older than 24 hours are deleted on startup. How files are stored and served: §3.
- **Tiles** (`ThumbnailGrid`), under the description and inside comment cards: images as before; videos show their first frame (a film icon until one is drawn, or when the browser can't play them) with a play badge and their length; text files and PDFs are wide tiles with an icon, the name and the size. A name too long for the one line of a small tile loses its middle, not its end ("crash-r…t-1.log", `splitFileName`), and its title shows it whole. Images and videos are named by number within their kind ("Open image 2", "Play video 1", "Remove video 1"), other files by name ("Open notes.txt"). Every x keeps the 44×44 target that never reaches a tile's middle (`test/regression/thumbnail-middle-never-removes`). Once an x is pressed (it removes a draft file or stops an upload at once; on the ticket screen it asks first) the grid takes no taps or clicks for 500 ms (`useRemoveShield`, with the action sheets' `useClickShield`, §1.5): the next file slides into its place under the finger or the mouse, and a double tap or double-click removed two (PT-83), on phones, touch tablets as wide as a desktop and with a mouse alike. Keyboard presses go through at once. An image the browser can't show (HEIC outside Safari) shows an icon, never a broken image.
- **Opening** (`AttachmentViewerProvider`, `viewerTarget`): images open the full-screen viewer (pinch and double-tap zoom, pan, swipe between the images, swipe down to close). Videos play in a full-screen viewer with the native controls (`overlays/VideoViewer`), scaled to fit the screen however small they were recorded, `playsinline` so iOS doesn't jump to full screen, starting at once where the browser allows it; swipe down or Close ends them, and the swipe takes only clearly downward drags, so taps and scrubbing reach the controls. Text files open in a sheet that reads the file and shows it monospaced and wrapped, scrolling, up to 100,000 characters ending on a whole line, then "Open the whole file" (a new tab); it swipes down to close like any sheet. PDFs open in a new tab.
- Agents get images as image content, text files inline and download links for the rest (§4).

### 1.5 Phone gestures and motion (Apple-like)

On phones (`max-width: 767px`) the app behaves like a native iOS app:

- **Navigation stack:** Projects → Project → Ticket screens stack. Push slides the new screen in from the right edge while the old one moves 30% left and dims; pop reverses. Desktop keeps the SPEC's 28px fade.
- **Edge swipe back:** dragging from the left edge pops interactively with a parallax underlay, and completes or cancels by distance and velocity with a spring. Disabled in iOS Safari browser mode, where Safari owns that gesture (enabled when installed to the home screen).
- **Sheets:** drag the grabber or sheet down to dismiss (follows the finger, rubber-bands upward, velocity-aware). Content scrolls inside; dragging down from the top of the content dismisses.
- **Unsaved changes:** a sheet with input never vanishes by accident. While `Sheet` gets `dirty`, a swipe-down past the threshold springs back, and a scrim tap or Escape (desktop too) leaves it open; an action sheet asks "Discard changes?" with "Discard changes" (Danger) and "Keep editing", which returns focus to the field. The header's `SheetCancelButton` asks the same on phones (iOS convention) and closes at once on desktop, where Cancel is a deliberate click. Create, Save and Apply close without asking, and a sheet without changes closes at once. These sheets set it: New ticket (any field off its default, or a file, including one still uploading), New project (text in any field), Edit project (a name, description or repository that differs from the project it opened with; when the project loads after the sheet opens, the loaded values are the start, not a change), Paste report (text in the box) and Statuses (an open status editor with a changed name, type or color). Quick capture sets it too (a title, description or file, including one still uploading).
- **Row swipe actions:** swipe a ticket row right to move it to the next status; swipe left to reveal "Status" and "Delete". A full swipe triggers the first action. Haptic tick at the threshold where supported.
- **Action sheets ignore a double tap's second tap** (PT-80). A tap opens an action sheet, which slides up under the finger, or turns it into its next step, whose row takes the tapped row's place (the confirm of Delete comment, report, review or project). The second tap of a double tap, 0 to 200 ms later, pressed the row that had just arrived there: it deleted the comment, report, review or project without a real confirm, and on a row near the bottom bar a double tap on the swipe's Delete deleted the ticket and one on Status moved it to Done (WebKit, iPhone 13 at 375×812 and 320×568). So an action sheet's rows take no taps for 500 ms after they appear, when it opens and whenever what its card shows changes: a row's label, tone or weight, or the caption's text (`actionSheetContent`), so a next step that keeps the same rows under a new question is held too (`useTapShield` in `lib/clickShield.ts`, `CLICK_SHIELD_MS`, built on `useClickShield`, the shield of the desktop menu's `MenuConfirm`, §1.7). Cancel never moves and takes taps at once, and so do keyboard presses (a click with `detail` 0). A single mouse click also goes through at once (PT-82): on desktop, Discard changes is an action sheet, and a click a person aims at it after reading can't be a stray tap. `MenuConfirm` still holds a mouse's single click for 500 ms (PT-97 changed these words, not the code): its Delete takes the place of the item just clicked, right under the mouse, where a held click costs one more click and a stray one deletes. The shield tells by the `pointerdown` before the click, since not every browser's click names its pointer: it holds touch and pen taps, a double-click's later clicks (`detail` 2 or more: a double-click on the New ticket backdrop near the bottom of the screen would put its second click on Discard changes), and clicks with no pointer before them. VoiceOver's taps are such synthetic clicks (`detail` 1), so they are held for 500 ms too. A press that ends without a click (dragged off the row, or dragging the sheet down) is forgotten when it ends, so it can't pass for the pointer of a later click that has none (PT-97): one released off the card makes no click on it and one the browser cancels none at all, so they are forgotten at once, and one released on the card makes its click there, which forgets it (`followPresses` in `lib/pressPointer.ts`). A timer after the `pointerup` forgot them before, and a busy page could take a click with no pointer 5–8 ms after the release first (Chromium, PT-106). A finger's `pointerup` lands where it went down wherever it lifts, since that element keeps its pointer, and Chromium sends its click a task later. One mechanism in `overlays/ActionSheet` covers every sheet: Comment, Report, Review and Project options, Delete ticket and Status from a row swipe, Remove image or file, and Discard changes. Tests and E2E specs wait 500 ms before tapping a sheet's row, like a person reading it (`readActionSheet`); unit tests of a phone's double tap press the rows with a touch pointer (`tap` in `overlays/testing.ts`), since a mouse click would go through. An iPad has the desktop layout with touch taps, so the Playwright project `tablet` (WebKit, iPad Mini at 768×1024) runs the tests tagged `@tablet`: a double tap on Undo, on Delete comment in a menu, on Delete status, and on the New ticket backdrop where Discard changes comes (PT-106).
- **Delete status ignores a double tap's second tap** (PT-97). In the Statuses sheet, Delete status turns the status editor into its delete confirm, which is shorter, so Add status below moved up under the finger: a double tap's second tap opened an empty new-status editor in place of the confirm (WebKit, iPhone 13 at 375×812), and where the confirm's Delete lands there instead it would delete the status. So for 500 ms after Delete status is pressed with a pointer, the sheet holds presses the way it does after a file note's dismiss (`holdPresses` in `lib/`, §1.4, which forgets a press that ends without a click as an action sheet does): the second tap of a double tap and a double-click's second click are dropped, keyboard presses go through, and tests wait before pressing the confirm.
- **Pull to refresh** on Projects and Project lists.
- **Large title** on Projects collapses into the nav bar title while scrolling.
- **Nav bar layout:** the back button (at least 44×44) and the right buttons keep their size. The title takes the space left, ends in an ellipsis and stays centred while it fits. When the back label has no room for a few letters, only the chevron shows.
- **Tap the nav bar to scroll up:** a tap anywhere on the nav bar except its buttons (including the safe-area padding at its top) smooth-scrolls the screen's scroller to the top, and jumps there with reduced motion (`navigation/useTapToTop.ts`). Each screen scrolls in its own scroller, and iOS's status-bar tap only scrolls the document, so the nav bar takes over that job.
- **Bottom bar and the keyboard:** on touch phones the bottom bar slides away and is inert while a text field has focus, because the keyboard covers it anyway (`navigation/useEditingText.ts`). It comes back when the field loses focus, but not during a press: a tap whose mousedown takes focus out of the field, such as Comment or Save, keeps it away until the release, so the click lands on what was tapped. When it comes back, the screen scrolls the field that was edited, with its form (the comment box and its Comment button), to 8px above the bar on the next frame, once, so a scroll right after closing the keyboard stays where the user left it (`navigation/keepFieldInSight.ts`). Only a field that fits between the nav bar and the bar moves: a longer one, such as a long description, stays where it is, because bringing its end up would push the part just edited off the top. A sent form, such as the comment box after Comment, is kept at least 8px above the bar while what it sent lands above it (the new comment), also when the keyboard closed before the tap and when the new comment pushed it below the screen: each time the content around it changes size (`ResizeObserver`), for a second after the send (the new comment shows at once, before the tracker answers) and until the user touches or scrolls the screen. These scrolls go to a position (`scrollTo` the current `scrollTop` plus the distance), not by a distance: WebKit runs a smooth scroll on its own thread, so while the page is busy rendering the new comment the scroll moves on from where the box was measured, and a second scroll by a distance landed the box 17–24px above the bar in about half the runs. What lands later, such as an agent's report, pushes the box down like any other content. The bar hides with `translate`, which its entrance animation on `transform` can't override, so a field focused while the bar slides in still sends it away.
- Press feedback (scale .97), spring selections, `prefers-reduced-motion` honored everywhere.

### 1.6 Other additions

- Live updates: the server pushes change events over SSE; open screens refresh when an agent changes something. The web app reopens the stream when the browser gives up on it or when it stays silent for 35 s (two missed pings: a proxy can keep a dead stream open after the API server crashes), waiting 1 s, then doubling up to 15 s. After any reopen, including the first open after a failed connect, all cached data except session and meta refreshes; keys with pending edits and deleted keys are skipped. The ping interval and the silence window are `HEARTBEAT_MS` and `LIVE_STALE_MS` in `packages/shared` (`domain/liveUpdates.ts`), used by the server and the web app. A page hidden for 30 s closes its stream, so a phone's radio doesn't wake for every ping, and reopens it as soon as it is visible again, with the same refresh (`api/live/pauseWhileHidden.ts`); a quicker switch to another app keeps the stream. The time hidden decides, not whether the timer ran, because a phone runs no timers while it suspends a hidden page: such a page also gets a new stream on return, since the one it kept may have died. While a stream is closed or reconnecting, TanStack Query's refetch on focus and on reconnect (the browser online again) are off (`api/live/refreshPending.ts`), so a return after 30 s, or with the network back (a phone that lost it while locked), reads each open query once, after the new stream opens, and no change falls between that read and the stream; with the stream open, focus and reconnect read stale queries as before. After three failed tries (`LIVE_WAIT_ATTEMPTS`: a proxy can refuse the stream while the API answers), they read again without waiting, and a stream that opens later still refreshes everything. The tries the browser makes itself on a dropped stream count too (PT-82): each `error` it reports while it reconnects is one, the drop's own included, so a stream it keeps failing to reopen no longer holds focus reads back until the 35 s silence check. So focus reads come back about 6–7 s after a drop the browser keeps failing to reopen (the drop and its next two tries, 3 s apart), and about 4–4.5 s after one whose first try gets a 502 (the drop, that try and the app's reopening 1 s later), in Chromium and WebKit. Those tries count only toward the three: the wait before the app's own reopening grows with its own reopenings, so after a silence check or a 502 it still tries again after 1 s (PT-97: counted in, an outage longer than the silence check left 15 s before the app's first try, and a 502 2 s). When the browser gives up on the stream, the app reads `GET /api/session` again, because EventSource hides the status and a 401 looks like a proxy's 502: when the server now needs a token, the token screen shows (which ends the retries); an unreachable server changes nothing.
- Project options menu adds **Manage statuses** and **Connect Claude Code** (MCP setup instructions with copy buttons).
- **Links:** http(s) URLs in comments, reports (raw text and every section) and review summaries are links that open in a new tab (`rel="noopener noreferrer"`), in the link color and wrapping anywhere. Punctuation after a URL stays out of it ("see https://x.dev/a." links `https://x.dev/a`), and a closing bracket only stays when the URL opened it. An apostrophe inside a URL stays (`…/The_Hitchhiker's_Guide…`). CJK punctuation ends a URL like a space, because CJK text has no spaces ("请看https://x.dev/a。谢谢" links `https://x.dev/a`), while CJK letters stay in it. Curly double quotes end it like a straight `"` ("请看https://x.dev/a“谢谢”" links `https://x.dev/a`), and so does an opening curly single quote; a closing one (’) stays inside, where iOS types it as an apostrophe. The trimming is one pass from the end, so text of any allowed length (reports take 100,000 characters) splits in linear time; `test/regression/link-trim-long-text` keeps 100,000 trailing brackets or dots under 100 ms. The text is split into text and links (`apps/web/src/lib/linkify.ts`) and rendered as React nodes, so nothing else becomes markup. Text longer than 10,000 characters goes out as several text nodes of at most that, split between graphemes (`lib/textRuns.ts`): WebKit lays out one text node with a very long run that has no break opportunity wider than its box, so a summary of 90,000 closing brackets scrolled the screen 88px sideways at 375px, and it draws a grapheme split across two nodes as two. The description is always the editable field (§4.3), so its URLs stay plain text.
- **A render error stays small** (`lib/ErrorBoundary.tsx`, which logs what failed and the error to the console): an activity item that fails to render shows as a card with "Couldn't show this item", its text as plain text and its menu, so a comment can still be edited or deleted, and a report or review deleted (`features/ticket/activity/UnshownItem.tsx`). The latest review under the title has its own boundary, and its stand-in keeps **Delete review** and, on desktop, **Move to Done** (phones have it in the bottom bar, §1.10). A stand-in tries the real card again once its activity changes, as when an Edit from it saves, but not while an edit is open in it: a comment's edit lives outside its boundary, shared by the card and its stand-in, so it carries over and focus goes back to the options button (`ActivityRow.tsx`, `CommentMenu.tsx`). Items are built so that one activity in a shape the app doesn't expect can't fail the others (`activityItems.ts`): an actor it can't read shows as "Someone" with an empty avatar, a type it doesn't know (from a newer tracker) as "Couldn't show this item" with its text and no menu, and an entry that isn't an object at all, such as `null`, a number or an array, is left out (also of the side panel's "Last report"; `lib/entries.ts`). An activity without an id, or with an id another row already has, still gets a row of its own: it gets a spare key, numbered among those and never one of the rows' ids, so every other row keeps its id as its key, React logs no key warning and each row has its own rise-in delay (`lib/uniqueKeys.ts`, `activityItems.ts`, `risePlan.ts`, PT-91, PT-93). File tiles and the image viewer's slides are keyed the same way (`ThumbnailGrid.tsx`, `overlays/ImageViewer.tsx`). The entry goes when the ticket is created, when the sheet closes any other way (Cancel, Discard changes) and when the fields are back to blank. It is `localStorage`, not `sessionStorage`, because a home-screen app that iOS stopped starts a new session.
- **Unsent quick capture text survives a reload** the same way, under `capture` (`features/capture/keptCapture.ts`): the title and description, with the priority and the project picked in the sheet (none while the default applies; a kept project that is gone gives way to the default), and once Create is pressed the capture's client id and the text that Create sent (§1.9). They are kept while the sheet is open with a title or description, and go when the capture is created or waits offline, when the sheet closes any other way and when the text is emptied. Its files are not kept: after a reload the capture opens with its text only, and its uploads wait on the server until they expire (§1.4).
- **Failed saves keep the typed text.** Title, description and assignee show "Title isn't saved yet." with **Retry** under the field; a comment edit whose Save failed keeps its editor open and shows "Your edit isn't saved yet." next to Save. Text kept from an earlier visit opens the same way.
  - Saves on their way (`fields/fieldSaves.ts`): on a slow connection several saves of a field can be on their way, and the tracker ends with the latest one's text. They are recorded per draft id, not in the field on screen, because the tracker may already have one of them without having answered it, which a check would take for someone else's change: the field opened again after leaving the ticket and the app-wide sync see them too.
  - Leaving a field sends nothing more only when the latest save sent carries the text the field shows and is still on its way: that save settles the field. Other text is sent again, also text an older save still on its way carries (typing more, then deleting it). The kept text goes only when the latest save sent lands; an older one landing records what the tracker has for now, which a later check compares with.
  - Retries: after a failure, typing no longer autosaves; a checked retry saves the text: Retry, leaving the field, opening the ticket again, and app-wide (`features/ticket/drafts/useTicketDrafts`, called once in `TrackerApp`) on start, on `online`, when a request gets an answer again after the tracker couldn't be reached, and when a bare 5xx gets a check the tracker answers (PT-109: it may have been a kept draft's own save, through a proxy whose connection broke, which otherwise waited for the next start, `online` or change in its project), also for tickets that aren't open; and when the tracker reports a change in a project that has tickets with kept text that aren't open (a live update refreshing one of its queries), which may be one of them deleted, reading only that project's tickets: an unsent comment can sit for days.
  - Retries started by an answer, a check or a change are at least 10 s apart, because a failed retry itself makes the tracker look unreachable and the refetch after it reachable again, or gets a bare 5xx that its check finds answered: a save the tracker keeps answering that way is tried again every 10 s.
  - Toasts: Retry and leaving the field say "Can't reach the tracker" when it can't be reached. Retries the app starts on its own show no toast, also when their save fails, because the note already says the text isn't saved.
  - One at a time: a field runs one retry at a time and none while a save of it is on its way, also one sent before it opened: a retry asked for meanwhile (leaving the field, Retry) runs once those saves are done, as one of older text landing leaves the field's newer text unsaved; a comment edit runs one at a time and none while its own Save is on its way. A field opened while the latest save of its kept text is on its way shows that text without a note and checks nothing: once that save lands it follows the tracker, and if it fails the field says the text isn't saved yet and is retried as usual.
  - The app-wide sync leaves the drafts of an open ticket to its screen, also while it loads, and a draft with a save on its way, in this tab or another, to that save (its own saves count the same way), so text kept from an earlier visit is sent once at start, and leaving a ticket while its saves are on their way brings no toast.
  - Other tabs' saves: other tabs know of a tab's saves on their way from marks in `localStorage` (`tracker.draftSaves:<tab>:<draft id>`, `fields/saveMarks.ts`): one key per tab and draft, which only that tab writes. When every tab wrote all marks back as one value, a tab that hadn't yet heard of another tab removing its mark put it back, and the other tabs waited a minute for a save that had landed. A mark stops counting a minute after its tab last sent or settled a save of the draft, so a tab that closed while sending doesn't hold the draft up; a save still hanging in an open tab after a minute stops counting too. A page that goes for good (`pagehide`, not one kept to show again) removes its marks at once, and each tab has a timer for the next of another tab's marks to run out (PT-105), so a field on screen, or a refused field waiting on it, moves on then; the app-wide sync notices on its next run and sends the draft as its own.
  - While another tab's save of a field is on its way, the field shows the kept text without a note and doesn't retry, like a field opened while its own save is on its way, and an edit there is always sent: the tracker may already have that tab's text, whatever this tab's copy says. Once that save lands, the field keeps showing its text, without a note, until this tab's copy of the ticket changes (its own read lands, which takes a while on a slow connection). Typing there goes on top of that text instead of saving the older one over it, and the field's saves compare with that text rather than the older copy, so an edit back to the older text is saved too (`landed` in `fields/fieldDraft.ts`).
  - Comment edits: a comment edit's Save sends it at once, unless the edit was kept from an earlier visit or a save of it failed: then Save first checks the comment like a retry (next), and says "Can't reach the tracker" when it can't, leaving the edit failed (`activity/commentEdit.ts`). Typing after Save starts a new edit, which waits for Save again.
    - A Save names the text the edit was typed over (`expected`, §3). One the tracker refuses because another tab's edit landed first says at once that the comment changed elsewhere (below), with no toast, and keeps its text without Save pressed for it, so it isn't sent for the user again, also after a reload; Save then replaces theirs (PT-105). The text kept is the editor's: text typed since Save is newer than the text refused, and the note shows over it too.
  - The check: the retry first reads the ticket fresh (saved answers above), so the answer comes from the tracker, or the check fails and nothing is saved. If the ticket still has the value the text was typed over, the text is saved; if it already has the text, the draft is done. If someone else (an agent) changed it meanwhile, nothing is saved either way: the field keeps the text and says "Title changed elsewhere while yours wasn't saved." with **Save mine** and **Use theirs**, and a comment edit says "The comment changed elsewhere while your edit wasn't saved." (Save replaces it, Cancel keeps theirs). When that happens to a ticket that isn't open, a toast says "Your edit to MOB-3 isn't saved: it changed elsewhere."
  - Older saves: every field save says what its text was typed over (`expected`, §3): the text of the field's latest save still on its way; else text another tab saved, or was still sending, when the field was typed over (`landed`); else the base of its kept text. A save after a check names what the check found.
    - The tracker refuses a save that lands after newer text with 409 `stale` (no toast), so a save of tab A that hangs while tab B types on top can't overwrite B's text when it lands: B's save, typed over A's text, waits for it.
    - The refused field shows its note ("Assignee isn't saved yet.") and checks like a retry once nothing of it is on its way, in this tab or another, and saves again when the tracker has what it was typed over. Retry meanwhile says "Another tab is still saving the assignee. Yours is tried again once that's done, within a minute." (`fields/useFieldRetry.ts`).
    - Until that check, the kept text going doesn't count as saved elsewhere: another tab's answer can drop it from a copy of the store that hadn't heard of it yet, so the check keeps it again first. A save that fails (no answer, a 5xx) keeps it again too when it went while the save was on its way (PT-105).
    - Not when another tab typed newer text over it meanwhile and that text has gone (saved there): the refused field then reads the ticket and follows the tracker, instead of putting its older text back over the newer one (PT-105).
    - Kept text carries the time it was typed (`at`): a field that still shows text it typed and hasn't saved keeps it when another tab writes older text back, and puts it back in the store (`fields/useKeptText.ts`). Text another tab typed later is still taken, and from then on this tab's text counts as typed over.
    - Otherwise the check finds its text saved, or someone else's change (the note with **Save mine** and **Use theirs**). It also counts the text the field typed over, because the base other tabs keep in step can lag a moment behind a save that just landed. The app-wide sync sends the base it just checked and doesn't count a `stale` refusal as refused: its next run checks the draft again.
  - Refusals: the app-wide sync goes ticket by ticket. No answer, a 5xx, or an answer that means "not now" (401, 408, 429) ends the run, and the rest wait for the next run, which sends them again. A draft the tracker refuses otherwise (another 4xx) stays kept and the others go on; later runs in that page don't send the refused text again, only new text, and on its ticket's screen the field says it isn't saved and retries it there.
- **Error toasts** (`components/Toast`): a toast is a success (the SPEC's circle-check) or an error, `show(text, { kind: 'error' })`: a circle-alert in `--danger-inverse` (#F97066, 6.2:1 on Ink, where Danger is 2.6:1), in the same status region with the same timing, so it is announced the same way.   - The button: "Undo" in `--accent-inverse` (#A3A3F2, 7.4:1 on Ink), a 44×44 target beside the toast's last line that reaches past a one-line toast's 41px instead of making it taller, with hover and focus drawn as a pill inside the toast. ### 1.9 Quick capture

- **Entry points:** on phones a bottom bar on Projects with a primary "New ticket" (instead of a floating +); on desktop "New ticket" in the Projects title row and the shortcut **C** anywhere no text field, sheet or menu has the keyboard; the PWA manifest shortcut "New ticket" opens `/?capture`, which opens the sheet and then drops the parameter. C does nothing while a modal (`aria-modal`), a dropdown (`listbox`), a `menu` or a popover menu's invisible "Close menu" layer is in the page: popover menus keep focus on their trigger, and their layer would take the next click. A closing dropdown, calendar or ••• menu, inert while it takes the second click of a double-click, doesn't count.
- **Sheet** (`{ type: 'capture' }`, `features/capture`): title focused on open (phones too), optional description and files, Project (the last one used, `tracker.capture.project`, else the most recently active) and Priority (Medium). No status is sent, so the server uses the project's first status. Create shows "MOB-7 created" and stays on the current screen. Typed text survives a reload (§1.6); files make it the draft `capture`. A title, description or file makes the sheet `dirty` (§1.5), so a swipe-down, scrim tap, Escape, click outside or a phone's Cancel asks "Discard changes?"; Create closes without asking.
- **Offline:** when the tracker can't be reached, or hasn't answered within 8 s, a text-only capture waits in `tracker.capture.queue` (localStorage) with a client id, and Projects shows "N waiting to sync". A capture with files stays in the sheet instead ("Files need a connection…"), because they only live on the server.
- **Sync:** on start, when `app/reachability` turns reachable, on `online` and when the page becomes visible; one run at a time (across tabs too where there are Web Locks), oldest first, one request at a time, then "N tickets added". Created ids are skipped. Network, 401 and 5xx failures stop the run and keep the rest; a capture the create refuses for good (another 4xx, such as its project being deleted) is dropped with the one-line toast "Couldn't add “…”", the title clipped to 24 characters so it fits at 375px. Sends go through the mutation cache (writes in flight, reachability) and refetch nothing on failure.
- **One ticket per capture:** every create for a capture, the sheet's and each sync's, carries the capture's client id (`clientId`, §3), and the tracker answers a repeat with the ticket the first one made. So a capture is sent again without looking anything up, and still makes one ticket: after a lost answer, when its tab closed mid-request, or when two tabs send it at once. The sheet makes the id at a capture's first Create and keeps it with the kept text (`capture` in `tracker.sheetDrafts`, written before the request goes out) until the capture is created, waits in the queue or the sheet closes. So Create again after a lost answer (files still attached, added or removed), a reload, or a crash or iOS stopping the app mid-create shows the first request's ticket ("MOB-7 created"). Files added in between end up on it too: the tracker attaches a repeat's files the ticket lacks, after its others (§3, `test/regression/client-id-repeat-adds-files`). One that was gone by then (its upload expired after 24 h, or someone removed it from the ticket) is left out, and the toast says so: "MOB-7 created, but 1 file couldn't be attached" (PT-97, `test/regression/capture-repeat-file-left-out`). Edits made in between keep the id, and what the person changed wins (`features/capture/sendCapture.ts`): the first Create keeps the text it sent (`sent`, trimmed as sent) with the id, and a queued capture carries it too (one without it counts as unchanged). The answer to a repeat is the ticket as it is now, so the sheet saves to it only the title, description or priority the person changed since that first Create and the ticket doesn't have yet, with an ordinary update (`PATCH /tickets/:key`, like an edit on the ticket screen) before "MOB-7 created"; a sync does the same for a queued capture. A field the person left alone is never sent, so an edit someone else made to the ticket in between stays, also when the capture is unchanged (title and description edits are not in the activity, so it would be gone for good; `test/regression/capture-keeps-other-edit`); a field both changed gets the person's text. If the tracker refuses that update, the sheet keeps the text and says "MOB-7 was created with your earlier text, and this text couldn't be saved to it. Try again."; a sync counts the capture added, since its ticket exists, and says "MOB-7 created with your earlier text" instead of "Couldn't add …". If the update can't be reached, the capture waits or stays as for any create. A capture emptied of its title, description and files lets its id go, so what is typed next is a new capture; so does one opened after the sheet closed. Changing the project between two Creates still makes a second ticket, in the new project, since client ids are per project.
- **Fewer requests across tabs:** while a request for a capture is out (the sheet's, which keeps going after the 8 s save, or a sync's), its tab holds the Web Lock `tracker-capture-send:<id>`. A sync skips a capture it can't lock, reads it again once it holds the lock, and lets go only after the result is recorded. Web Locks need a secure context, so a phone on a plain http address keeps a lease time in `localStorage` `tracker.capture.sending.<id>` instead, renewed every 20 s and void a minute after the last renewal. That lease is not atomic: Chromium shows a tab another tab's writes a moment late, so two tabs coming back online together can both send a capture. The locks only spare requests (and a second "1 ticket added"); the client id is what keeps it one ticket.

## 3. HTTP API

All routes are under `/api`, JSON in and out. Errors: `{ "error": { "code", "message" } }` with codes `invalid_input` (400), `unauthorized` (401), `forbidden` (403), `not_found` (404), `conflict` (409), `stale` (409, below), `no_match` (422). `packages/client/src/client.ts` is the reference for every route and its types.

| Method & path                                                               | Does                                                                                                                     |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `GET /projects`                                                             | Project summaries in creation order (counts, `lastActivityAt`)                                                           |
| `POST /projects`                                                            | Create (prefix: `resolvePrefix` + `uniquePrefix`; color `PROJECT_COLORS[count % 6]`; default statuses) → `ProjectDetail` |
| `GET/PATCH/DELETE /projects/:key`                                           | Read / edit name, description, repo / delete with everything in it                                                       |
| `GET /projects/:key/board`                                                  | Project, statuses, ticket list items                                                                                     |
| `GET /projects/:key/prompt`                                                 | Project prompt and open ticket count                                                                                     |

| `GET /tickets?status=&category=&q=`                                         | The same filters across every project, most recently updated first, with the statuses of their projects                  |
| `POST /projects/:key/tickets`                                               | Create ticket (top of its group, "created the ticket"); a repeated `clientId` gets the first one (below)                 |
| `POST /projects/:key/statuses`, `PUT /projects/:key/statuses/order`         | Create status / reorder                                                                                                  |
| `PATCH /statuses/:id`, `DELETE /statuses/:id?moveTo=`                       | Edit / delete status                                                                                                     |
| `GET/PATCH/DELETE /tickets/:key`                                            | Ticket detail / edit fields (events per SPEC §6.2) / delete                                                              |
| `POST /tickets/:key/move`                                                   | Drag or keyboard move (`planMove`)                                                                                       |

| `PATCH /activity/:id`, `DELETE /activity/:id`                               | Edit comment / delete comment, report or review                                                                          |
| `POST /attachments`, `GET /attachments/:id/file`, `DELETE /attachments/:id` | Upload / serve / delete files (below)                                                                                    |
| `POST /reports/preview`, `POST /reports/apply`                              | Paste-report preview and apply                                                                                           |

Status changes made by the dropdown, a report, sending, claiming, submitting or reviewing put the ticket at the **top** of its new group (`topRank`). Drags and keyboard moves renumber the destination group (`planMove`).

**Client ids.** `POST /projects/:key/tickets` takes an optional `clientId` (1–64 characters) from a client that may send the same create again (quick capture, §1.9). The ticket keeps it, unique per project. A create that repeats it answers 201 with the ticket the first one made, as it is now, whatever the body's text says (quick capture saves the text the person changed with an update, §1.9), and logs nothing. Only its files count: those in `attachmentIds` the ticket lacks, pending uploads chosen after the first create, are attached after the ticket's other files in the order given, as a file uploaded to it later would be, with a new `updatedAt` and a change event; a file that is gone, such as one the first create attached and someone removed from the ticket since, or one chosen after it whose upload expired (24 h, §1.4), is left out (PT-82; it answered "Some files could not be attached. Upload them again." for a ticket that exists, `test/regression/client-id-repeat-removed-file`), and the answer names it: the ticket with `leftOutAttachmentIds`, a field only there when a file was left out (`CreatedTicket`, PT-97, `test/regression/client-id-repeat-expired-file`), while one that can't be attached otherwise (on another ticket or a comment) refuses the repeat with 400, as it would a create, and none is attached. A first create naming a file that is gone is still refused. Without new files a repeat changes nothing. It is looked up in the create's transaction, so two identical creates at once give one ticket, one number and the same answer. On Postgres with several connections both can miss it; the unique index then refuses the second once the first has committed (`23505`; SQLite's `SQLITE_CONSTRAINT_UNIQUE` is caught too), and the second, rolled back with its number, runs again like a later repeat. SQLite and PGlite run one transaction at a time, so `test/regression/client-id-race` makes the lookup miss to show it.

**Saves typed over a value.** `PATCH /tickets/:key` takes an optional `expected` with the text the title, description or assignee was typed over (the assignee trimmed, as kept). A field the update names in both that has other text now refuses the whole update with 409 `stale` and changes nothing, so an older save that lands late can't overwrite a newer one. That holds also when the update would change nothing: a tab that cleared a name another tab was still sending must not let that save land after it. The write matches the values too (`updateTicketMatching`), so on Postgres a save committed after the read is caught as well. Agents send no `expected` and save as before. The web app sends it with every field save (§1.6). `PATCH /activity/:id` takes `expected: { text }` the same way for a comment edit (trimmed, as kept; `updateActivityMatching`, PT-105).

**Attachment files.** `POST /attachments` takes the file itself as the body: its type as `Content-Type` (`application/octet-stream` when the browser gives none), its name percent-encoded in `X-File-Name` (`FILE_NAME_HEADER`) and `?ticketKey=`. A form, as pages from before this sent, gets "Reload the page and add the file again." The type and a declared `Content-Length` are checked with `checkAttachment` (§1.4) before the body is read, so each kind has its own limit. The body then streams to storage as it arrives (`measureUpload`, `FileStorage.write`), so the server holds a chunk of an upload, never the file: reading it whole first took a 95 MB video from 76 MB to 660 MB; streamed, the server keeps nothing (`npx tsx scripts/check-upload-memory.ts` shows its memory under a few 95 MB uploads). While it streams, a body sent without a length is cut off at its kind's limit (the same message), and one that breaks off or ends short of its length gets "The file did not arrive whole. Try again."; either way no file and no row are kept. Uploads get an hour (`requestTimeout` in `main.ts`; Node's default of five minutes answered 408 to a 100 MB video sent slower than 2.8 Mbit/s), so the largest file arrives over a 240 kbit/s uplink. Every other request keeps Node's five minutes to send its body (`endSlowRequests`, which answers 408 and closes the connection the way Node does), even one answered before its body has arrived, as a GET or HEAD is, and headers keep Node's one minute. `npm run dev`'s Vite server gives requests the same hour (`vite.config.ts`), since uploads pass through its `/api` proxy. Files are stored as `<id>.<extension of the type>` (`FileStorage`: disk, or memory in tests), images keep their dimensions (read from their first 512 KB), and names lose their control characters (Postgres refuses a NUL; a tab or line break becomes a space) and are cut to 200 characters without splitting one (`attachment.<ext>` when there is none). `GET /attachments/:id/file`:

- Always `Accept-Ranges: bytes`. One range (`bytes=a-b`, `bytes=a-` or `bytes=-n`) answers 206 with `Content-Range` and reads only those bytes from storage (`FileStorage.read(key, range)`; disk storage streams them). iOS Safari doesn't play video without this. A range that starts past the end (or `bytes=-0`) answers 416 with `Content-Range: bytes */size`; several ranges or a malformed one get the whole file (200). HEAD answers the headers of the whole file and ignores `Range`.
- `Content-Disposition: inline; filename="…"; filename*=UTF-8''…` (RFC 5987, with an ASCII fallback), so downloads keep their names. `X-Content-Type-Options: nosniff` and `Cache-Control: private, max-age=31536000, immutable` on every answer with the file.
- Text kinds are served with `; charset=utf-8` and `Content-Security-Policy: sandbox` (defense in depth). Not PDFs: Chrome won't show a sandboxed PDF.

## 4. Agent integration (`apps/agent`)

- **MCP server** (`tracker-mcp`, stdio): tools `list_projects`, `list_statuses`, `list_tickets`, `get_ticket`, `create_ticket`, `update_ticket`, `move_ticket`, `add_comment`, `claim_next_ticket`, `claim_ticket`, `submit_for_review`, `review_ticket`; prompts `work` and `review` that appear as slash commands in Claude Code. Config by env: `TRACKER_URL`, `TRACKER_TOKEN`, `TRACKER_AGENT_NAME`.
- **CLI** (`tracker`): the same operations for shells and agents without MCP.
- Register with Claude Code for every project: `claude mcp add tracker -s user --env TRACKER_URL=http://localhost:4100 --env TRACKER_AGENT_NAME=Claude -- node <repo>/apps/agent/dist/mcp.js`.
- `move_ticket` uses `PATCH /tickets/:key { statusId }` (top of the new group). In agent-facing text the person is called "User".
- The tools take as much text as the API, from the limits in `@tracker/shared` (`TICKET_TITLE_MAX`, `TICKET_DESCRIPTION_MAX`, `TICKET_ASSIGNEE_MAX`, `COMMENT_TEXT_MAX`, `REPORT_TEXT_MAX` for a report's summary, files and next steps and a review's summary, and `TICKET_SEARCH_MAX` for `list_tickets`' query, the API's `q`), so too long a text fails before it is sent; `test/tools/limits.test.ts` checks each tool field against the API's schema.
- **Attachments:** `get_ticket`, `claim_ticket`, `claim_next_ticket` and `tracker show` list a ticket's attachments under the description and each comment's in its card. Images keep their line (name, size, dimensions), and the MCP tools return up to 4 as image content (PNG, JPEG, GIF, WebP up to 1.5 MB). Text files are shown inline in a code fence (`TrackerClient.fetchAttachmentText`), up to 20,000 characters each, ending on a whole line when one is near, and 40,000 in all (Claude Code caps a tool result at about 25,000 tokens); a cut file gets a note with its download URL. Videos, PDFs and text files left out are one line with name, type, size and the download URL (`attachmentFileUrl`, based on `TRACKER_URL`). When `TRACKER_TOKEN` is set and a link is shown, the text ends with a note that downloads need it as `Authorization: Bearer`.
