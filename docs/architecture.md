# Architecture

This document records the product changes from `init-design/SPEC.md` and the technical design. When it disagrees with the SPEC, this document wins. Everything the SPEC says that is not changed here still applies.

## 1. Product changes from the SPEC

### 1.1 Statuses are data, per project

- Each project owns its statuses. New projects get five defaults (`DEFAULT_STATUSES` in `packages/shared/src/domain/status.ts`):

  | Name        | Category      | Color     | Glyph                                            |
  | ----------- | ------------- | --------- | ------------------------------------------------ |
  | To do       | `todo`        | `#8E8E99` | empty ring                                       |
  | In progress | `in_progress` | `#C26A06` | ring + half pie                                  |
  | Need review | `in_review`   | `#0B68CB` | ring + three-quarter pie                         |
  | Reviewed    | `reviewed`    | `#18794E` | ring + full pie                                  |
  | Done        | `done`        | `#5B5BD6` | filled circle + check (SPEC glyph and animation) |

- The **category** gives a status its meaning and glyph shape; the **color** is the glyph color. Users can create, rename, recolor, recategorize, reorder and delete statuses. Names are unique per project (case-insensitive). A project keeps at least one status. Deleting a status that has tickets requires a target status; those tickets move to the end of the target group.
- Glyph shapes stay distinguishable without color: 0, 1/2, 3/4, full pie, check.
- `resolveStatus(statuses, category)` (shared) finds the status to use for a workflow step, with fallbacks when a category is missing.
- **Done** means category `done`. Progress %, open counts, the Active/Done filters and overdue all use the category.
- Groups on the Project screen follow status order (position). Keyboard and drag moves cross groups in that order.
- Filter tabs stay **All · Active · Done** (Active = not `done`).

### 1.2 The agent workflow

```
To do ──claim──▶ In progress ──submit──▶ Need review ──review: approved──▶ Reviewed ──person──▶ Done
   ▲                                          │
   └────────────── review: changes requested ─┘
```

- **Worker agent:** finds work with `claim_next_ticket` (category `todo`, ordered High → Low priority, then manual order, then number), works, comments as it goes, then `submit_for_review` with a summary, files and next steps. Submitting stores a report card and moves the ticket to the `in_review` status.
- **Reviewer agent:** lists `in_review` tickets, checks the work against the title, description and comments, then `review_ticket` with a verdict (`approved` / `changes_requested`), a 1–5 rating and a summary. Approved moves the ticket to `reviewed`; changes requested moves it to the top of `todo` so a worker picks it up next.
- **Agents can never move a ticket to a `done` status** (API returns 403). Only a person does that.
- Activity has an **actor**: `{ kind: 'human' | 'agent', name }`. People show as "You"; agents show by name with the terminal tile. Requests set the actor with `x-actor-kind` / `x-actor-name` headers (name URI-encoded). No header means the person.
- New activity type **review** renders as a card with the verdict, star rating and summary.
- A report whose text is TICKET / STATUS / SUMMARY / FILES / NEXT fields (a submission, or a pasted Claude Code report, Markdown marks allowed) renders as labeled sections instead of the raw mono block (`features/ticket/activity/reportSections.ts`): a status line ("Submitted for review" when the STATUS words mean done, otherwise "Status: …" as written), Summary in body text, Next on a highlighted panel, then Files one per line in mono. A file list written over several lines keeps each line whole; a list on one line is split on commas outside brackets, so "src/a.ts (parser, tests)" stays one file. More than 6 files show the first 5 and a "Show N more" text button (§7.3's rule, 44px target, `aria-expanded`, "Show less" when open; `ReportFiles.tsx`). Next and Files are left out when they say "none", also with Markdown marks around it ("**none**"). Submissions write labels in capitals, so when a field has a capital label, a line in another case that starts with the same word ("Next: …" or "Status: …" in a summary) is text of the field above it. Text before the first field, a field given twice or no SUMMARY keeps the raw text.
- Comments can be edited (sets `editedAt`, shows "edited") and deleted. Reports and reviews can be deleted. Events cannot be edited or deleted.

### 1.3 The copy/paste loop still exists

"Send to Claude Code" and "Paste report" work as in the SPEC, for agents without the MCP tools:

- Prompts are built on the server (`GET /api/tickets/:key/prompt`, `GET /api/projects/:key/prompt`) with the shared builders. Status labels use the status names. The ticket block also shows the last review (`Last review: Changes requested · 2/5` + summary).
- "Open tickets" for the project prompt means categories `todo` and `in_progress`, ordered in-progress first, then priority, then number.
- The switch reads "Move MOB-3 to {in_progress status name}" and shows for tickets in a `todo` status.
- Report STATUS words map to categories (`normalizeReportStatus`): reviewed/approved/verified → `reviewed`; done/complete/fixed/finished/resolved and review words → `in_review`; not started → `todo`; progress/partial/blocked/wip/started/ongoing → `in_progress`; to do → `todo`. A report never sets Done.

### 1.4 Attachments

- Tickets (under the description) and comments can have attachments of four kinds. The text fields stay plain text. The rules live in `packages/shared/src/domain/attachment.ts` (`ATTACHMENT_TYPES`, `ATTACHMENT_KINDS`):

  | Kind    | Types (extensions)                              | Up to  |
  | ------- | ----------------------------------------------- | ------ |
  | `image` | PNG, JPEG (jpg, jpeg), GIF, WebP, HEIC, HEIF    | 15 MB  |
  | `video` | MP4, QuickTime (mov, as iPhones record), WebM   | 100 MB |
  | `text`  | Plain text (txt, log), Markdown (md), CSV, JSON | 5 MB   |
  | `pdf`   | PDF                                             | 25 MB  |

- No SVG or HTML: opened from the tracker's address they could run script.
- The type the browser gives decides. When it is empty, `application/octet-stream` (common for .log and .md), `application/vnd.ms-excel` (Windows, for .csv) or `text/x-markdown`, the extension decides (`resolveAttachmentType`); a declared type that isn't allowed is refused whatever the name. `checkAttachment(file)` gives the stored type and kind, or the message to show: one per kind from `tooLargeMessage` ("Videos can be up to 100 MB.") or `UNSUPPORTED_ATTACHMENT_MESSAGE`, which lists what can be attached. File inputs use `ATTACHMENT_ACCEPT` (every type and extension, because some systems give .log and .md no type), and `attachmentKind(mimeType)` tells how to show a stored attachment.
- Add images by a photo button (opens camera roll/camera on phones), paste, or drag and drop. The web app downscales photos larger than 2048px before upload.
- Upload first (`POST /api/attachments`, multipart `file` + optional `ticketKey`); without `ticketKey` the attachment is pending until a ticket or comment is created with its id in `attachmentIds`. Pending attachments older than 24 hours are deleted on startup. How files are stored and served: §3.
- Image thumbnails show under the description and inside comment cards. Tapping opens a full-screen viewer: pinch and double-tap zoom, pan, swipe between images, swipe down to close.
- Agents get images as image content, text files inline and download links for the rest (§4).

### 1.5 Phone gestures and motion (Apple-like)

On phones (`max-width: 767px`) the app behaves like a native iOS app:

- **Navigation stack:** Projects → Project → Ticket screens stack. Push slides the new screen in from the right edge while the old one moves 30% left and dims; pop reverses. Desktop keeps the SPEC's 28px fade.
- **Edge swipe back:** dragging from the left edge pops interactively with a parallax underlay, and completes or cancels by distance and velocity with a spring. Disabled in iOS Safari browser mode, where Safari owns that gesture (enabled when installed to the home screen).
- **Sheets:** drag the grabber or sheet down to dismiss (follows the finger, rubber-bands upward, velocity-aware). Content scrolls inside; dragging down from the top of the content dismisses.
- **Unsaved changes:** a sheet with input never vanishes by accident. While `Sheet` gets `dirty`, a swipe-down past the threshold springs back, and a scrim tap or Escape (desktop too) leaves it open; an action sheet asks "Discard changes?" with "Discard changes" (Danger) and "Keep editing", which returns focus to the field. The header's `SheetCancelButton` asks the same on phones (iOS convention) and closes at once on desktop, where Cancel is a deliberate click. Create, Save and Apply close without asking, and a sheet without changes closes at once. These sheets set it: New ticket (any field off its default), New project (text in any field), Edit project (a name, description or repository that differs from the project it opened with; when the project loads after the sheet opens, the loaded values are the start, not a change), Paste report (text in the box) and Statuses (an open status editor with a changed name, type or color). Quick capture sets it too (a title, description or photo, including one still uploading).
- **Row swipe actions:** swipe a ticket row right to move it to the next status; swipe left to reveal "Status" and "Delete". A full swipe triggers the first action. Haptic tick at the threshold where supported.
- **Pull to refresh** on Projects and Project lists.
- **Large title** on Projects collapses into the nav bar title while scrolling.
- **Nav bar layout:** the back button (at least 44×44) and the right buttons keep their size. The title takes the space left, ends in an ellipsis and stays centred while it fits. When the back label has no room for a few letters, only the chevron shows.
- **Tap the nav bar to scroll up:** a tap anywhere on the nav bar except its buttons (including the safe-area padding at its top) smooth-scrolls the screen's scroller to the top, and jumps there with reduced motion (`navigation/useTapToTop.ts`). Each screen scrolls in its own scroller, and iOS's status-bar tap only scrolls the document, so the nav bar takes over that job.
- **Bottom bar and the keyboard:** on touch phones the bottom bar slides away and is inert while a text field has focus, because the keyboard covers it anyway (`navigation/useEditingText.ts`). It comes back when the field loses focus, but not during a press: a tap whose mousedown takes focus out of the field, such as Comment or Save, keeps it away until the release, so the click lands on what was tapped. When it comes back, the screen scrolls the field that was edited, with its form (the comment box and its Comment button), to 8px above the bar: on the next frame, and again once the bar is in, for what the action added above the field, such as the sent comment (`navigation/keepFieldInSight.ts`). The bar hides with `translate`, which its entrance animation on `transform` can't override, so a field focused while the bar slides in still sends it away.
- Press feedback (scale .97), spring selections, `prefers-reduced-motion` honored everywhere.

### 1.6 Other additions

- Live updates: the server pushes change events over SSE; open screens refresh when an agent changes something. The web app reopens the stream when the browser gives up on it or when it stays silent for 35 s (two missed pings: a proxy can keep a dead stream open after the API server crashes), waiting 1 s, then doubling up to 15 s. After any reopen, including the first open after a failed connect, all cached data except session and meta refreshes; keys with pending edits and deleted keys are skipped. The ping interval and the silence window are `HEARTBEAT_MS` and `LIVE_STALE_MS` in `packages/shared` (`domain/liveUpdates.ts`), used by the server and the web app. A page hidden for 30 s closes its stream, so a phone's radio doesn't wake for every ping, and reopens it as soon as it is visible again, with the same refresh (`api/live/pauseWhileHidden.ts`); a quicker switch to another app keeps the stream. When the browser gives up on the stream, the app reads `GET /api/session` again, because EventSource hides the status and a 401 looks like a proxy's 502: when the server now needs a token, the token screen shows (which ends the retries); an unreachable server changes nothing.
- Project options menu adds **Manage statuses** and **Connect Claude Code** (MCP setup instructions with copy buttons).
- **Links:** http(s) URLs in comments, reports (raw text and every section) and review summaries are links that open in a new tab (`rel="noopener noreferrer"`), in the link color and wrapping anywhere. Punctuation after a URL stays out of it ("see https://x.dev/a." links `https://x.dev/a`), and a closing bracket only stays when the URL opened it. An apostrophe inside a URL stays (`…/The_Hitchhiker's_Guide…`). CJK punctuation ends a URL like a space, because CJK text has no spaces ("请看https://x.dev/a。谢谢" links `https://x.dev/a`), while CJK letters stay in it. The trimming is one pass from the end, so text of any allowed length (reports take 100,000 characters) splits in linear time; `test/regression/link-trim-long-text` keeps 100,000 trailing brackets or dots under 100 ms. The text is split into text and links (`apps/web/src/lib/linkify.ts`) and rendered as React nodes, so nothing else becomes markup. The description is always the editable field (§4.3), so its URLs stay plain text.
- **A render error stays small** (`lib/ErrorBoundary.tsx`, which logs what failed and the error to the console): an activity item that fails to render shows as a card with "Couldn't show this item", its text as plain text and its menu, so a comment can still be edited or deleted, and a report or review deleted (`features/ticket/activity/UnshownItem.tsx`). Reports are read inside their card (`ReportBody`), so a report the reader trips on only takes down its own card. A screen that fails shows "Something went wrong" with **Back** (when it has a parent) and **Reload** in its place (`app/ScreenError.tsx`). Each screen's boundary sits inside its stack layer (`app/renderScreen.tsx`), so the stack, the sidebar and breadcrumb, and the edge swipe back keep working.
- Optional access token: when `TRACKER_TOKEN` is set, the API needs `Authorization: Bearer <token>` or the session cookie from `POST /api/session`. The web app shows a token screen once. After a sign-in it reads `GET /api/session` once more and ignores the answer, so the service worker replaces its saved signed-out copy and an offline start opens the app.
- Installable PWA (manifest, icons, offline app shell).
- **Saved answers:** the service worker reads `GET /api` network-first (3 s timeout; not `/api/events` or image files) and answers from its cache when the network fails, is too slow, or a proxy answers for a stopped API with a bare 5xx. It marks those answers with `x-tracker-saved` (`pwa/savedAnswerPlugin`), and a fetch wrapper (`pwa/savedAnswers`, installed by the shell) notes whether the latest answer was one. A read answered that way counts as the tracker being unreachable (`app/reachability`), so the banner says "Offline — showing saved data", and capture sync and draft retries don't start; writes are never cached.
- App updates never lose typed text. While the app stays open it looks for a new build when the page becomes visible and every 30 minutes (skipped while offline). A new service worker takes over at once, but the page reloads into the new build only when no text field is focused, no dialog is open, there are no drafts (`hasDrafts()`) and no write is in flight, whether the page is visible or hidden. It checks again every second and on `visibilitychange` (`apps/web/src/pwa`). Writes in flight come from the QueryClient's mutation cache. A lazy chunk that fails to load (`vite:preloadError`: a page still on the old build asks for a file the new build replaced) reloads the page by the same rule (`pwa/reloadOnPreloadError.ts`); until then the failed import fails as usual.
- **Draft contract** (`apps/web/src/lib/drafts.ts`): a feature that holds unsent text a reload would lose marks it with `useDraftMark(id, active)` (`lib/useDraftMark.ts`), `active` while the text differs from what is saved; the mark goes when `active` turns false (sent, saved or emptied) and when the component unmounts. Underneath are `markDraft(id)` and `clearDraft(id)`. Use one id per draft, such as `comment:MOB-3`. Marks are counted per id, so each `markDraft` needs its own `clearDraft`, and two mounted components that share an id keep the draft until both let go. Text in the ticket drafts store (next point) counts as a draft without a mark, until it is saved or dropped. While `hasDrafts()`, reloading or closing the page asks first (`beforeunload`; iOS doesn't show it). A draft that is never cleared keeps the page on the old build until the next launch. An open sheet needs no mark to hold an update, because the reload already waits while a dialog is open; quick capture marks `capture` anyway so that closing the page asks, since its text lives only in the sheet. The New ticket sheet's kept fields (below) are not a draft: `hasDrafts()` leaves them out, because the sheet opens with them again after a reload.
- **Unsaved ticket text survives leaving the ticket and reloading.** Title, description, assignee, comment edits and the comment box keep typed text in a small store (`apps/web/src/lib/storedDrafts.ts`, `localStorage` `tracker.drafts`, in memory when storage fails) under their draft ids (`title:MOB-3`, `description:MOB-3`, `assignee:MOB-3`, `comment-edit:<comment id>`, `comment:MOB-3`), with the ticket key, the field, the server value the text was typed over and, for a comment edit, whether Save was pressed for it. An entry stays until the tracker has its text, also while a save is on its way, so leaving the ticket or reloading during a request loses nothing. The ticket opens again with that text. An entry goes once the server has its text, when the comment box is sent or emptied, when an edit is cancelled or emptied (a comment needs text, so an empty edit can't be saved), on **Use theirs**, and when its comment or ticket is deleted: by the user, or elsewhere, which the app-wide sync below finds out (it reads every ticket that isn't open and has kept text) and so does the ticket screen when it gets a 404 for its ticket. The comment box's text is never sent for the user, and neither is an edit nobody pressed Save for: it opens again in its editor as it was left, without a note and without taking focus, and only Save sends it.
- **Unsent New ticket text survives a reload.** While the New ticket sheet is open with changes, its fields (title, description, status, priority, assignee, due date) are kept in the sheet drafts store (`apps/web/src/lib/sheetDrafts.ts`, `localStorage` `tracker.sheetDrafts`, in memory when storage fails; both stores use `lib/draftStorage.ts`) under `new-ticket:<project key>`. Opening New ticket for that project again, after a reload, a crash or iOS stopping the app, starts from them; a kept status that was deleted meanwhile gives way to the sheet's default. The entry goes when the ticket is created, when the sheet closes any other way (Cancel, Discard changes) and when the fields are back to blank. It is `localStorage`, not `sessionStorage`, because a home-screen app that iOS stopped starts a new session.
- Failed saves keep the typed text. Title, description and assignee show "Title isn't saved yet." with **Retry** under the field; a comment edit whose Save failed keeps its editor open and shows "Your edit isn't saved yet." next to Save. Text kept from an earlier visit opens the same way. Leaving a field while its autosave is still on its way sends nothing more: that save settles the field and its kept text. After a failure, typing no longer autosaves; a checked retry saves the text: Retry, leaving the field, opening the ticket again, and app-wide (`features/ticket/drafts/useTicketDrafts`, called once in `TrackerApp`) on start, on `online` and when a request gets an answer again after the tracker couldn't be reached, also for tickets that aren't open; while tickets that aren't open have kept text, also when the tracker reports a change (a live update refreshing the cache), which may be one of them deleted. Retries started by an answer or a change are at least 10 s apart, because a failed retry itself makes the tracker look unreachable and the refetch after it reachable again. Retry and leaving the field say "Can't reach the tracker" when it can't be reached. Retries the app starts on its own show no toast, also when their save fails, because the note already says the text isn't saved. A comment edit's Save sends it at once; typing after Save starts a new edit, which waits for Save again. The retry first reads the ticket fresh: the read carries `x-tracker-fresh` (`{ fresh: true }` in `@tracker/client`), which the service worker's network-first route leaves alone (`pwa/apiReadRoute.ts`), the one exception to the saved answers above. So the answer comes from the tracker, or the check fails and nothing is saved. If the ticket still has the value the text was typed over, the text is saved; if it already has the text, the draft is done. If someone else (an agent) changed it meanwhile, nothing is saved either way: the field keeps the text and says "Title changed elsewhere while yours wasn't saved." with **Save mine** and **Use theirs**, and a comment edit says "The comment changed elsewhere while your edit wasn't saved." (Save replaces it, Cancel keeps theirs). When that happens to a ticket that isn't open, a toast says "Your edit to MOB-3 isn't saved: it changed elsewhere." The app-wide sync goes ticket by ticket: no answer, a 401 or a 5xx ends the run and the rest wait for the next one, while a draft the tracker refuses otherwise (another 4xx) stays kept and the others go on.

### 1.7 Small deviations from the design

- Going back from a ticket keeps the Project screen's filter and search, because screens stay mounted in the navigation stack. Opening a project from Projects (or the sidebar) still resets them to All and an empty search.
- When the projects list is narrower than 640px (a desktop window around 768px wide), the Progress column hides so names stay readable.
- Delete confirmations count tickets correctly ("its 1 ticket", "its 3 tickets").
- A status move is announced once, by the toast; the hidden live region announces reorders ("MOB-3 moved"), and every announcement is read again even when the text repeats.
- The click that ends a drag is ignored until the release's task ends, instead of the SPEC's 400 ms (§7.4): browsers fire that click in the same task as `pointerup`, so a slow phone can't open the ticket by dropping it, and a deliberate tap right after a drag still opens its ticket.
- Phone ticket rows give the title the first line beside the avatar, wrapping up to three lines, with priority, key and due date on a second line below it. The per-row status glyph is hidden there because the group header shows it. Desktop rows keep the SPEC's single line. The phone drag ghost copies the phone row, title in the row's regular weight so it breaks into the same lines; the desktop ghost stays the SPEC's one line (medium title, no due date).
- Phones narrower than 375px (320, 360) show "Send" on the Project bottom bar, because "Send open tickets" doesn't fit beside "Paste report" there; the button's accessible name stays "Send open tickets", which starts with the visible word, so Voice Control's "tap Send" works (WCAG 2.5.3). The List/Board switch is 120px instead of 132px there, so the 320px filter row keeps its 16px gutters.
- Phones narrower than 360px (320) show "Paste" on the Ticket bottom bar, because "Paste report" beside "Send to Claude" or "Move to Done" needs about 347px; the accessible name stays "Paste report", which starts with the visible word (WCAG 2.5.3). The primary keeps its whole label: "Send to Claude", or "Move to Done" for a reviewed ticket, where a long done name ends in an ellipsis and the check icon keeps its 20px. The primary ignores taps for 500 ms after it switches between the two, because both sit in the same spot: the second tap of a double tap on Move to Done would otherwise open Send to Claude.
- Text colors reach WCAG AA (4.5:1) on every background they sit on, down to `--fill-2` (#EFEFF1: the segmented track, the phone search field, the selected sidebar item) and the slightly darker `--drop-tint` (#EEEEFC), and on the 1.4 s row flash (#E4E4FA) even without its multiply blend, which darkens the text too. Placeholder (placeholders, times, "None") is #6C6C77 instead of #9A9AA3, the lightest gray that passes on #EFEFF1. The grays above it step darker by at least 4.5 L*, the smallest step the design draws between them (Subtle → Placeholder), so a Muted label stays apart from a Subtle count or a Placeholder time: Subtle (counts, keys) is #60606B instead of #8E8E99, Muted (secondary text, labels, values) #555560 instead of #6B6B76, and Muted-2 (due dates, repo paths, priority bars) #4A4A54 instead of #55555F. The search icon and an empty due date's calendar follow their text color; the To do ring (#8E8E99, status data), Faint chevrons and separators, and dashed lines keep the design's colors. `apps/web/test/regression/text-contrast.test.ts` checks every text color against its backgrounds and `secondary-text-steps.test.ts` the steps.
- Drag handles (`--handle`, list rows, board cards and the statuses list) are #82828D instead of Faint #B4B4BC, because phones always show them: 3:1 (WCAG 1.4.11) on every row background, the row flash included (`drag-handle-contrast.test.ts`). Hovered handles keep the design's Muted on #EFEFF1.
- Star ratings (`components/StarRating`: review cards, Latest review, Ready for you rows) show the score after the stars, "4/5" in Muted, so it reads at a glance; screen readers get "Rated 4 out of 5" from the label. Filled stars are `--star` #B57D00 instead of #E5A000, 3:1 on Surface and on a hovered row's Fill, and empty stars are hollow Faint outlines instead of #D9D9DE fills, so filled and empty differ by fill and not by color alone (`star-rating-contrast.test.tsx`). The stars are never an input.
- The New ticket title wraps instead of the SPEC's one-line input, so a long idea stays readable while typing on a phone (`components/TitleField`, built on `AutoTextarea` for other sheet titles too). It grows to five lines, which hold a 150-character title at 375px, then scrolls. It is still one line of text: Enter creates the ticket or shows the missing-title error, line breaks that arrive by paste become spaces, the keyboard's key says "done", and it takes at most the API's 300 characters. It keeps the design's 20/600, which is large enough that iOS doesn't zoom in, and a one-line title is as tall as the input was.

### 1.8 Board view

- The Project screen's filter row has a **List · Board** switch (next to search; beside it on phones). The choice is remembered per project on the device (`localStorage` `tracker.projectView.<KEY>`, session fallback when storage fails); List is the default. Filter and search apply to both.
- The board shows one column per visible status in status order, empty ones included ("No tickets", or "No matches" while searching), each with glyph, name, count and "+". Cards show priority, key, title, due date and avatar. The board fills the screen below the filters and each column scrolls on its own; columns are at least 260px and the board scrolls sideways when they don't fit.
- Moves reuse the list's flow (`useTicketMove`, `planMove`, toast, live region, flash). Drags use the same `DragSession` with a board environment (`features/project/board/boardEnvironment.ts`): on desktop the column under the pointer by x and the slot by card midpoints, auto-scroll near the board's sides and a column's top and bottom. Arrow keys on a card's handle: ↑/↓ within the column, ←/→ to the same slot of the neighbouring column.
- Phones page through the columns with scroll snap (a column is the width minus a 26px peek of the next) and a "2 / 5" indicator with page dots. Cards open on tap; a drag from the handle moves within the column on screen and pages to the neighbouring column after the finger rests 500ms within 32px of the screen edge. A 20px strip at the left edge doesn't pan the board, so the edge swipe back still works.

### 1.9 Quick capture

- **Entry points:** on phones a bottom bar on Projects with a primary "New ticket" (instead of a floating +); on desktop "New ticket" in the Projects title row and the shortcut **C** anywhere no text field, sheet or menu has the keyboard; the PWA manifest shortcut "New ticket" opens `/?capture`, which opens the sheet and then drops the parameter. C does nothing while a modal (`aria-modal`), a dropdown (`listbox`), a `menu` or a popover menu's invisible "Close menu" layer is in the page: popover menus keep focus on their trigger, and their layer would take the next click.
- **Sheet** (`{ type: 'capture' }`, `features/capture`): title focused on open (phones too), optional description and photos, Project (the last one used, `tracker.capture.project`, else the most recently active) and Priority (Medium). No status is sent, so the server uses the project's first status. Create shows "MOB-7 created" and stays on the current screen. Typed text is the draft `capture`. A title, description or photo makes the sheet `dirty` (§1.5), so a swipe-down, scrim tap, Escape, click outside or a phone's Cancel asks "Discard changes?"; Create closes without asking.
- **Offline:** when the tracker can't be reached, or hasn't answered within 8 s, a text-only capture waits in `tracker.capture.queue` (localStorage) with a client id, and Projects shows "N waiting to sync". A capture with photos stays in the sheet instead, because photos only live on the server.
- **Sync:** on start, when `app/reachability` turns reachable, on `online` and when the page becomes visible; one run at a time (a Web Lock across tabs), oldest first, one request at a time, then "N tickets added". Created ids are skipped. Network, 401 and 5xx failures stop the run and keep the rest; a capture the create refuses for good (another 4xx, such as its project being deleted) is dropped with the one-line toast "Couldn't add “…”", the title clipped to 24 characters so it fits at 375px. Sends go through the mutation cache (writes in flight, reachability) and refetch nothing on failure.
- **One request per capture, across tabs:** while a request for a capture is out (the sheet's, which keeps going after the 8 s save, or a sync's), its tab holds the Web Lock `tracker-capture-send:<id>`. Web Locks need a secure context, so a phone on a plain http address keeps a lease time in `localStorage` `tracker.capture.sending.<id>` instead, renewed every 20 s and void a minute after the last renewal. A sync skips a capture it can't lock, reads it again once it holds the lock, and lets go only after the result is recorded.
- **Lookup before sending again:** a capture whose request may have reached the server is marked `attempted` before sending and looked up before it is sent again: a search for its title (the whole words that fit the search's 200 characters, since titles may have 300), then the same title and description, created after it, compared on the client. A lookup that fails keeps the capture for a later run; a 404 (the project is gone) leaves the answer to the create.

### 1.10 Ready for you

- Projects (phone and desktop) shows a **Ready for you** card above the project list while any project has a ticket in a `reviewed` status (`GET /api/tickets?category=reviewed`, most recently updated first; `features/ready`). It is left out when empty or when it can't load. Rows show key, title, project color and name, the latest review's verdict chip and stars; long lists collapse like a group (§7.3).
- Tapping a row opens the ticket. Phones swipe a row right to move it to its project's first `done` status; desktop shows a **Done** button on hover and on focus, and it stays in the tab order. Both use the Project screen's status change (toast "MOB-3 moved to Done", flash). The row leaves at once and comes back if the save fails.
- Project rows label their counts: "4 open", with "2 ready" below it when some are reviewed (the Open column is 64px).
- Every `TicketListItem` has `lastReview: { verdict, rating } | null`, the latest `review` activity, read in the same query as the list.
- The ready list (query key `['ready']`) refreshes on every change event, like the project list, but not while a ticket edit is in flight; the last edit to settle refreshes it.
- **Ticket screen:** a ticket in a `reviewed` status shows its latest review (reviewer, time, verdict chip, stars, summary) under the title, above the description, with **Move to Done** (the project's first `done` status, same toast). Above the description, because most descriptions run long enough (the median PT ticket has about 630 characters) to push the review below the fold at 375×812, and at 320×568 even 300 characters did. On phones Move to Done is also the bottom bar's primary instead of "Send to Claude"; on desktop it is the only primary button, so the side panel's "Send to Claude Code" turns secondary while it shows. Focus then moves to the Status row. A ticket sent back (latest review: changes requested, now in a `todo` or `in_progress` status) shows that review in the same place without the button until it is submitted again. The full activity stays as it was.
- **Sent back on the Project screen:** while a ticket's latest review asks for changes and it waits in a `todo` or `in_progress` status (`isSentBack` in `packages/shared`), its list row and board card show a **Changes requested** chip (↺, Danger), so it doesn't look like a new idea. Submitting it again ends the chip. The row puts the chip between the key and the due date; below 1024px wide (phones, narrow windows) it shows only the ↺, 22×18 so a phone row keeps its height, because the full chip (144px) doesn't fit beside the priority, key and due date there (a phone row has about 105px left for it at 375px, 50px at 320px). The label stays in the row's accessible name. Cards always show the label, with the due date beside it or wrapped below. The drag ghost copies the row's chip.
- **One verdict chip** (`components/VerdictChip`) for Ready rows, review cards, the latest review, rows and cards. An approval takes the project's Reviewed status color on a 10% tint of it. Status colors are data, so a light one can be unreadable on its own tint (teal `#12A594` is 2.77:1): the label then takes the lightest shade of the color toward black that reaches 4.5:1 (`chipText.ts`); the default Reviewed green already does and stays as it is.

## 2. Data model

TypeScript types live in `packages/shared/src/domain`. Database tables (snake_case, mapped to camelCase with Kysely's `CamelCasePlugin`):

| Table         | Columns                                                                                                                                                                                                                                         |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `projects`    | `id` text pk, `name`, `key` (unique), `description`, `repo`, `color`, `next_num` int, `created_at` bigint, `updated_at` bigint                                                                                                                  |
| `statuses`    | `id` pk, `project_id` → projects (cascade), `name`, `category`, `color`, `position` int, `created_at` bigint                                                                                                                                    |
| `tickets`     | `id` pk, `project_id` → projects (cascade), `num` int, `status_id` → statuses (restrict), `rank` int, `title`, `description`, `priority`, `assignee`, `due` text (`YYYY-MM-DD` or ''), `created_at`, `updated_at`; unique (`project_id`, `num`) |
| `activities`  | `id` pk, `ticket_id` → tickets (cascade), `type`, `actor_kind`, `actor_name`, `text`, `review_verdict` null, `review_rating` int null, `created_at`, `edited_at` null                                                                           |
| `attachments` | `id` pk, `ticket_id` null → tickets (cascade), `activity_id` null → activities (cascade), `file_name`, `mime_type`, `size` int, `width` int null, `height` int null, `storage_key`, `created_at`                                                |

Portability rules (SQLite now, Postgres later): app-generated text ids (`crypto.randomUUID()`), epoch-ms timestamps as `bigint` (parsed to numbers), no booleans, no JSON columns, case-insensitive search with `lower()`, schema built only with Kysely's schema builder. Integration tests run on SQLite and on PGlite (real Postgres in WASM). `DATABASE_URL` picks the dialect: a file path or `:memory:` for SQLite, `postgres://…` for Postgres.

## 3. HTTP API

All routes are under `/api`, JSON in and out. Errors: `{ "error": { "code", "message" } }` with codes `invalid_input` (400), `unauthorized` (401), `forbidden` (403), `not_found` (404), `conflict` (409), `no_match` (422). `packages/client/src/client.ts` is the reference for every route and its types.

| Method & path                                                               | Does                                                                                                                     |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `GET /projects`                                                             | Project summaries in creation order (counts, `lastActivityAt`)                                                           |
| `POST /projects`                                                            | Create (prefix: `resolvePrefix` + `uniquePrefix`; color `PROJECT_COLORS[count % 6]`; default statuses) → `ProjectDetail` |
| `GET/PATCH/DELETE /projects/:key`                                           | Read / edit name, description, repo / delete with everything in it                                                       |
| `GET /projects/:key/board`                                                  | Project, statuses, ticket list items                                                                                     |
| `GET /projects/:key/prompt`                                                 | Project prompt and open ticket count                                                                                     |
| `GET /projects/:key/tickets?status=&category=&q=`                           | Filtered tickets (status by name, case-insensitive)                                                                      |
| `GET /tickets?status=&category=&q=`                                         | The same filters across every project, most recently updated first                                                       |
| `POST /projects/:key/tickets`                                               | Create ticket (top of its group, "created the ticket")                                                                   |
| `POST /projects/:key/statuses`, `PUT /projects/:key/statuses/order`         | Create status / reorder                                                                                                  |
| `PATCH /statuses/:id`, `DELETE /statuses/:id?moveTo=`                       | Edit / delete status                                                                                                     |
| `GET/PATCH/DELETE /tickets/:key`                                            | Ticket detail / edit fields (events per SPEC §6.2) / delete                                                              |
| `POST /tickets/:key/move`                                                   | Drag or keyboard move (`planMove`)                                                                                       |
| `GET /tickets/:key/prompt`, `POST /tickets/:key/sent`                       | Ticket prompt / mark as sent                                                                                             |
| `POST /tickets/:key/comments`                                               | Add comment (text and/or `attachmentIds`)                                                                                |
| `PATCH /activity/:id`, `DELETE /activity/:id`                               | Edit comment / delete comment, report or review                                                                          |
| `POST /attachments`, `GET /attachments/:id/file`, `DELETE /attachments/:id` | Upload / serve / delete files (below)                                                                                    |
| `POST /reports/preview`, `POST /reports/apply`                              | Paste-report preview and apply                                                                                           |
| `POST /projects/:key/claim`                                                 | Claim the next `todo` ticket (204 when none)                                                                             |
| `POST /tickets/:key/claim`                                                  | Claim a specific ticket                                                                                                  |
| `POST /tickets/:key/submit`                                                 | Agent submits work for review                                                                                            |
| `POST /tickets/:key/review`                                                 | Agent reviews a ticket in `in_review`                                                                                    |
| `GET /people`                                                               | Assignee suggestions                                                                                                     |
| `GET /meta`                                                                 | Server info for Connect Claude Code: `serverUrl` (`PUBLIC_URL`, else the URL the request reached), entry paths           |
| `GET /events`                                                               | SSE stream of `ChangeEvent` (`{ type: 'changed', projectId, ticketId }`), `event: ping` every 15 s (`HEARTBEAT_MS`)      |
| `GET/POST /session`                                                         | Auth state / exchange token for an HttpOnly cookie                                                                       |

Status changes made by the dropdown, a report, sending, claiming, submitting or reviewing put the ticket at the **top** of its new group (`topRank`). Drags and keyboard moves renumber the destination group (`planMove`).

**Attachment files.** `POST /attachments` checks the file with `checkAttachment` (§1.4), so each kind has its own limit; the route itself refuses a body over the largest limit plus 64 KB of form overhead ("Files can be up to 100 MB.") before reading it. Files are stored as `<id>.<extension of the type>` (`FileStorage`: disk, or memory in tests), images keep their dimensions, and names are cut to 200 characters without splitting one (`attachment.<ext>` when there is none). `GET /attachments/:id/file`:

- Always `Accept-Ranges: bytes`. One range (`bytes=a-b`, `bytes=a-` or `bytes=-n`) answers 206 with `Content-Range` and reads only those bytes from storage (`FileStorage.read(key, range)`; disk storage streams them). iOS Safari doesn't play video without this. A range that starts past the end (or `bytes=-0`) answers 416 with `Content-Range: bytes */size`; several ranges or a malformed one get the whole file (200). HEAD answers the headers of the whole file and ignores `Range`.
- `Content-Disposition: inline; filename="…"; filename*=UTF-8''…` (RFC 5987, with an ASCII fallback), so downloads keep their names. `X-Content-Type-Options: nosniff` and `Cache-Control: private, max-age=31536000, immutable` on every answer with the file.
- Text kinds are served with `; charset=utf-8` and `Content-Security-Policy: sandbox` (defense in depth). Not PDFs: Chrome won't show a sandboxed PDF.

## 4. Agent integration (`apps/agent`)

- **MCP server** (`tracker-mcp`, stdio): tools `list_projects`, `list_statuses`, `list_tickets`, `get_ticket`, `create_ticket`, `update_ticket`, `move_ticket`, `add_comment`, `claim_next_ticket`, `claim_ticket`, `submit_for_review`, `review_ticket`; prompts `work` and `review` that appear as slash commands in Claude Code. Config by env: `TRACKER_URL`, `TRACKER_TOKEN`, `TRACKER_AGENT_NAME`.
- **CLI** (`tracker`): the same operations for shells and agents without MCP.
- Register with Claude Code for every project: `claude mcp add tracker -s user --env TRACKER_URL=http://localhost:4100 --env TRACKER_AGENT_NAME=Claude -- node <repo>/apps/agent/dist/mcp.js`.
- `move_ticket` uses `PATCH /tickets/:key { statusId }` (top of the new group). In agent-facing text the person is called "User".
- **Attachments:** `get_ticket`, `claim_ticket`, `claim_next_ticket` and `tracker show` list a ticket's attachments under the description and each comment's in its card. Images keep their line (name, size, dimensions), and the MCP tools return up to 4 as image content (PNG, JPEG, GIF, WebP up to 1.5 MB). Text files are shown inline in a code fence (`TrackerClient.fetchAttachmentText`), up to 20,000 characters each, ending on a whole line when one is near, and 40,000 in all (Claude Code caps a tool result at about 25,000 tokens); a cut file gets a note with its download URL. Videos, PDFs and text files left out are one line with name, type, size and the download URL (`attachmentFileUrl`, based on `TRACKER_URL`). When `TRACKER_TOKEN` is set and a link is shown, the text ends with a note that downloads need it as `Authorization: Bearer`.
